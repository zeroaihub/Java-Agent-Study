## 第一部分：为什么学（Why）——为什么 Demo 直接上线会"死得很惨"？

第五章的 Demo 很漂亮，但如果你直接把它丢到生产环境，会遇到一连串灾难：

| 场景 | Demo 的问题 | 后果 |
|------|------------|------|
| 用户量上来了 | 没有限流 | 大模型 API 被打爆，账单飙升 |
| 大模型偶尔超时 | 没有熔断/降级 | 请求堆积，服务雪崩 |
| 老板要换模型省钱 | 模型写死在配置 | 每个业务都要改，牵一发动全身 |
| 财务问"这月花了多少" | 没有成本统计 | 一问三不知 |
| 用户输入恶意 Prompt | 没有安全防护 | Prompt 注入、内容违规、法律风险 |
| 线上出问题要排查 | 日志分散、无追踪 | 定位问题靠猜 |

**这就是"Demo 思维"和"架构思维"的本质区别**：Demo 关注"能不能跑通"，架构关注"能不能稳定、安全、经济地跑十年"。

作为要打造**商业级** AI Agent 平台的工程师，你必须提前建立架构地图。否则你会在错误的地基上盖楼，越盖越高，最后推倒重来。本章就是给你这张地图——**它不是让你现在就实现所有东西，而是让你在写每一行代码时，心里都有全局**。

## 第二部分：是什么（What）——商业级 AI 平台的分层架构

一个成熟的企业 AI Agent 平台，通常是这样的分层架构（自上而下）：

```
┌──────────────────────────────────────────────┐
│  接入层  Gateway / BFF                          │  限流、鉴权、路由
├──────────────────────────────────────────────┤
│  应用层  各业务 Agent（客服/办公/交易/公众号）      │  业务编排
├──────────────────────────────────────────────┤
│  Agent 核心层  LLM + Memory + Tools + Workflow  │  第三章的四要素
├──────────────────────────────────────────────┤
│  能力层  RAG检索 / 工具调用 / 多轮记忆 / 结构化输出  │  可复用能力
├──────────────────────────────────────────────┤
│  模型网关层  Model Gateway                       │  统一接入多模型、路由、降级
├──────────────────────────────────────────────┤
│  基础设施层  向量库 / 缓存 / 消息队列 / 监控         │  存储与观测
└──────────────────────────────────────────────┘
        ↑ 横切：可观测性、成本控制、安全合规 ↑
```

对比第五章的 Demo，你会发现 Demo 只覆盖了中间薄薄一层（应用层 + 一点点 Agent 核心）。企业级平台在上下都做了大量加固。

### 六大企业级议题

| 议题 | 解决什么问题 | 关键技术 |
|------|-------------|----------|
| **分层架构** | 职责清晰、可维护、可扩展 | Controller/Service/Gateway 分层 |
| **模型网关** | 多模型统一接入、路由、降级 | 抽象 ModelRouter |
| **成本控制** | 控制 Token 消耗与账单 | Token 统计、缓存、模型分级 |
| **限流熔断** | 防打爆、防雪崩 | Sentinel/Resilience4j |
| **可观测性** | 能监控、能排查 | 日志/指标/链路追踪 |
| **安全合规** | 防注入、防违规、保数据 | Prompt 防护、内容审核、脱敏 |

## 第三部分：怎么用（How）——从 Demo 演进到平台的四步走

不要试图一步到位。架构是**演进**出来的，不是设计出来的。以你的 Demo 为起点，演进路径如下：

### 阶段一：单体 Demo（你现在的位置）

```
Controller → Service → ChatClient → 单个模型
```

**特征**：能跑通，够用于验证想法和内部工具。

### 阶段二：加"能力"（Day 2 - Day 10 大致范围）

在 Service 和模型之间，逐步长出可复用能力：

```
Service → [Memory 多轮记忆] → [Tools 工具调用] → [RAG 知识检索] → ChatClient
```

- **Memory**：让 AI 记住上下文（对话历史存 Redis/DB）
- **Tools（Function Calling）**：让 AI 能查数据库、调 API、发邮件
- **RAG**：让 AI 基于你的私有知识库回答（解决幻觉）
- **结构化输出**：让 AI 返回可解析的 JSON

**这些正是后续章节要逐个攻克的**，它们都插在第五章骨架的"调用大模型"那一步前后。

### 阶段三：加"治理"（模型网关 + 横切能力）

引入 **模型网关（Model Gateway）** 统一管理模型，用伪代码表达其核心思想：

```java
// 模型网关：统一入口，屏蔽多模型，支持路由与降级
public class ModelGateway {

    public String chat(String scene, String message) {
        // 1. 根据业务场景路由到合适的模型（成本优化）
        ModelClient client = route(scene);
        try {
            // 2. 限流检查（防打爆）
            rateLimiter.acquire(scene);
            // 3. 调用 + 记录 Token 消耗（成本统计）
            ChatResult result = client.chat(message);
            costRecorder.record(scene, result.getTokenUsage());
            return result.getContent();
        } catch (RateLimitException e) {
            // 4. 限流时排队或拒绝
            throw new BizException("请求过于频繁，请稍后再试");
        } catch (Exception e) {
            // 5. 主模型失败 → 降级到备用模型（防雪崩）
            return fallbackModel().chat(message);
        }
    }

    private ModelClient route(String scene) {
        // 简单场景用便宜模型，复杂场景用强模型
        return "simple".equals(scene) ? cheapModel : strongModel;
    }
}
```

> 这段伪代码浓缩了四大治理能力：**路由、限流、成本统计、降级**。你会发现，这不过是把你熟悉的"网关/中间件"思想套用到大模型调用上——**你的分布式系统经验在这里完全适用**。

### 阶段四：平台化（多业务复用一套底座）

当客服、办公、交易、公众号多个 Agent 都复用同一套 Memory/Tools/RAG/网关时，你就拥有了一个**平台**，而非一堆散装应用。这正是"30 天打造商业级 AI Agent 平台"的终极目标。

## 第四部分：用在哪（Where）——用架构地图规划你的个人项目

用本章的分层地图，重新审视你的五个个人项目，你会立刻知道每个项目该往哪演进：

### 「零启 Hub」——平台底座

这就是你的**平台层**本身。它应沉淀模型网关、Memory、Tools、RAG 等公共能力，供其他项目复用。这是最应该优先做扎实的部分。

### 「AI 工具导航站」——RAG + 成本控制

- **RAG**：把工具库做成知识库，用户问"有没有能做 XX 的工具"，AI 基于私有库精准回答。
- **成本控制**：高频摘要用便宜模型，走缓存，避免重复调用。

### 「AI 公众号自动化」——Workflow + 结构化输出

- **Workflow**：选题 → 初稿 → 配图建议 → 排版，多步骤编排。
- **结构化输出**：让 AI 返回带标题/正文/标签的 JSON，便于程序处理。

### 「AI 办公助手」——Memory + Tools

- **Memory**：多轮对话记住上下文（"刚才那封邮件再正式一点"）。
- **Tools**：调用日历、邮件、文档 API，真正"办事"而非"聊天"。

### 「AI 量化交易 Agent」——安全合规 + 可观测性

- **安全合规**：交易决策必须可审计、可追溯，每次 AI 判断都要留痕。
- **可观测性**：延迟、成功率、Token 成本必须实时监控——这关系真金白银。

### 规划建议

| 项目 | 首要补强的架构能力 |
|------|-------------------|
| 零启 Hub | 平台底座（网关 + 公共能力） |
| 工具导航站 | RAG + 缓存/成本 |
| 公众号自动化 | Workflow + 结构化输出 |
| 办公助手 | Memory + Tools |
| 量化交易 Agent | 安全合规 + 可观测性 |

**Day1 结束时，你应该能对着这张表，说出每个项目下一步该学什么、该做什么。**

## 第五部分：避坑优化（Optimization）——架构演进的 5 大误区

### 误区 1：过度设计（一上来就上全套微服务）

**问题**：Demo 阶段就搞一堆网关、注册中心、消息队列，复杂度爆炸，迟迟出不了成果。

**正解**：架构是**演进**出来的。先单体跑通，遇到瓶颈再拆。**能用一个 Service 解决的，别上分布式**。

### 误区 2：模型写死，无网关抽象

**问题**：每个业务直接 new ChatClient，换模型时全项目地毯式修改。

**正解**：早期可以简单，但**心里要有"模型网关"这层抽象**，至少把模型调用收敛到一个 Service，为未来统一治理留接口。

### 误区 3：忽视成本，账单爆炸才后悔

**问题**：不统计 Token，不做缓存，不分级模型，月底账单吓一跳。

**正解**：**从第一天就记录 Token 消耗**（第五章日志已埋下伏笔）。相同问题走缓存，简单任务用便宜模型。

### 误区 4：安全合规当事后补丁

**问题**：先做功能，上线后才想起 Prompt 注入、内容违规、数据泄露。

**正解**：安全是**横切关注点**，从设计之初就要考虑：输入校验、Prompt 防注入、输出内容审核、敏感数据脱敏。尤其是量化交易这类高敏感场景。

### 误区 5：没有可观测性，出事靠猜

**问题**：日志分散、无 traceId、无指标监控，线上问题定位靠运气。

**正解**：**可观测性三支柱——日志(Logging)、指标(Metrics)、追踪(Tracing)** 要尽早建立。AI 调用是慢操作、贵操作、易错操作，更需要观测。

### 优化总原则

> **演进优于设计，简单优于复杂，可观测优于纯功能。**
> 先让它跑起来，再让它跑得稳，最后让它跑得省。

## 常见面试题（企业视角）

**Q1：从 Demo 到生产级 AI 应用，主要要补哪些能力？**
A：限流熔断（防打爆防雪崩）、模型网关（多模型治理与降级）、成本控制（Token 统计/缓存/分级）、可观测性（日志/指标/追踪）、安全合规（防注入/内容审核/脱敏）、以及 Memory/Tools/RAG 等业务能力。

**Q2：什么是模型网关？为什么需要它？**
A：模型网关是统一接入多个大模型的中间层，负责路由、限流、降级、成本统计、鉴权。价值：业务与模型解耦、便于统一治理与成本优化、主模型故障可自动降级到备用模型，提升可用性。

**Q3：AI 应用的成本主要花在哪？怎么优化？**
A：主要是大模型的 Token 消耗（输入+输出）。优化手段：相同请求走缓存；简单任务用便宜/小模型，复杂任务才用强模型；精简 Prompt；控制上下文长度；批量处理；监控与告警。

**Q4：AI 应用有哪些特有的安全风险？**
A：Prompt 注入（用户输入操纵 AI 行为）、内容违规（生成不当内容）、数据泄露（敏感信息进 Prompt 或日志）、幻觉误导。防护：输入校验与 Prompt 隔离、输出内容审核、敏感数据脱敏、关键决策留痕可审计。

## 本章练习答案

**思考题 1 参考答案**：
因为真实的需求、瓶颈、流量是随业务发展逐步暴露的，无法在一开始全部预知。一上来就上最完整的分层架构，风险有三：①**过度设计**——为可能永远不会到来的规模付出巨大复杂度成本；②**拖慢交付**——精力耗在基础设施上，迟迟产出不了业务价值；③**方向错误**——过早的架构决策可能与后来真实需求不符，反而要推倒重来。正确做法是"演进式架构"：先满足当前需求，遇到真实瓶颈（性能、成本、协作）再针对性重构，让架构随业务共同生长。

**思考题 2 参考答案**：
模型网关最像传统架构里的 **API 网关 / 服务网关（如 Spring Cloud Gateway）**，或数据库领域的 **数据源路由/分库中间件**。核心价值：①**解耦**——业务代码不直接依赖具体模型，换模型不改业务；②**统一治理**——限流、鉴权、日志、成本统计集中在一处；③**高可用**——主模型故障自动降级备用模型；④**成本优化**——按场景智能路由到不同价位的模型。本质是"把横切关注点从业务里抽出来，收敛到一个统一入口"，这正是网关思想的精髓。

**思考题 3 参考答案**：
因为大模型按 Token 计费，成本随调用量线性甚至指数增长，且**事后难以追溯**。如果不从第一天记录，等账单爆炸时会面临：①**无数据**——不知道钱花在哪个业务、哪个接口，无法针对性优化；②**改造成本高**——事后补埋点要改动大量已上线代码；③**已成事实**——超支的钱已经花出去，无法挽回。从第一天就记录 Token（如第五章日志埋点），能让成本全程可见、可归因、可优化，把成本控制变成"持续治理"而非"事后救火"。
