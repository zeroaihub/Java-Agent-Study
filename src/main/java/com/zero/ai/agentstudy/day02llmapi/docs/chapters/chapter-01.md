## 第一部分：为什么学（核心价值）

### 1. 为什么 AI 应用开发必须掌握 API 调用？

先说结论：**对企业和工程师来说，"用 AI" 几乎等价于 "调 LLM API"。**

一个主流大模型，参数规模在数百亿到万亿级，权重文件几百 GB 起步，
推理时要吃掉成千上万张 GPU 的显存与算力。这意味着：

- 你**无法**把它打进 Jar 包、部署到自己的业务服务器；
- 你**无法**在一台普通机器上加载它；
- 你**唯一现实的选择**，是把模型托管在厂商的推理集群里，通过 HTTP API 远程调用。

所以，模型能力再强，对你而言都是「墙那边的一个远程服务」。
**能不能把它接进你的 Java 系统、治理好这次远程调用，才是你作为 AI Agent 工程师的核心竞争力。**

这也是你多年 Java/Spring 经验的迁移点：一次 LLM 调用，本质就是一次
**带鉴权、要限流、会超时、需重试、得监控、还花钱**的远程 RPC。你太熟悉这套了。

### 2. 为什么不能只使用 ChatGPT 网页？

网页版（ChatGPT / 各家对话页）是给**终端用户**用的，不是给**产品**用的。它的致命局限：

| 维度 | 网页版 | API |
| --- | --- | --- |
| 集成能力 | 只能人肉复制粘贴 | 可嵌入任意系统、批量自动化 |
| 定制人设 | 每次手动输入 | System Prompt 固化角色 |
| 数据打通 | 无法读你的数据库/知识库 | 可结合 RAG、工具调用 |
| 多用户 | 一个账号一个人 | 一套服务支撑百万用户 |
| 可控性 | 无法控温度/长度/日志 | 参数、日志、成本全可控 |
| 商业化 | 不能对外收费 | 可封装成你自己的产品收费 |

一句话：**网页版是"用别人的产品"，API 是"造你自己的产品"。**

### 3. API 对于商业产品意味着什么？

意味着**你能把模型能力变成可编排、可控制、可计费、可规模化的服务**：

- **可编排**：把模型调用嵌进业务流程（审批、客服、检索……）。
- **可控制**：控制人设、温度、长度、上下文，让输出稳定可用。
- **可计费**：按你自己的定价对外收费，模型 Token 成本是你的原料成本。
- **可规模化**：一套服务背后接厂商弹性算力，轻松扛百万级用户。

### 4. 为什么所有 AI SaaS 产品都依赖模型 API？

因为**自建大模型的门槛，99% 的公司迈不过去**：需要顶尖算法团队、
巨额 GPU 投入、持续的数据与训练成本。绝大多数 AI SaaS 的真实形态是：

```
自研的价值 = 业务理解 + 工程能力 + 数据 + Prompt/RAG/Agent 编排
底座能力   = 调用厂商 LLM API
```

结合几类典型产品看 API 的不可替代性：

- **AI 客服**：把企业知识库 + 对话历史拼进 messages，调 API 生成回答。没有 API，客服机器人无从谈起。
- **AI 写作**：用户给主题，产品把「写作人设 + 要求 + 素材」组装成 Prompt 调 API 产出文案。
- **AI 知识库**：先检索（RAG）再把命中片段塞进 Prompt 调 API 做「有依据的回答」。
- **AI Agent**：模型是 Agent 的「大脑」，每一次「思考 / 决策 / 调用工具」都是一次 API 调用。

**结论：API 是把"模型智能"注入产品的唯一管道。管道断了，产品就是空壳。**

## 第二部分：是什么（概念与原理）

### 2.1 LLM API 到底是什么

它不是一个本地函数，而是一个**跨网络的远程推理服务**。你发一段结构化请求（谁说了什么），
它返回模型算出来的下一段话，并告诉你花了多少 Token。

### 2.2 一次调用的完整链路

```
Java 应用
   ↓  ① 带 API Key 的 HTTPS 请求
API Gateway（鉴权 / 限流 / 路由）
   ↓ ② 校验通过，转发
Model Service（Chat Completion 服务）
   ↓  ③ 排队 + 组 batch，拼装模型输入
模型推理（GPU 前向计算，逐 Token 生成）
   ↓  ④ 生成完成
Response（一次性 JSON 或 SSE 流）
   ↓
返回 Java 应用
```

各环节职责：

- **API Gateway**：校验 API Key（鉴权）、按 RPM/TPM 做限流、把请求路由到合适的模型集群。
- **Model Service**：把你的 `messages` 转成模型能吃的输入序列，调度推理。
- **推理层**：真正"烧钱"的地方，逐个 Token 前向计算生成结果。
- **Response**：非流式一次性返回完整 JSON；流式用 SSE 逐块推送。

### 2.3 请求 / 响应的核心字段

请求（最小可用）：

```json
{
  "model": "gpt-4o-mini",
  "messages": [
    { "role": "system", "content": "你是一位资深 Java 架构师。" },
    { "role": "user",   "content": "什么是 IOC？" }
  ]
}
```

响应（关键字段）：

- `choices[0].message.content`：AI 的回答正文。
- `finish_reason`：`stop` 正常结束 / `length` 被 max_tokens 截断。
- `usage.total_tokens`：本次消耗 Token，**直接对应你的账单**。

### 2.4 一句话记住

> **LLM API = 把"输入的对话上下文"发过去，把"模型算出来的下一段话 + 花费"拿回来的远程服务。**

## 第三部分：怎么用（本章不写业务代码，只建立最小心智模型）

本章不落代码（代码从第五章开始）。但你要在脑中建立**最小调用心智模型**：

1. **准备身份**：拿到 API Key，放进环境变量 / 配置中心（**绝不硬编码**）。
2. **组装请求**：选 `model`，拼 `messages`（system 定人设、user放问题），按需设 `temperature` / `max_tokens`。
3. **发起调用**：走 HTTPS POST；在企业里，这一步要封装进独立的 **LLM Client 层**。
4. **处理响应**：取 `content` 给业务，记录 `usage` 做成本统计，处理 `finish_reason`。
5. **治理这次调用**：超时、重试、限流、日志、脱敏——像对待任何一次远程 RPC 一样。

对应 Spring AI 的心智映射（后续章节展开）：

```
ChatClient  →  封装好的 LLM Client
.system()   →  组装 system message（人设）
.user()     →  组装 user message（问题）
.options()  →  temperature / maxTokens 等参数
.call()     →  发起一次远程推理调用
.content()  →  取回答正文
```

## 第四部分：用在哪（真实场景）

同一条"调 API"的地基，撑起了几乎所有 AI 产品。10 个典型案例：

1. **AI 客服**：知识库 + 会话历史 → API → 自动答疑。
2. **AI 搜索**：检索结果 → API → 生成有出处的总结（对话式搜索）。
3. **AI 写作**：写作人设 + 要求 → API → 文案/公众号/邮件。
4. **AI 编程助手**：代码上下文 → API → 补全/解释/重构建议。
5. **AI 知识库**：RAG 检索命中片段 → API → 带依据的问答。
6. **AI 办公助手**：会议纪要/文档 → API → 摘要、待办、日程。
7. **AI 教育**：学生问题 + 学情 → API → 个性化讲解与出题。
8. **AI 营销**：用户画像 + 商品 → API → 个性化文案/推荐话术。
9. **AI 金融分析**：研报/公告 → API → 摘要、风险点提取。
10. **AI 量化 Agent**：行情/新闻 → API（作为大脑）→ 决策/信号解读。

**它们为什么都必须调 API？** 因为模型太大只能远程托管，
而这些产品的价值全在于**"把自己的数据/流程 + 模型智能"组合起来**——
组合的唯一接口，就是 LLM API。

## 第五部分：避坑与优化（企业最佳实践）

即便只是"入口认知"章节，也先埋下企业级红线，后续章节逐条落地：

1. **API Key 安全**：绝不硬编码、不进 Git；用环境变量 / 配置中心；泄露即刻吊销轮换。
2. **成本意识**：每次调用都花 Token，`usage` 必须记录；上线前先估算量级。
3. **超时兜底**：远程调用必设超时，不能让业务线程无限等待。
4. **限流认知**：厂商有 RPM/TPM 限制，高并发下必然触发，需重试 + 排队。
5. **不要直连**：Controller/Service 不直接感知"在调 OpenAI"，统一走 LLM Client 层。
6. **日志脱敏**：用户输入可能含隐私，记日志要脱敏，回答只记长度不记全文。
7. **可替换**：面向接口封装 client，方便未来换厂商（通义/DeepSeek 等）。
8. **参数默认值**：temperature / max_tokens 给合理默认，避免调用方乱传。
9. **失败降级**：模型不可用时要有降级策略（提示、缓存、兜底话术）。
10. **观测优先**：耗时、Token、成功率要能被监控，别让线上问题"黑盒"。

**本章最佳实践总结**：把每一次 LLM API 调用，都当成一次**需要治理的、花钱的远程 RPC**——
这正是 Java 工程师最擅长的事，也是你相对算法背景转型者的护城河。
