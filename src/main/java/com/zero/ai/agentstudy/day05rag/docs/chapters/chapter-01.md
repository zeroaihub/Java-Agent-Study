# 第一章：为什么需要 RAG？

> Day5 · 第一章学习笔记。本章只讲「动机」，不写代码。先想通「为什么」，后面写代码才不会迷路。

## 一、为什么学（核心价值）

### 1.1 一个真实的痛点场景

你在一家公司做了个 AI 客服，用的是最强的大模型。用户问：

> 「我买的 XX 型号冰箱，保修期是几年？延保怎么办理？」

模型自信地回答了……**但全是错的**。因为这是你公司**内部的售后政策**，模型训练时根本没见过。它只能靠「猜」，猜出来的东西就是「幻觉」。

这就是所有企业 Agent 落地的第一道坎：**模型不知道你的私有知识**。

### 1.2 LLM 的三大知识边界

1. **知识有截止时间（时效性）**：模型是用某个时间点前的数据训练的，之后发生的事一概不知（新政策、新产品、今天的订单）。
2. **不知道私有知识**：公司内部文档、合同、代码库、客户数据，模型训练时从未见过。
3. **会产生幻觉**：当它不知道时，不会说「我不知道」，而是**一本正经地编**。这在企业场景是致命的。

### 1.3 为什么 OpenAI、Google、微软都在用 RAG

- **微软 Copilot**：企业版能回答「你公司的文档、邮件、Teams 记录」，靠的就是 RAG（Microsoft Graph + 向量检索）。
- **Google**：搜索 + Gemini 的「基于搜索结果生成答案」本质就是 RAG。
- **OpenAI**：Assistants / GPTs 的「知识文件（File Search）」就是内置的 RAG。

一句话：**所有「让 AI 懂你自己数据」的产品，底座都是 RAG。**

### 1.4 学会 RAG 你能做什么产品

- 企业知识库问答、智能客服、智能文档助手
- 法律 / 医疗 / 金融领域的专业问答 Agent
- 代码库问答助手（问「这个函数在哪调用」）
- 个人第二大脑 / 笔记问答

## 二、是什么（概念 + 为什么这样解决）

### 2.1 三种「让模型懂私有知识」的方案对比

面对「模型不懂私有知识」，工程上有三条路：

#### 方案 A：把知识塞进 Prompt（In-Context）

把相关文档直接粘到提示词里，让模型「看着资料回答」。

思路对，但直接全塞不行，原因见下面「为什么不能塞 1000 页 PDF」。**RAG 本质就是这个方案的「聪明版」——不塞全部，只塞相关的那几段。**

#### 方案 B：微调模（Fine-tune）

用私有数据再训练模型，把知识「炼」进模型参数里。

问题：
- **成本高、周期长**：准备数据 + 训练 + 评估，动辄几天几万块。
- **更新难**：政策改了、加了新文档，就要重新训练。
- **会遗忘**：微调可能让模型忘掉部分通用能力（灾难性遗忘）。
- **无法追溯出处**：答案从参数里「流」出来，你没法告诉用户「这句话出自哪份文件」。
- **知识边界模糊**：模型仍可能把微调知识和原有知识混着编。

> 结论：微调适合「改变模型的风格 / 格式 / 领域语感」，**不适合「灌入频繁变化的事实性知识」**。

#### 方案 C：RAG（检索增强生成）✅

不改模型参数，而是：**提问时，先从知识库检索出最相关的几段资料，把资料 + 问题一起给模型，让它基于资料回答。**

优势：
- **知识随时更新**：改文档 = 更新向量库，无需重训模型。
- **成本低**：只在提问时多做一次「检索」，不训练。
- **可追溯**：答案来自具体的 Chunk，能标注引用出处。
- **私有可控**：数据在你自己的向量库里，不进模型参数。
- **抗幻觉**：模型「有据可依」，可以约束它「资料里没有就说不知道」。

### 2.2 为什么不能把 1000 页 PDF 全部发给 AI

很多新手第一反应：「那我把整份文档都贴进 Prompt 不就行了？」不行，四个原因：

1. **上下文窗口有限**：模型能接收的 Token 有上限（比如 8K / 32K / 128K）。1000 页远超上限，**塞不下**。
2. **超出部分被截断**：塞不下的内容会被直接丢掉，模型看不到，等于没给。
3. **每次都很贵**：就算塞得下，**每次提问**都要把整本书当输入 Token 计费，成本爆炸。
4. **信息被稀释（Lost in the middle）**：内容太长，模型注意力被分散，**真正相关的那句话反而被淹没**，回答质量不升反降。

> 所以正确做法是：**不塞全部，只塞「和这个问题相关的那几段」。** 而「怎么找出相关的那几段」——就是 RAG 里的「检索（Retrieval）」。

### 2.3 RAG 到底解决了什么问题（一张表总结）

| 问题 | 不用 RAG | 用 RAG |
| --- | --- | --- |
| 私有知识 | 模型不知道，瞎编 | 从知识库检索真实资料 |
| 知识更新 | 微调要重训 | 更新向量库即可，实时生效 |
| 幻觉 | 高（无依据） | 低（有据可依，可约束） |
| 成本 | 全文塞入=贵 / 微调=贵 | 只检索少量相关片段，便宜 |
| 出处追溯 | 无法 | 可返回引用来源 |
| 上下文限制 | 塞不下 / 被截断 | 只放 Top-K，稳定可控 |

### 2.4 RAG 的直觉类比（帮助记忆）

> RAG = **开卷考试**。
>
> - 不用 RAG 的 LLM = 闭卷考试，全凭脑子记（记不住就编）。
> - 微调 = 考前疯狂背书（背了也可能背错、背旧）。
> - RAG = 允许你带资料进考场，答题前先**翻到相关那一页**，照着答（准、可查、可更新）。

## 三、怎么用（本章无代码，仅建立心智模型）

本章是「机章」，不写代码。但你要在脑子里装下这张最简流程图，后面所有代码都围绕它展开：

```
【离线：把知识灌进去，做一次】
 文档 → 切分成小块 → 每块变向量 → 存进向量库

【在线：用户每次提问】
 问题 → 变向量 → 去向量库找最像的几块 → 把这几块+问题给模型 → 模型基于资料回答
```

记住一句话：**RAG = 先找资料，再让模型看着资料说话。**

## 四、用在哪（真实项目案例）

1. **企业知识库问答**：员工问「报销流程」「年假天数」，Agent 从制度文档检索后回答。
2. **AI 智能客服**：从产品手册 / FAQ / 售后政策检索，回答用户咨询，答错率大幅下降。
3. **法律 Agent**：从法条、判例、合同库检索，辅助律师起草与检索，且**必须标注条文出处**。
4. **医疗 Agent**：从诊疗指南、药品说明书检索，辅助医生，绝不能靠模型「记忆」乱答。
5. **金融 Agent**：从研报、财报、风控政策检索，回答投研问题，要求可追溯、可审计。
6. **代码助手**：把代码库 Embedding，问「这个方法在哪被调用、怎么用」，检索相关代码片段回答。

> 共同点：**这些领域的知识是私有的、频繁更新的、且答错代价极高**。所以它们**必须**用 RAG（检索真实资料 + 可追溯出处），而不能靠模型记忆或微调。

## 五、避坑与最佳实践（第一章相关的认知误区）

1. **误区：RAG 能消灭幻觉。** 不能，只能大幅降低。若召回到无关资料，模型仍可能编。要配合「资料里没有就回答不知道」的 Prompt 约束。
2. **误区：文档越多回答越准。** 不一定。垃圾文档、重复文档会污染召回，「垃圾进垃圾出」。
3. **误区：直接全文塞 Prompt 更简单。** 见 2.2，塞不下、贵、还会被淹没。
4. **误区：微调比 RAG 高级。** 两者解决不同问题。事实性、频繁更新的知识用 RAG风格 / 格式 / 领域语感用微调。二者可结合。
5. **误区：RAG 不用管数据质量。** 恰恰相反，RAG 的天花板由知识库质量决定。**数据治理是 RAG 工程的一等公民。**

**架构建议（认知层面）**：把 RAG 看成两条独立可演进的流水线（离线索引流、在线问答流），每一环节（解析 / 切分 / Embedding / 存储 / 检索 / 生成）都能独立替换和优化。这是后面所有代码分层的根本原因。

## 六、面试问题与参考答案

**Q1：为什么企业不直接微调模型，而用 RAG？**
A：微调成本高、周期长、知识更新要重训、可能灾难性遗忘、且无法追溯出处；而事实性知识频繁变化。RAG 不改参数，提问时检索真实资料注入 Prompt，知识可实时更新、成本低、可追溯、私有可控，因此更适合「灌入频繁变化的事实性知识」。微调更适合改变风格 / 格式 / 领域语感，二者可结合。

**Q2：为什么不能把整份文档塞进 Prompt？**
A：上下文窗口有限（塞不下 / 被截断）、每次提问按全文计费（贵）、内容过长导致注意力稀释（Lost in the middle，相关信息被淹没）。正确做法是只检索并注入与问题最相关的 Top-K 片段。

**Q3：RAG 解决了 LLM 的哪些核心问题？**
A：知识时效性（可实时更新）、私有知识（可注入企业数据）、幻觉（有据可依可约束）、成本（只注入少量相关片段）、可追溯（返回引用出处）。

## 本章小结

- LLM 有三大知识边界：时效性、私有知识、幻觉。
- 解决私有知识有三条路：Prompt 直塞（塞不下 / 贵 / 被淹没）、微调（贵 / 难更新 / 无出处）、**RAG（推荐）**。
- RAG =先检索相关资料，再让模型看着资料回答，本质是「开卷考试」。
- RAG 由「离线索引流」和「在线问答流」两条主线组成。
- 记住这张图：**文档→切分→向量→入库（离线）；问题→向量→检索→拼 Prompt→生成（在线）**。
