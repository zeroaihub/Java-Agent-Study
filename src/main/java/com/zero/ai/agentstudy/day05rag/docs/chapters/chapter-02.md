## 一、为什么学（核心价值）

第一章我们知道 RAG = 开卷考试。但「开卷考试」这句话太模糊，落到工程上你必须回答六个问题：

1. 文档凭什么能被「按语义」找出来？（→ Embedding）
2. 一份 100 页文档，检索的最小单位是什么？（→ Chunk）
3. 向量存在哪、怎么建索引才能查得快？（→ Vector Store）
4. 「最相关」到底用什么数学标准衡量？（→ Similarity）
5. 找回来的东西叫什么、取几个？（→ Retrieval / Top-K）
6. 找到资料后怎么变成模型能用的输入？（→ Augmented Generation）

把这六个问题串起来，就是 RAG 的完整原理。**理解了这张图，后面第 3~7 章都是在给这张图的每个环节写代码。**

## 二、是什么（原理 + 完整流程图）

### 2.1 RAG 的两条流水线（再强调一次，这是骨架）

RAG 永远是「一次离线 + 多次在线」：

- **离线索引流（Indexing）**：把知识灌进库，通常灌一次（或文档更新时增量灌）。
- **在线问答流（Query）**：用户每问一次，跑一次。

### 2.2 离线索引流：详细 ASCII 图

```
┌─────────────────────────────────────────────────────────────┐
│                      离线索引流 (Indexing)                       │
└──────────────────────────────────────────────────────────────┘

  原始文档                解析                切分
 ┌─────────┐  Parse   ┌─────────┐  Split   ┌──────────┐
 │ PDF/Word│ ───────▶ │ 纯文本   │ ───────▶ │ Chunk 列表│
 │ 网页/MD │          │(去格式)  │          │ c1 c2 c3…│
 └─────────┘          └─────────┘          └────┬─────┘
                                                 │ 每个 Chunk
                                                 ▼
                                          ┌──────────────┐
                                Embedding │ 文本 → 向量    │
                                          │ c1 → [0.1,...] │
                                          │ c2 → [0.7,...] │
                                          └──────┬────────┘
                                                ▼
                                       ┌────────────────────┐
                                       │   Vector Store      │
                                       │  存: 向量 + 原文     │
                                       │      + 元数据(来源)  │
                                       │  建: 相似检索索引     │
                                       └────────────────────┘
```

关键点：
- **存的不只是向量**，还要存「原文本 + 元数据(文件名/页码/租户/权限)」。向量只用来「找」，最终喂给模型的是**原文**。
- 元数据是后面做「引用出处、多租户过滤、权限控制」的基础。

### 2.3 在线问答流：详细 ASCII 图

### 2.4 六大概念逐个拆解

#### ① Embedding（嵌入）——文本变向量
把一段文本映射成固定长度的浮点数组（如 1536 维）。**语义相近的文本，向量距离也近。** 它是 RAG「按意思找」而不是「按关键词找」的基。（第三章深入）

#### ② Chunk（切块）——文档变小段
长文档不能整篇 Embedding：太长会超模型输入限制，且一个向量代表太多内会「什么都像、什么都不像」。所以要切成小块，每块单独向量化。**切分质量直接决定召回质量。**（第四章深入）

#### ③ Vector（向量）——语义空间里的坐标
就是一串数字，代表文本在「语义空间」中的位置。你可以想象成：把所有句子放进一个高维地图，意思相近的句子挨在一起。

#### ④ Similarity Search（相似检索）——怎么算「像」
三种常见度量：
- **余弦相似度（Cosine）**：看两个向量「方向」是否一致，范围 -1~1，越大越像。RAG 最常用。
- **内积（Dot Product）**：方向 + 长度都考虑，向量归一化后与余弦等价。
- **欧氏距离（L2）**：看两点直线距离，越小越像。

> 直觉：余弦只关心「说的是不是同一个意思」，不关心「说了多长」，所以最适合语义检索。

#### ⑤ Retrieval（召回）——取回 Top-K
按相似度排序，取最像的前 K 个 Chunk（K 常取 3~8）。K 太小可能漏关键资料，K 太大引入噪声且更贵。这是 RAG 最关键的调参点之一。

#### ⑥ Augmented Generation（增强生成）——拼 Prompt 让模型答
把召回的 Chunk 原文 + 用户问题，按模板拼成 Prompt，交给 LLM 生成答案。模板里通常有一句「铁律」：**「只依据以下资料回答，资料中没有就回答不知道」**，用来压制幻觉。

### 2.5 一句话把六个概念串起来

> 把文档**切块(Chunk)**，每块用 **Embedding** 变成 **向量(Vector)** 存进 **向量库(Vector Store)**；提问时把问题也变向量，用**相似检索(Similarity)** 召回**(Retrieval)** 最像的 Top-K 块，拼进 Prompt 让 LLM **增强生成(Augmented Generation)** 答案。

## 三、怎么用（本章仍无代码，做一次「人肉走查」）

拿「我一年有几天年假?」走一遍，验证你真的懂了：

1. **离线（已做过）**：制度文档被切成 `["员工年假为10天...", "试用期不享受年假...", "年假需提前3天申请..."]`，每条变向量存库。
2. **在线-Embedding**：问题「我一年有几天年假?」→ 向量 Q。
3. **在线-检索**：Q 与库里每条向量算余弦，`"员工年假为10天"` 分数最高被选中。
4. **在线-召回**：取 Top-3 原文。
5. **在线-增强**：拼成「资料[1][2][3] + 问题」。
6. **在线-生成**：模型输出「年假 10 天，需提前 3 天申请」，并标注来源。

> 注意第 2 步和离线时用的**必须是同一个 Embedding 模型**——否则问题向量和文档向量不在同一个空间，比较相似度毫无意义。这是新手最常见的坑之一。

## 四、用在哪（真实项目中的流程映射）

- **AI 客服**：离线灌产品手册/FAQ；在线用户问题→召回 FAQ 片段→生成答复并给出处。
- **法律 Agent**：离线灌法条/判例，元数据存「条文号」；召回后必须回显条文出处。
- **代码助手**：离线把每个函数/文件切块 Embedding；在线问「登录逻辑在哪」→召回相关代码块。
- **医疗 Agent**：离线灌诊疗指南；召回时用元数据过滤「科室/版本」，避免用过时指南。

共同结构：**都是这张两条流水线的图，只是文档类型、元数据、Prompt 铁律不同。**

## 五、避坑与最佳实践（针对原理环节）

1. **问题和文档了不同 Embedding 模型** → 向量不可比，召回全乱。必须同一模型。
2. **只存向量不存原文** → 召回回来没法喂给模型，也没法显示出处。必须存原文 + 元数据。
3. **Top-K 拍脑袋定** → 太小漏答、太大引噪+涨成本。要按业务实测调。
4. **不设「无依据就说不知道」的铁律** → 召回不到也硬编，幻觉照旧。
5. **相似度度量选错** → 未归一化就用内积、或该用余弦却用 L2，排序失真。
6. **离线切分和在线检索脱节** → 切得太碎，召回的片段缺上下文，模型看不懂。
7. **忽略元数据** → 无法做多租户隔离、权限过滤、出处引用，上不了生产。

**架构建议**：把六个概念对应成六个**可替换的组件**（Parser / Splitter / Embedding / VectorStore / Retriever / Generator）。这正是第六章代码分层的蓝图——每个组件都能独立升级（比如把内存向量库换 pgvector、给 Retriever 加 Rerank），其余不动。

## 六、面试问题与参考答案

**Q1：完整描述一次 RAG 问答的数据流。**
A：离线时文档经解析→切分→Embedding→连同原文和元数据存入向量库；在线时用户问题用**同一个** Embedding 模型转向量，在向量库做相似检索取 Top-K 相关 Chunk，将其原文与问题按模板拼成 Prompt（含「仅依据资料回答」约束）交给 LLM 生成答案，并可回显出处。

**Q2：为什么问题和文档必须用同一个 Embedding 模型？**
A：不同模型产出的向量处于不同的语义空间，坐标含义不一致，跨空间算相似度没有意义，会导致召回错乱。必须同模型（同维度、同版本）保证可比。

**Q3：余弦相似度、内积、欧氏距离怎么选？**
A：语义检索最常用余弦，只看方向（意思是否一致）不受文本长度影响；向量归一化后内积与余弦等价，工程上常用内积加速；欧氏距离看绝对距离，对未归一化向量敏感，较少直接用于纯语义召回。

**Q4：Top-K 如何取值？**
A：无固定值，常从 3~8 起步，按业务实测：召回不全就加大 K，噪声多/成本高就减小 K，并配合 Rerank 精排（第八章）。

## 本章小结

- RAG = 两条流水线：离线索引 + 在线问答。
- 六大概念：Embedding(变向量)、Chunk(切块)、Vector(坐标)、Similarity(算像)、Retrieval(取 Top-K)、Augmented Generation(拼 Prompt 生成)。
- 向量库要存「向量 + 原文 + 元数据」，原文喂模型，元数据做出处/权限/租户。
- 铁律：问题与文档用同一 Embedding 模型；Prompt 里加「无依据就说不知道」。
