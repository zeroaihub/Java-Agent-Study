# 第四章：Chunk 切分 —— 为什么切、怎么切、切多大

> Day5 · 第四章学习笔记。这是 RAG 离线索引流的「第一道工序」，也是最影响召回质量、却最容易被忽视的一步。

---

## 一、为什么学（核心价值）

一份《员工手册》可能有 5 万字。如果我们把整份文档直接 Embedding 成一个向量存起来，会发生什么？

1. **超出模型输入上限**：大多数 Embedding 模型输入上限是 512 ~ 8192 token，5 万字直接被截断，后半段全丢。
2. **语义被稀释**：整篇文档揉成一个向量，就像把一整本书的意思压成一个词——「年假」「报销」「考勤」全混在一起，向量谁都不像，谁都召回不准。
3. **回答时塞不进 Prompt**：就算召回了，5 万字也塞不进 LLM 的上下文窗口。

**结论**：必须把长文档切成一段段「大小合适、语义完整」的小块（Chunk），再逐块 Embedding**切得好，召回准；切得烂，后面再强的模型也救不回来。** 这就是「Garbage In, Garbage Out」在 RAG 里的体现。

## 二、是什么（概念 + 底层原理）

### 2.1 一句话定义

> Chunk（切块）= 把一份长文档，按一定策略切成若干「大小可控、语义尽量完整」的文本片段，每个片段将独立 Embedding、独立存储、独立被召回。

### 2.2 切分在流程中的位置

```
原始文档(PDF/Word/TXT)
      │  ① Parser 解析成纯文本
      ▼
   一大段纯文本
      │  ② Splitter 切分  ← 【本章】
      ▼
  [Chunk1][Chunk2][Chunk3]...   每块几百字
      │  ③ Embedding 逐块向量化
      ▼
  [向量1][向量2][向量3]...  → 存入向量库
```

### 2.3 三个核心参数

| 参数 | 含义 | 直觉 |
|------|------|------|
| **chunkSize（块大小）** | 每块最多多少字符/token | 太大→语义稀释、塞不进Prompt；太小→上下文断裂 |
| **overlap（重叠）** | 相邻两块重复的字数 | 防止把一句完整的话从中间切断，保留上下文连续性 |
| **separator（分隔符）** | 优先在哪里切（段落>句号>逗号） | 尽量在「自然边界」切，别把一句话拦腰斩断 |

### 2.4 为什么需要重叠（overlap）？

假设不重叠，硬按 200 字切：

```
...员工入职满一年后，年假为    │切│    10天，可分次休完...
        Chunk A 结尾              Chunk B 开头
```

用户问「入职满一年年假几天？」——答案「10天」被切到了 B，而「入职满一年」在 A。两块都不完整，召回哪块都答不全。

**加上 overlap（比如重叠 50 字）**：B 会把 A 结尾的「年假为」也带上，这样「入职满一年…年假为 10 天」在某一块里是连续的，召回就能答全。

### 2.5 常见切分策略（由简到繁）

1. **固定长度切分（Fixed-size）**：每 N 个字符切一刀。最简单，但会切断句子。
2. **按分隔符切分（Recursive / by separator）**：优先按「段落 → 句号 → 逗号」递归切，尽量保留语义边界。**工程首选。**
3. **按语义切分（Semantic）**：用模型判断语义边界再切。效果好但慢、贵，进阶方案。
4. **按结构切分（Markdown/HTML 标题层级）**：适合结构化文档，按标题分块。

本项目采用 **② 递归分隔符 + 重叠** 这一工程主流方案，兼顾简单与效果。

## 三、怎么用（实战：写一个 TextSplitter）

本章产出第二个代码文件：`splitter/TextSplitter.java`。它接收一大段文本 + chunkSize + overlap，返回 `List<String>` 切块结果。

**设计思路（企业写法）**：
- 面向接口：先定义能力，未来可换「递归切分」「语义切分」不同实现。
- 参数可配：chunkSize / overlap 由外部传入或从配置读，不写死。
- 边界安全：空文本返回空列表；overlap 不能 ≥ chunkSize（否则死循环）。

### 3.1 核心算法（滑动窗口 + 重叠）

```
start = 0
while start < 文本长度:
    end = min(start + chunkSize, 文本长度)
    取 [start, end) 作为一个 chunk
    start = end - overlap    // 回退 overlap 个字符，制造重叠
```

关键点：`start = end - overlap` 就是「重叠」的实现——下一块的起点往回退一点。

### 3.2 Java（本项目）

代码见下方 `TextSplitter.java`，已生成到 `day05rag/splitter/`。核心是滑动窗口 + 防御式参数校验，每个方法带注释。

### 3.3 Python 对照（帮助理解，不在本项目运行）

```python
def split_text(text, chunk_size=300, overlap=50):
    chunks, start = [], 0
    while start < len(text):
        end = min(start + chunk_size, len(text))
        chunks.append(text[start:end])
        if end == len(text):
            break
        start = end - overlap
    return chunks
```

可以看到 Java 和 Python 逻辑完全一致，只是语法不同。生产级库（LangChain 的 `RecursiveCharacterTextSplitter`、Spring AI 的 `TokenTextSplitter`）在此基础上增加了「按分隔符优先级递归切」和「按 token 而非字符计数」。

## 四、用在哪（真实项目）

1. **企业知识库**：员工手册、产品文档、API 文档入库前都要切分。
2. **客服 / 法律 / 医疗问答**：长条款、长病历切成条款级 / 段落级 chunk，精准召回某一条。
3. **代码问答（如本训练营）**：按函数 / 类 / 文件切分代码，召回相关代码片段。
4. **论文 / 报告分析**：按章节切分，问「第三章讲了什么」能精准定位。

共同点：**只要文档长到超过模型窗口，或需要「定位到某一小段」，就要切分。**

## 五、避坑与最佳实践

1. **chunkSize 太大** → 语义稀释，一块里塞太多主题，召回不准，且塞不进 Prompt。经验值：中文 300~500 字 / 英文 500~1000token 起步。
2. **chunkSize 太小** → 上下文断裂，一句话被切碎，召回到半句答不全。
3. **overlap 设为 0** → 边界处的完整语义被切断（如 2.4 的例子），召回质量下降。经验值：overlap 取 chunkSize 的 10%~20%。
4. **overlap ≥ chunkSize** → `start = end - overlap` 可能不前进甚至倒退，**死循环**！必须校验 `overlap < chunkSize`。
5. **无脑固定长度切** → 把句子、表格、代码从中间劈开。优先按段落 / 句号等自然边界切。
6. **切分前没清洗** → 页眉页脚、目录、乱码噪声进入 chunk，污染向量。解析后清洗再切。
7. **忽略元数据** → 切完只存文本，丢了「来自哪个文档、第几页、第几块」。召回后无法溯源、无法给出处。chunk 应携带元数据（第五章向量库会存）。
8. **所有文档一刀切用同一参数** → 代码、法律条款、聊天记录结构差异大。可按文档类型用不同策略/参数。

**最佳实践**：先按「段落」切，段落过大再按「句子」递归细分；overlap 取 10%~20%；每个 chunk 带上来源元数据；上线后用真实问题回测召回效果，反调 chunkSize。

## 六、面试问题与参考答案

**Q1：为什么 RAG 要先做 Chunk 切分，不能整篇 Embedding？**
A：三点——① 超出 Embedding 模型输入上限会被截断丢信息；② 整篇揉成一个向量语义被稀释、召回不准；③ 整篇塞不进 LLM 上下文窗口。切成语义完整的小块才能精准召回、精准喂给模型。

**Q2：overlap（重叠）的作用是什么？设多大？**
A：防止把一句完整语义从块边界处切断，保留上文连续性，避免召回到「半句话」。经验取 chunkSize 的 10%~20%；且必须 < chunkSize，否则滑动窗口死循环。

**Q3：chunkSize 怎么定？太大太小各有什么问题？**
A：太大→语义稀释、塞不进 Prompt；太小→上下文断裂、答不全。需按文档类型和召回效果调，中文常见 300~500 字起步，上线后用真实问题回测反调。

**Q4：有哪些切分策略？工程上常选哪种？**
A：固定长度、递归分隔符、语义切分、按结构（标题）切分。工程首选「递归分隔符 + 重叠」，兼顾简单与语义完整；对结构化文档可用按标题切分；语义切分效果好但慢贵，进阶用。

## 本章小结

- Chunk = 把长文档切成「大小可控、语义完整」的小块，逐块 Embedding、存储、召回。
- 三参数：chunkSize（块大小）、overlap（重叠）、separator（切分边界）。
- overlap 防止语义被边界切断；必须 < chunkSize，否则死循环。
- 工程首选「递归分隔符 + 重叠」；chunkSize 中文 300~500 字起步，overlap 取 10%~20%。
- 每个 chunk 应携带来源元数据，为召回溯源做准备。
- 本章产出代码：`splitter/TextSplitter.java`（滑动窗口 + 重叠 + 参数校验）。
