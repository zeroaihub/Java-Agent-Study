# 第五章：VectorStore 向量存储 —— 向量库怎么设计、怎么写、怎么升级

> Day5 · 第五章学习笔记。前面我们把文档「切块」并能「算相似度」了，本章解决：**这些向量存到哪里？怎么存才能被快速检索？** 这是 RAG 的「记忆中枢」。

---

## 一、为什么学（核心价值）

回顾离线索引流：文档 → 切块 → Embedding → **存储** → （在线）检索。

Embedding 算出来的一堆 `float[]` 如果只放在内存变量里，程序一重启就全没了；而且随便放在 `List` 里，查询时要和每一条挨个算相似度——数据量一大就慢得没法用。

**向量库（VectorStore）解决三件事：**
1. **存**：把「向量 + 原文 + 元数据」三件套持久化保存。
2. **查**：给一个查询向量，快速找出「最相似的 Top-K 条」。
3. **管**：增、删、更新知识库内容。

**为什么单独学**：RAG 的召回质量和性能，一半取决于向库。理解它的设计，你才知道内存版够不够用、什么时候该上 pgvector / Milvus，面试也必问。

## 二、是什么（概念 + 底层原理）

### 2.1 一句话定义

> VectorStore（向量库）= 专门用来「存储向量并按相似度检索」的存储组件。核心能力是「给一个向量，返回库中与它最相似的若干条记录」。

### 2.2 一条记录存什么？（第二章铁律②）

每条记录 = **三件套**，缺一不可：

```
┌──────────────────────────────────────────┐
│  Chunk 记录                                 │
├──────────────────────────────────────────┤
│  id        : 唯一标识  chunk-001            │
│  content   : 原文文本  "员工年假为10天"      │  ← 召回后要拿它喂给 LLM
│  vector    : float[]   [0.91,0.12,...]     │  ← 用来算相似度
│  metadata  : 元数据    {source:"手册.pdf",  │  ← 溯源/过滤：来自哪、第几页
│                         page:12}            │
└──────────────────────────────────────────┘
```

- **只存向量不存原文**：召回后只有一串数字，没法喂给 LLM——错误。
- **只存原文不存向量**：没法算相似度——错误。
- **不存元数据**：召回后无法告诉用户「答案出自手册第12页」，也无法按部门/时间过滤。

### 2.3 检索的两种实现：暴力 vs 近似

**① 暴力检索（Brute-force / Flat）** —— 本章内存版采用
```
把查询向量和库里【每一条】都算一次余弦相似度 → 排序 → 取前 K 个
```
- 优点：实现简单、结果 100% 精确。
- 缺点：O(N) 复杂度，N 大（百万级）会慢。
- **适用：教学、小数据量（几千~几万条）。**

**② 近似最近邻 ANN（HNSW / IVF 等）** —— 生产向量库采用
```
建索引（如分层图 HNSW），检索时只探查一小部分候选 → 近似 Top-K
```
- 优点：亚线性复杂度，百万/亿级也能毫秒响应。
- 缺点：牺牲少量精度、实现复杂。
- **适用：生产、大数据量。由 pgvector / Milvus / Faiss 等实现，我们不重复造轮子。**

### 2.4 常见向量库选型

| 方案 | 定位 | 适用 |
|------|------|------|
| **内存版（本章手写）** | 学习、原型 | 数据量小、重启可丢 |
| **pgvector** | PostgreSQL 扩展 | 已有 PG、想复用事务/SQL、中小规模 |
| **Milvus / Qdrant / Weaviate** | 专业向量数据库 | 大规模、高并发、生产首选 |
| **Redis / ES 向量能力** | 已有基础设施顺带用 | 已在用这些中间件 |

**本项目策略**：先手写内存版把原理讲透，并**面向接口设计**，后续换 pgvector 只需实现同一个接口，上层不用改。

### 2.5 面向接口设计（企业分层关键）

```
        VectorStore（接口）
        ├─ save(Chunk)          存
        ├─ search(vec, topK)    查
        └─ deleteById(id)       删
               ▲
   ┌───────────┴────────────┐
InMemoryVectorStore   PgVectorStore(未来)
（本章实现）           （第五章升级方向）
```

上层（检索器、Service）只依赖 `VectorStore` 接口，不关心底层是内存是 PG。**这就是「依赖倒置」在 RAG 里的落地**，也是本项目能平滑升级的关键。

## 三、怎么用（实战：Chunk 实体 + VectorStore 接口 + 内存实现）

本章产出三个代码文件：
1. `entity/Chunk.java`：一条记录的三件套载体（id/content/vector/metadata）。
2. `vectorstore/VectorStore.java`：向量库能力接口（save/search/deleteById）。
3. `vectorstore/InMemoryVectorStore.java`：基于 `List` + 暴力检索的内存实现，用第三章的 `VectorMath.cosineSimilarity` 算相似度。

### 3.1 检索核心逻辑（暴力 Top-K）

```
输入：查询向量 queryVec，topK
for 每个 chunk in 库:
    score = cosineSimilarity(queryVec, chunk.vector)
    记录 (chunk, score)
按 score 降序排序
返回前 topK 个
```

代码里用 `Stream + sorted + limit` 实现，简洁且易读。（见下方三个 `.java` 文件，已生成到对应目录。）

### 3.2 Python 对照（帮助理解，不在本项目运行）

```python
def search(query_vec, chunks, top_k=3):
    scored = [(c, cosine(query_vec, c.vector)) for c in chunks]
    scored.sort(key=lambda x: x[1], reverse=True)
    return scored[:top_k]
```

Java 与 Python 逻辑一致：算分 → 排序 → 取前 K。生产向量库把这步换成了 ANN 索引，但「按相似度取 Top-K」的语义不变。

### 3.3 为什么用 ConcurrentHashMap 存

内存版用 `ConcurrentHashMap<String, Chunk>`（id→chunk）而非 `List`：
- 按 id 增删改是 O(1)，方便 `deleteById`。
- 线程安全，多请求并发读写不出错。
- 检索时遍历 `values()` 做暴力打分。

## 四、用在哪（真实项目）

1. **企业知识库问答**：所有文档 chunk 的向量都存这里，问答时来这检索。
2. **语义搜索引擎**：商品/文章向量入库，搜索即向量检索。
3. **推荐/去重/聚类**：都依赖「按向量找最近邻」，底层都是向量库。
4. **多租户隔离**：用 metadata 存 tenantId，检索时按元数据过滤，实现一库多租户。

共同点：**凡是需要「按语义找最相似的若干条」，背后都有一个向量库。**

## 五、避坑与最佳实践

1. **只存向量不存原文** → 召回后无法喂 LLM。三件套必须齐全（铁律②）。
2. **不存元数据** → 无法溯源出处、无法按条件过滤。至少存 source/位置。
3. **内存版当生产用** → 重启数据丢失、数据量大检索慢。生产必须换持久化向量库。
4. **不同维度的向量混入同一库** → 相似度算不了或算错。入库前应校验维度一致（第三章 `checkSameDimension`）。
5. **topK 设太大** → 召回大量低相关内容，稀释 Prompt、增加成本。一般 3~5 起步。
6. **topK 设太小** → 漏掉关键片段，答不全。需结合 chunk 大小和问题复杂度调。
7. **不设相似度阈值** → 库里没有相关内容时，仍强行返回最不相关的 K 条，导致「一本正经地瞎编」。应设最低分阈值，低于阈值视为「没查到」。
8. **删除/更新后不重建** → 换 Embedding 模型或大量更新后，老向量残留，检索错乱。

**最佳实践**：面向接口设计，内存版验证原理、生产换 pgvector/Milvus；三件套 + 维度校验 + 相似度阈值；topK 3~5 起步按效果调；用 metadata 支持过滤与溯源。

## 六、面试问题与参考答案

**Q1：向量库一条记录要存哪些字段？为什么？**
A：三件套——向量（算相似度）、原文（召回后喂 LLM）、元数据（溯源与过滤）。缺向量算不了相似度，缺原文没法回答，缺元数据无法溯源/过滤。

**Q2：暴力检索和 ANN 有什么区别？各自适用场景？**
A：暴力检索把查询向量和每条都算相似度，O(N)、精确，适合小数据量/教学；ANN（如 HNSW）建索引只探查部分候选，亚线性、近似，牺牲少量精度换大规模高性能，适合生产。

**Q3：为什么要面向接口设计 VectorStore？**
A：底层实现（内存/pgvector/Milvus）会变，但「save/search/delete」能力稳定。面向接口 + 依赖倒置，上层只依赖接口，换实现无需改上层代码，可平滑从原型升级到生产。

**Q4：检索时为什么要设相似度阈值？**
A：不设阈值时，即使库里没有相关内容，也会强行返回最相似的 K 条（其实并不相关），LLM 拿到无关上下文容易胡编。设最低分阈值，低于阈值判定「没查到」，可回答「知识库中没有相关信息」，更安全可信。

## 本章小结

- VectorStore = 存向量并按相似度检索的「记忆中枢」，核心能力 save/search/delete。
