# 第七章：增强生成 —— 把召回片段拼进 Prompt，让 LLM 基于资料回答

> Day5 · 第七章学习笔记。第六章我们拿到了「相关片段」，本章解决最后一公里：**怎么把这些片段喂给大模型，让它「根据资料回答」而不是「凭记忆瞎编」**。这就是 RAG 里的 **A（Augmented Generation，增强生成）**。

---

## 一、为什么学（核心价值）

RAG 三个字母：**R**etrieval（检索，第六章）+ **A**ugmented（增强）+ **G**eneration（生成）。前面辛辛苦苦召回了片段，如果只是把问题原样丢给 LLM，那检索白做了——模型还是靠训练时的旧记忆答题，照样过时、照样瞎编。

**增强生成的本质**：把「召回的资料」和「用户问题」按一定格式拼成一段 Prompt，明确告诉 LLM：**「只准根据我给你的资料回答，资料里没有就说不知道」**。

一句话：**检索决定「找得到吗」，增强生成决定「答得对吗、答得可信吗」。** 这一步没做好，前面全白搭。

---

## 二、是什么（概念 + 底层原理）

### 2.1 一句话定义

> 增强生成 = 把「检索到的上下文(context)」注入到「提示词(Prompt)」中，约束 LLM 基于该上下文作答，并要求标注来源、拒绝编造。

### 2.2 在整个流程中的位置

```
用户问题
   │
   ▼  第六章 Retriever.retrieve()
召回片段 List<SearchResult>
   │
   ▼  ① PromptBuilder 组装
┌───────────────────────────────────────────┐
│  System: 你是企业知识库助手，只依据下方资料回答，  │
│          资料中没有就回答"未在资料中找到"。       │
│                                             │
│  【资料】                                     │
│  [1] 员工每年享有10天带薪年假 (来源:员工手册.pdf) │
│  [2] 试用期3个月，转正后年假增加 (来源:员工手册)  │
│                                             │
│  【问题】员工每年有几天年假？                    │
└───────────────────────────────────────────┘
   │
   ▼  ② LlmClient.chat(prompt)
LLM 生成答案："根据资料[1]，员工每年享有10天带薪年假。"
```

### 2.3 一个好的 RAG Prompt 有哪几块

1. **角色/指令(System)**：你是谁、任务是什么。
2. **约束(最关键)**：「只依据资料回答」「资料没有就说没有」「可标注引用编号」。这是**防幻觉的核心护栏**。
3. **上下文(Context)**：把召回片段编号列出，最好带来源，便于溯源。
4. **问题(Question)**：用户的原始问题。

**顺序与措辞会显著影响效果**——把约束写清楚，模型才不会「自作主张」。

### 2.4 为什么要抽 LlmClient 接口

跟 Embedding 一样的思路：调大模型有多种后端(OpenAI / 通义 / 本地 Ollama / 离线降级)。抽成 `LlmClient` 接口，上层(RAG 主流程)只依赖接口：

```
          LlmClient（接口）
          └─ String chat(String prompt)
                   ▲
   ┌───────────────┼────────────────┐
EchoLlmClient   OpenAiLlmClient   OllamaLlmClient
（离线降级/本章）  （云端/未来）      （本地/未来）
```

本章用 **离线降级实现 `EchoLlmClient`**：不真正调用大模型(演示环境可能无网/无 key)，而是把「拼好的 Prompt」按规则组织成一个可读答案，**证明「资料→Prompt→答案」链路能跑通**。真实智能靠换成云端/本地大模型——面向接口，主流程一行不改。

### 2.5 Context 太长怎么办：token 预算

召回片段数 × 每片长度不能无限大，受 LLM 上下文窗口(token 上限)约束。工程上要做 **token 预算控制**：按得分从高到低拼，拼到接近预算就停。本章用「最多拼 N 条 + 总字符上限」的简化版演示这个思想。

## 三、怎么用（实战：PromptBuilder + LlmClient + EchoLlmClient）

本章产出三个代码文件：
1. `prompt/PromptBuilder.java`：把 `List<SearchResult>` + 问题 → RAG Prompt 字符串。
2. `llm/LlmClient.java`：`chat(prompt)` 能力接口。
3. `llm/EchoLlmClient.java`：离线降级实现，示「基于资料回答」的形态。

### 3.1 PromptBuilder 核心逻辑

```
build(question, results):
    if results 为空:
        return 带"资料为空，请回答未找到"的 Prompt
    sb = System 指令 + 约束
    sb += "【资料】"
    for i, r in results:            // 按得分顺序编号列出
        sb += "[i+1] r.content (来源: r.metadata.source)"
    sb += "【问题】" + question
    return sb
```

要点：**编号 + 来源**，既方便 LLM 引用，也方便用户溯源。

### 3.2 防幻觉约束怎么写

关键几句(写进 System)：
- 「你只能依据【资料】中的内容回答。」
-「若资料中没有相关信息，请直接回答：未在资料中找到相关信息。」
- 「回答时可用 [编号] 标注引用的资料。」

这三句是 RAG 可信度的护栏，缺了模型就会「自由发挥」。

### 3.3 Python 对照（帮助理解，不在本项目运行）

```python
def build_prompt(question, results):
    if not results:
        context = "（无相关资料）"
    else:
        context = "\n".join(
            f"[{i+1}] {r.content}（来源:{r.source}）"
            for i, r in enumerate(results))
    return f"""你是企业知识库助手，只依据下方资料回答，资料没有就说未找到。
【资料】
{context}
【问题】{question}"""

answer = llm.chat(build_prompt(question, results))
```

Java 与 Python 完全同构。Spring AI 里对应 `PromptTemplate` + `ChatClient.prompt().user(...).call()`，本质一样：把 context 填进模板，交给 ChatModel。

## 四、用在哪（真实项目）

1. **企业知识库问答**：本训练营主线，客服/HR/IT 助手的「回答」环节。
2. **文档摘要/报告生成**：召回相关段落 → 让 LLM 归纳成摘要。
3. **代码助手**：召回相关代码片段/文档 → 让 LLM 基于真实 API 生成代码，减少「幻觉 API」。
4. **合规/法务问答**：必须「基于条款回答并标注出处」，增强生成的约束与引用能力是刚需。

共同点：**凡是「让大模型基于给定资料、可溯源地回答」，都是增强生成在起作用。**

## 五、避坑与最佳实践

1. **不写约束，直接把资料丢进去** → 模型仍可能混用自身记忆瞎编。必须明确「只依据资料 + 没有就说没有」。
2. **不标编号/来源** → 无法溯源、无法让用户核实，可信度打折。
3. **Context 无限拼** → 超 token 上限报错或被截断。要做 token/条数预算，按得分优先拼。
4. **召回为空却硬让模型答** → 应在 Prompt 里明确「资料为空时回答未找到」，或干脆不调 LLM 直接返回兜底话术。
5. **把用户问题和资料混在一起分不清** → 用清晰分隔(【资料】【问题】)，避免模型混淆指令与数据(也降低 Prompt 注入风险)。
6. **温度(temperature)过高** → 生成发散、更易编造。知识问答建议低温度、更确定。
7. **忽视 Prompt 注** → 用户问题里可能藏「忽略以上指令」等攻击语句。要对用户输入做隔离/转义，System 指令优先级最高。
8. **一次拼太多低相关片段** → 稀释重点、误导模型。宁精勿滥，配合第六章阈值。

**最佳实践**：结构化 Prompt(指令/约束/资料/问题四段) + 编号溯源 + token 预算 + 低温度 + 输入隔离防注入 + 召回为空兜底。

## 六、面试问题与参考答案

**Q1：RAG 里的「增强生成」具体做了什么？**
A：把检索到的相关片段作为上下文注入 Prompt，并加约束指令让 LLM「只依据这些资料回答、没有就说没有、可标注来源」，从而让模型基于最新且可溯源的资料作答，而非依赖训练记忆。

**Q2：怎么降低 RAG 回答的幻觉？**
A：多层护栏——检索端设相似度阈值(第六章)过滤不相关；生成端在 Prompt 明确「只依据资料、无则回答未找到」；标注引用来源便于核实；降低温度；召回为空时走兜底话术不硬答。

**Q3：Context 太长放不下怎么办？**
A：做 token 预算——按相似度得分从高到低拼片段，累计接近上下文窗口上限就停；也可对片段先做压缩/摘要，或减小 chunk、调低 topK。

**Q4：为什么把 LLM 调用抽成 LlmClient 接口？**
A：解耦后端(云端/本地/离线)。上层 RAG 主流程只依赖接口，切换或降级实现时不用改业务代码；也便于测试(可注入假的 LlmClient)。

## 本章小结

- 增强生成 = 把召回片段注入 Prompt + 约束 LLM「只依据资料、可溯源、不编造」。
- 好 Prompt 四段：角色指令 / 约束(护栏) / 资料(编号+来源) / 问题。
- 面向接口：LlmClient 可从离线 Echo 平滑换成云端/本地大模型。
- 护栏组合：阈值过滤 + 约束指令 + 溯源 + token 预算 + 低温度 + 防注入 + 空召回兜底。
- 本章产出代码：`prompt/PromptBuilder.java`、`llm/LlmClient.java`、`llm/EchoLlmClient.java`。
