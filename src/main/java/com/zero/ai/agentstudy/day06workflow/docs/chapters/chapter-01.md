# 第一章：为什么需要 Workflow？

> 本章不写代码，先建立「思想」。Workflow 是 Agent 从「会说话」走向「能干活」的分水岭。

---

## 第一部分：为什么学（核心价值）

### 1. Workflow 解决了什么问题？

Day1~Day5 我们的 Agent 只会「单步反应」：一问一答、调一个工具。
但真实任务是**多步、有依赖、有分支、会失败**的。Workflow 解决的核心问题是：
**把一个复杂任务，拆解成可编排、可执行、可观测、可恢复的步骤图，并由引擎自动驱动执行。**

### 2. 没有 Workflow 会怎样？

你会写出「巨型方法」——一个 `service` 方法里塞满了：
调 LLM、if 判断、调工具、再 if、再调 LLM、try/catch……
后果是：
- 步骤耦合，改一步牵动全身；
- 无法单独测试某一步；
- 失败了不知道死在哪一步，也无法从中间恢复；
- 想加一步要改核心代码、重新发布；
- 产品经理想调整流程顺序，只能提需求排期。

### 3. 为什么简单的 Tool Calling 不足以构建复杂 Agent？

Function Calling 解决的是「**要不要调、调哪个工具**」，它是**单步决策**。
但它不负责：
- 多个工具之间的**顺序与依赖**（先查天气才能定方案）；
- **分支**（下雨走 A 方案，晴天走 B 方案）；
- **失败重试 / 超时 / 降级**；
- **状态在多步之间的传递与持久化**；
- **执行过程的可观测与可恢复**。

这些都是 Workflow 的职责。**Tool Calling 是「一只手」，Workflow 是「指挥这只手做完整件事的大脑」。**

### 4. 企业为什么需要 Workflow？

- **可维护**：业务方只写 Node，平台方维护引擎，各自演进。
- **可配置**：流程外置到 DB/JSON，改流程不改代码、不发版。
- **可观测**：每步 I/O 入日志，线上问题定位到具体节点。
- **可容错**：重试/超时/降级统一治理。
- **可恢复**：宕机后从上次成功节点续跑。
- **可协作**：产品拖拽编排、开发写节点、运维看日志，分工清晰。

### 5. 哪些真实产品在使用 Workflow？

- **Dify / Coze / n8n**：可视化拖拽式 Workflow 编排平台。
- **LangGraph（LangChain）**：以「图 + 状态」组织 Agent 执行。
- **Spring AI Advisor 链 / Chain**：把处理环节串成链。
- **Temporal / Airflow / Camunda**：企业级工作流 / 编排引擎。
- 各大厂内部的**AI 审批流、AI 客服路由、AI 数据管道**。

### 6. Workflow 与 Java 设计模式的联系

Workflow 的实现几乎是 GoF 设计模式的「集大成者」：
- 责任链（Node 串联处理）
- 状态模式（状态自动流转）
- 策略模式（同一步可插拔实现）
- 命令模式（把操作封装成对象，可记录/撤销）
- Pipeline（数据逐级加工）

## 第二部分：是什么（先建立直觉）

用一句话概括：

> **Workflow = 一张有向图（Nodes + Edges）+ 一个共享状态（Context）+ 一个执行引擎（Engine）。**

一个「旅行规划」任务的 Workflow 直觉图：

```
[输入城市] → [查天气] → [查酒店] → [生成计划] → [输出行程]
                            │
                    天气=雨 ─┘（条件分支：走室内方案）
```

- 每个方块是一个 **Node**（只做一件事）；
- 箭头是 **Edge**（决定下一步去哪）；
- 一路传递的城市、天气、酒店数据装在 **Context** 里；
- 谁来按箭头一步步推动？是 **Engine**。

## 第四部分：用在哪（真实项目）

| 场景 | 单步 Tool Calling 够吗 | Workflow 的作用 |
|------|------------------------|-----------------|
| AI 客服 | 不够 | 意图识别→查单→查库→是否转人工（条件+HITL） |
| AI 审批 | 不够 | 提单→校验→多级审批→通知（状态机） |
| AI 数据分析 | 不够 | 取数→清洗→计算→出图→写报告（管道+并行） |
| AI 量化 | 不够 | 行情→策略→风控→下单→记录（重试+风控节点） |

**规律：只要任务超过一步、有依赖或分支，就该上 Workflow。**

## 第五部分：避坑与优化（本章相关）

1. **不要写巨型 service 方法**——那是「伪 Workflow」，无法测试和恢复。
2. **不要把状态藏在成员变量**——状态必须显式放进 Context，才能持久化/恢复。
3. **不要让业务代码里到处 try/catch 重试**——重试是横切关注点，交给引擎。
4. **不要一开始就上重型引擎**（Temporal 等）——先理解本质，再按需引入。
5. **Node 要单一职责**——一个 Node 只做一件事，否则又变回巨型方法。

## 本章总结

- Workflow 让 Agent 从「单步反应」升级为「多步执行」。
- 它 = 图（Node+Edge）+ 状态（Context）+ 引擎（Engine）。
- Tool Calling 是单步的手，Workflow 是编排全局的大脑。
- 企业需要它的可维护、可配置、可观测、可容错、可恢复。

---

## 核心概念

| 概念 | 一句话 |
|------|--------|
| Workflow | 描述「一件事怎么一步步做完」的执行图 |
| Node | 只做一件事的最小执行单元 |
| Edge | 决定下一步去哪的连接（可带条件） |
| Context | 贯穿全程的共享数据/状态袋 |
| Engine | 按 Edge 驱动 Node、管日志/重试/超时的调度器 |

---

## 常见错误

- 把 Workflow 理解成「就是 if/else 换个说法」——忽略了状态显式化、可持久化、可观测。
- 认为有了 Function Calling 就不需要 Workflow——混淆了「单步决策」和「多步编排」。

## 本章练习答案

**问：Workflow 和普通 Java 业务流程最大的区别是什么？**

**答（参考）：** 普通 Java 业务流程是「写死在代码里的控制流」——步骤耦合、状态藏在局部变量、失败靠 try/catch 局部处理、改流程要改代码重新发布。
而 Workflow 是「可编排、可持久化、可观测的执行图」——步骤是独立可插拔的 Node、状态显式放在 Context 中（可持久化、可断点恢复）、失败/超时/重试由引擎统一治理、流程可配置化甚至可视化编排，修改流程无需改核心代码。
**一句话：普通流程是「代码控制流」，Workflow 是「数据驱动、可观测、可恢复的执行图」。**
