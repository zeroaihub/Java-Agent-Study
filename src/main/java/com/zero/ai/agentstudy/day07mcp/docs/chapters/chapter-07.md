# 第七章 企业最佳实践：把「能跑的 Demo」打磨成「敢上线的系统」

> 本章是「实践复盘 + 生产清单」章节，不新增业务代码，而是回看前六章的实现，
> 指出哪些地方在企业环境下需要加固，并给出可落地的改造方向与取舍。

---

## 一、为什么要学（Why）

前六章我们从零手写了一套 MCP：协议报文（第二章）、传输层（第三章）、客户端（第四章）、工具服务端（第五章）、工作流编排（第六章）。这套代码**逻辑完整、能跑通闭环**，非常适合学习原理。但它是「教学实现」——为了让你看清本质，我们刻意省去了很多生产环境必备的加固。

如果直接把它搬上线，你会在半夜被以下问题叫醒：

- 某个工具卡住了，整个请求线程被无限期挂起（没有超时）；
- 网络抖动导致一次调用失败，本可重试却直接报错给用户（没有重试）；
- 一个畸形请求打进来，栈信息直接暴露给前端（异常没治理）；
- 线上出问题，日志里只有一句「调用失败」，无法定位是哪一步、哪个请求（可观测性差）；
- 协议版本、超时时间硬编码在代码里，改一次要重新发版（配置没外置）。

**企业级和 Demo 级的差距，几乎全在「非功能性需求」上。** 本章就是把这些「看不见但要命」的点逐一补齐的清单。

---

## 二、是什么（What）——生产级 MCP 的六大支柱

| 支柱 | Demo 现状 | 企业要求 |
| --- | --- | --- |
| 超时控制 | `transport.send` 同步阻塞、无超时 | 每次调用有超时上限，超时即快速失败 |
| 重试与幂等 | 失败直接抛异常 | 可重试错误自动重试 + 退避；保证幂等 |
| 连接与资源管理 | 进程内传输、无连接概念 | 远程传输需连接池、心跳、优雅关闭 |
| 异常治理 | 异常信息可能直达前端 | 分层异常 + 统一错误码 + 不泄露内部细节 |
| 可观测性 | 只有零散 `log.info` | 结构化日志 + traceId 全链路 + 指标 + 调用链 |
| 配置化 | 协议版本/超时等硬编码 | 外置到配置中心，可动态调整 |

下面逐一展开，并对照我们现有代码指出「该改哪里」。

## 三、怎么用（How）——逐项加固方案

### 3.1 超时控制：不让任何一次调用无限期挂起

**现状**：`McpClient.callTool` → `transport.send(req)` 是同步阻塞。进程内传输没问题，但换成 stdio/HTTP 传输时，对端卡住会让调用线程永久挂起。

**改造方向**：
- 传输层引入超时。若是 HTTP，用 `HttpClient` 的 `connectTimeout` + `requestTimeout`；若是 stdio，用带超时的 `Future.get(timeout)`。
- 超时应**分级**：连接超时（建连）、读超时（等响应）分开配置。
- 超时后要**快速失败并释放资源**，而不是让线程堆积。

```java
// 伪代码：给 callTool 包一层超时
CallToolResult result = CompletableFuture
        .supplyAsync(() -> doCall(toolName, args), toolExecutor)
        .orTimeout(timeoutMs, TimeUnit.MILLISECONDS)
        .exceptionally(ex -> CallToolResult.fail("调用超时或异常: " + ex.getMessage()))
        .join();
```

要点：超时时间应做成**每工具可配**——查天气可以给 2s，跑大模型的工具可能要 30s。

### 3.2 重试与幂等：把「偶发抖动」自动抹平

**现状**：`checkError` 一旦发现协议级错误就 `throw`，没有重试。

**改造方向**：
- **区分可重试与不可重试错误**：网络超时、连接重置、`-32000` 服务端临时错误 → 可重试；参数错误 `-32602`、方法不存在 `-32601` → 不可重试（重试也白搭）。
- **指数退避 + 抖动（jitter）**：`100ms → 200ms → 400ms`，加随机抖动避免「重试风暴」。
- **限制重试次数**（如 3 次），并对整体调用设「重试总预算」，防止叠加超时把上游拖垮。
- **幂等前提**：只有幂等操作才能安全重试。查询类（`get_weather`、`get_current_time`）天然幂等；写操作要靠「幂等键」保证重试不产生副作用。

> 呼应第五章：**业务失败（`isError`）不该重试**——城市不存在你重试一百次还是不存在。只有「基础设施抖动」才重试。

### 3.3 连接与资源管理：远程传输的必修课

**现状**：`InProcessTransport` 是进程内直连，没有连接、没有资源需要释放。

**改造方向（当迁移到远程 Server 时）**：
- **连接池**：复用 TCP/HTTP 连接，避免每次调用重新建连的开销。
- **心跳/保活**：长连接要定期 ping，及时发现半死连接。
- **优雅关闭**：应用下线时 `@PreDestroy` 里发关闭通知、排空在途请求、关闭连接池。
- **背压**：并发过高时限流，而不是把请求全压给 Server 导致雪崩。

### 3.4 异常治理：分层 + 统一错误码 + 不泄露

**现状**：`McpClient` 抛 `IllegalStateException`，`McpAgentService.chat` 用 `catch (Exception)` 兜底返回 `处理异常: + e.getMessage()`——**这会把内部异常信息直接暴露给用户**。

**改造方向**：
- **自定义异常分层**：`McpProtocolException`（协议级）、`McpTransportException`（传输级）、`McpBusinessException`（业务级），各自携带错误码。
- **统一异常处理器**：Spring 里用 `@RestControllerAdvice` + `@ExceptionHandler` 集中处理，对外只返回「稳定错误码 + 友好文案」，把堆栈只写进日志。
- **对外不泄露内部细节**：`e.getMessage()` 可能含内网地址、SQL 片段等，绝不能直接返回给前端。

```java
@RestControllerAdvice
public class McpExceptionHandler {
    @ExceptionHandler(McpProtocolException.class)
    public ResponseEntity<ErrorResp> handle(McpProtocolException e) {
        log.error("协议异常", e);                       // 细节进日志
        return ResponseEntity.status(502)
                .body(new ErrorResp("MCP_PROTOCOL_ERROR", "服务暂时不可用，请稍后再试")); // 对外友好
    }
}
```

### 3.5 可观测性：出事时能「看得见、查得到」

**现状**：全靠零散 `log.info`，没有 traceId，多个请求的日志交织在一起无法区分。

**改造方向**：
- **traceId 全链路**：入口生成 traceId（或从上游透传），放进 MDC，让一次请求的所有日志都带同一个 id。第六章的 `WorkflowResult.executedNodes` 就是「调用链」的雏形，生产环境要把它升级成带 traceId、耗时、每节点入出参的结构化链路。
- **结构化日志**：用 JSON 格式日志，便于 ELK/Loki 检索。关键字段：traceId、tool、耗时、成功与否、错误码。
- **指标（Metrics）**：每个工具的 QPS、P99 耗时、错误率、超时率，暴露给 Prometheus，配告警。
- **调用链追踪**：接入 OpenTelemetry，把「Agent → McpClient → Transport → Server → Tool」串成一条可视化 span。

### 3.6 配置化：让参数「可调而不必发版」

**现状**：`PROTOCOL_VERSION = "2024-11-05"`、超时、重试次数等都硬编码在代码里。

**改造方向**：
- 抽到 `application.yml` 或配置中心：

```yaml
mcp:
  protocol-version: "2024-11-05"
  client-info:
    name: agentstudy-mcp-client
    version: 1.0.0
  timeout:
    connect-ms: 1000
    call-default-ms: 5000
  retry:
    max-attempts: 3
    backoff-base-ms: 100
  tools:
    get_weather: { timeout-ms: 2000 }
    slow_llm_tool: { timeout-ms: 30000 }
```

- 用 `@ConfigurationProperties` 绑定成强类型配置类，配合配置中心实现**动态刷新**（改超时无需重启）。

## 四、用在哪（Where）

| 场景 | 最该优先补齐的支柱 |
| --- | --- |
| 对外 C 端高并发 | 超时 + 限流 + 可观测性（P99/错误率告警） |
| 内部工具集成 | 异常治理 + 配置化（工具多、变更频繁） |
| 跨网络远程 MCP Server | 连接池 + 重试 + 心跳 |
| 金融/交易类写操作 | 幂等 + 审计日志（调用链持久化） |

**优先级建议**：任何要上线的系统，**先补超时和异常治理**（否则一个卡顿或畸形请求就能拖垮服务），再补可观测性（否则出事无法定位），最后按流量与业务性质补重试、连接池、限流。

## 五、避坑与优化

| 坑 | 后果 | 正确做法 |
| --- | --- | --- |
| 无超时的同步调用 | 单点卡顿引发线程耗尽、雪崩 | 每次调用设超时，超时快速失败 |
| 对业务失败也重试 | 无谓放大请求量、掩盖真实问题 | 只重试基础设施类可恢复错误 |
| 对非幂等操作重试 | 重复扣款/重复下单 | 幂等键保证，或干脆不重试写操作 |
| `e.getMessage()` 直接返回前端 | 泄露内网/实现细节，安全风险 | 统一异常处理器，对外只给错误码+文案 |
| 日志无 traceId | 线上无法定位单次请求 | MDC 注入 traceId，全链路透传 |
| 参数硬编码 | 调个超时都要发版 | 外置配置 + 动态刷新 |
| 一把 `catch (Exception)` 吞掉一切 | 掩盖真实错误、难排查 | 分层捕获，该抛的抛、该记的记 |

## 六、核心知识速记

- 企业级 vs Demo 的差距**主要在非功能性需求**：超时、重试、资源、异常、观测、配置。
- **超时**：每次调用有上限，分级（连接/读），可按工具配置。
- **重试**：只重试可恢复错误 + 指数退避 + 幂等前提。
- **异常治理**：分层异常 + 统一错误码 + 对外不泄露内部细节。
- **可观测性**：traceId 全链路 + 结构化日志 + 指标 + 调用链。
- **配置化**：参数外置到配置中心，动态可调不发版。
- 上线优先级：**先超时+异常治理 → 再可观测性 → 后重试/连接池/限流**。

## 七、常见面试题

**Q1：MCP 客户端调用工具时，如何防止一次卡顿拖垮整个服务？**
A：给每次调用加超时（连接超时 + 读超时，可按工具粒度配置），超时立即失败并释放线程/连接；配合线程池隔离与限流，避免慢调用堆积导致线程耗尽和雪崩。

**Q2：哪些错误可以重试，哪些不能？为什么？**
A：可重试——网络超时、连接重置、服务端临时错误（如 `-32000`），这类是「偶发、可自愈」的；不可重试——参数错误（`-32602`）、方法不存在（`-32601`）、业务失败（`isError`），重试结果不变还放大压力。且只有幂等操作才能安全重试。

**Q3：为什么不能把 `e.getMessage()` 直接返回给前端？**
A：内部异常信息可能包含内网地址、堆栈、SQL 片段、依赖细节，泄露给外部有安全风险，也会让攻击者摸清系统结构。正确做法是把细节写进日志，对外只返回稳定错误码 + 友好文案。

**Q4：线上一次请求出错，你怎么快速定位到是哪一步、哪个工具？**
A：靠 traceId 全链路——入口生成/透传 traceId 放进 MDC，所有日志带同一 id；结合结构化日志与调用链（如第六章的 executedNodes 升级版 / OpenTelemetry span），按 traceId 一键串出整条链路及每步耗时与错误。

**Q5：协议版本、超时这些为什么要外置配置而不是写死？**
A：写死意味着改一个参数就要改代码、重新测试、重新发版，响应慢且风险高。外置到配置中心并用 `@ConfigurationProperties` 绑定，可实现动态刷新——调超时、切协议版本、灰度不同工具超时都无需重启。

## 八、本章练习答案

**练习1：给 `McpClient.callTool` 增加「超时 + 一次重试」需要改动哪些地方？**
答：①在传输层或 `callTool` 外层包超时（`orTimeout` 或带超时的 `Future.get`）；②在 `checkError` 前判断错误是否可重试，可重试则退避后再发一次；③超时/重试次数从配置读取；④重试仅对幂等的查询类工具开启。核心是**不改协议报文格式**，只在调用编排层加固。

**练习2：如何为整个 Day07 加上 traceId 全链路日志？**
答：在 `McpAgentController`/`WorkflowController` 入口生成 traceId 写入 MDC（`MDC.put("traceId", ...)`），在日志格式里加 `%X{traceId}`，请求结束在 finally 里 `MDC.clear()`。若跨线程（如第七章 3.1 的 `CompletableFuture`）需手动把 MDC 传递到子线程。

**练习3：`McpAgentService.chat` 目前用一把 `catch (Exception)` 兜底并返回 `e.getMessage()`，如何改造成企业级？**
答：①定义分层异常（协议/传输/业务）；②在 Controller 层用 `@RestControllerAdvice` 统一处理，按异常类型映射错误码与友好文案；③堆栈只 `log.error` 进日志，对外不返回原始 message；④`chat` 里区分「可预期的业务失败」（正常返回，success=false）与「意外异常」（抛出交给全局处理器），不再一把吞掉。
