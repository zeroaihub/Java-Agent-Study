## 第一部分：为什么学（核心价值）

### 1.1 为什么单 Agent 不能解决所有问题？

先看一个真实的“翻车现场”。你让一个单 Agent：**“帮我写一篇 AI 工具推荐文章。”**

这个单 Agent 的 System Prompt 会被塞成这样：

> “你是一个全能助手。你要先规划文章结构，然后搜集每个工具的资料，然后写出流畅的正文，然后检查语法、事实、逻辑，还要保证 SEO，最后排版成 Markdown……”

结果通常是：
- **规划潦草**：因为它急着写正文，大纲一带而过。
- **素材虚构**：它没有“研究”这个独立步骤，写到哪编到哪，出现幻觉。
- **无人复核**：它自己写、自己交，没有第二双眼睛发现错误。
- **改一处、乱全局**：你说“审校标准再严一点”，它连带把写作风格也改了。

这不是“模型不够聪明”，而是 **“一个人同时扮演四个专家”这件事本身就不合理**。就像你不会让同一个人既当运动员又当裁判，既写代码又审自己的代码。

### 1.2 为什么需要角色分工？

人类社会解决复杂问题的方式从来不是“找一个全能超人”，而是**分工协作**：报社里有选题编辑、记者、撰稿人、校对；软件公司里有产品、架构、开发、测试。

分工带来三个不可替代的价值：
1. **专注 → 专业**：每个角色的“脑子”只装一件事，Prompt 短、注意力集中，质量更高。
2. **解耦 → 可维护**：改校对规则不影响记者写稿，符合单一职责原则。
3. **制衡 → 可校验**：校对与撰稿分离，形成“生成—审查”的对抗结构，错误更容易被发现。

Multi-Agent 就是把这套“人类组织智慧”搬进 AI 系统。

### 1.3 为什么 AI 团队比 AI 个人更强？

因为复杂任务的质量瓶颈，往往不在“单点能力”，而在**流程、校验和专注度**：
- 单 Agent 的能力上限 ≈ 一个模型在“分心状态”下的平均水平。
- 多 Agent 的能力上限 ≈ 多个模型在“各自专注状态”下的水平之和，再叠加“互相校验”带来的纠错增益。

用一句话说：**AI 个人拼的是“智商”，AI 团队拼的是“组织”。** 而工程世界里，好的组织往往比个别天才更可靠。

### 1.4 哪些真实产品已经用了 Multi-Agent？

- **MetaGPT**：模拟一家软件公司，产品经理 → 架构师 → 工程师 → 测试，各是一个 Agent。
- **AutoGen（微软）**：多个 Agent 在“群聊”里协作，一个 Manager 决定谁发言。
- **Devin / 各类 AI 编程助手**：规划、检索、编码、运行测试往往由不同角色/子流程承担。
- **企业 AI 客服**：意图识别、知识检索、话术生成、情绪安抚常拆成多个 Agent。

### 1.5 Multi-Agent 解决了哪些工程问题？

| 工程问题 | 单 Agent | Multi-Agent |
|---------|---------|-------------|
| Prompt 过长、注意力稀释 | 严重 | 每个 Agent Prompt 短而专注 |
| 职责耦合、难维护 | 牵一发动全身 | 改一个 Agent 不影响其他 |
| 缺乏校验、易幻觉 | 自产自销 | Reviewer 独立把关 |
| 无法并行 | 串行独木桥 | 天然可并行扩展 |
| 无法复用 | 一次性脚本 | Agent 是可复用能力单元 |

## 第二部分：是什么（概念）

**Multi-Agent System（多智能体系统）**：由多个具备自主决策能力的 Agent，通过通信与协作，共同完成单个 Agent 难以高质量完成的任务的系统。

本章先建立三个最小概念（详细底层原理放到第二章）：

- **Agent（智能体）**：拥有一个明确角色（role）、能接收输入、独立思考/行动、产出结果的单元。在本项目里，它是一个实现了 `Agent` 接口的 Java 类。
- **Role（角色分工）**：Planner（规划）、Research（调研）、Writer（写作）、Reviewer（审校）。角色决定了它的 System Prompt 和职责边界。
- **Collaboration（协作）**：Agent 之间通过“共享记忆（黑板）”交换中间结果，由一个 Coordinator 决定谁先干、谁后干。

一句话记忆：**Agent = 角色 + 能力 + 上下文；Multi-Agent = 一群 Agent + 一套协作规则。**

## 第四部分：用在哪（真实项目）

本章只点题，详细案例见 README 第 8 节。请记住这条**判断法则**：

> 一个任务是否值得上 Multi-Agent，看它是否同时满足：**链路长 + 需要多种专业能力 + 需要独立质检/风控 + 可并行**。

- 满足越多，越该用 Multi-Agent（如 AI 法务、AI 医生、AI 研发、AI 内容生产）。
- 只是“一问一答”的简单任务（如翻译一句话），单 Agent 足够，硬上多 Agent 反而增加成本和延迟——**这也是避坑重点**。

---

## 第五部分：避坑与优化（企业最佳实践预告）

第一章先埋下三个最关键的“坑”，第七章会系统展开：

1. **不要为了多而多**：Agent 越多，Token 成本、延迟、调试难度都上升。只在真正要分工时才拆分。
2. **必须防死循环**：Reviewer 打回、Writer 重写，可能无限互踢。工程上必须设 `maxRounds` 上限并有降级出口。
3. **必须可观测**：多 Agent 是“黑盒”，一旦出错很难定位。从第一行代码起就要记 `AgentExecutionLog`，这是本项目的硬性要求。

## 本章总结

- 单 Agent 的天花板不在智商，而在“一个人扛所有职责”不可持续。
- Multi-Agent 用“角色分工 + 协作规则”换取专业性、可维护性、可校验性、可扩展性。
- 判断是否该用：链路长 + 多专业 + 需质检 + 可并行。
- 三大红线：别为多而多、防死循环、要可观测。

// 仅示意：帮助你在读完本章后建立“Agent = 角色 +行”的直觉

## Python 参考（CrewAI 风格，帮助跨语言理解）

```python
# CrewAI：用角色定义 Agent，用 Task 定义任务，用 Crew 编排
from crewai import Agent, Task, Crew, Process

planner  = Agent(role="规划师", goal="产出文章大纲", backstory="资深内容策划")
writer   = Agent(role="撰稿人", goal="根据大纲写正文", backstory="专栏作家")
reviewer = Agent(role="审校员", goal="审校并打分",   backstory="严格的主编")

crew = Crew(agents=[planner, writer, reviewer], process=Process.sequential)
result = crew.kickoff(inputs={"topic": "AI 工具推荐"})
```

> 对比即懂：CrewAI 的 `Crew + Process.sequential` ≈ 我们要手写的 `Coordinator` 顺序编排；`role/goal/backstory` ≈ 我们的 `AgentRole` + System Prompt。

## 常见问题（FAQ）

- **Q：多 Agent 是不是就是多次调用大模型？**
  A：形式上是，但本质区别在于“每次调用有明确角色、且结果被结构化地传递与校验”，而不是简单的多轮对话。
- **Q：会不会更慢更贵？**
  A：会。所以要按需拆分，简单任务别硬上；复杂任务用质量提升和可维护性来换成本。
- **Q：Agent 之间怎么传数据？**
  A：本项目用“共享记忆（黑板）”，解耦、可追溯，详见第五章。
