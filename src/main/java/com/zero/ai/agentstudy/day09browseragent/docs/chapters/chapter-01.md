# 第 1 章 · 为什么要学 Browser Agent

> 本章目标：让你从"知道有这个东西"变成"发自内心地想学它"。我们不写一行代码，只把一个问题讲透——为什么一个已经会调大模型、会 RAG、会 Workflow 的 Agent，还非得学会操作浏览器不可？

---

## 一、为什么学（Why）

### 1.1 一个真实的周一早晨

想象你是某电商公司的技术负责人。周一早上，运营主管找到你：

> "我们每天要登录 5 个供应商的后台，把昨天的库存和价格导出来，汇总成一张表发给采购。3 个人，每天花 2 小时干这事，纯手工复制粘贴。这些供应商系统都没有 API，能不能自动化？"

你心里盘算了一下现有的技术武器：

- **爬虫？** 这些系统要登录，有验证码，页面还是 JS 动态渲染的，传统 HttpClient 抓不到；
- **申请 API？** 供应商说"我们没有开放 API，要对接得走商务，最快三个月"；
- **RPA 工具？** 买一套 UiPath 授权一年几十万，而且规则一变就得重新配置；
- **让大模型帮忙？** 大模型只会"说"，它读不到那个需要登录才能看的页面。

**这就是 Browser Agent 要解决的问题**：让 AI 像人一样，打开浏览器、登录、点击、翻页、把数据读出来——**凡是人能在浏览器里做的，Agent 都能做，而且 7×24 小时不知疲倦。**

### 1.2 Agent 进化的必然一步

回顾我们这门课走过的路：

| 阶段 | Agent 的能力 | 局限 |
| --- | --- | --- |
| Day02 大模型 API | 会"思考""对话" | 只能基于训练数据回答 |
| Day05 RAG | 会查"我们自己的知识库" | 只能读预先入库的文档 |
| Day06 Workflow | 会"按流程编排任务" | 每一步还是文本处理 |
| Day07/08 Tool Calling | 会"调用我们写好的函数" | 工具得我们一个个开发 |
| **Day09 Browser** | **会"操作任意网站"** | **打开了通向整个 Web 的大门** |

前面几天，Agent 的能力边界是"我们喂给它什么，它才能用什么"。而浏览器不一样——**整个互联网都是它的数据源和操作对象**。这是 Agent 从"封闭系统内的助手"迈向"能与真实世界交互的智能体"的关键一跃。

### 1.3 学会它，你能做什么

- **自动化数据采集**：无 API 系统的数据抓取、竞品价格监控、舆情收集；
- **自动化操作**：自动填表、批量下单、后台报表导出、定时签到；
- **智能测试**：让 AI 自己走一遍业务流程做回归测试，还能描述哪里出了问题；
- **AI 助理的"手"**：给你的对话式 AI 接上浏览器，它就能真正"帮你办事"，而不只是"告诉你怎么办"。

这些都是当下企业里**真金白银的需求**，也是 AI Agent 商业化落地最扎实的场景之一。

## 二、是什么（What）

### 2.1 一句话定义

> **Browser Agent = 大模型（决策大脑）+ 浏览器自动化能力（执行手脚）+ 循环编排（自主完成多步任务）。**

它不是简单的"脚本自动化"，关键区别在于**决策由大模型动态做出**：

- 传统脚本：你写死"第一步点这里，第二步填那里"，页面一变就崩；
- Browser Agent：你说"帮我登录后查一下最新订单"，**大模型自己判断**要先打开、再登录、再读取，遇到情况还能调整。

### 2.2 三个组成部分

```
        ┌─────────────────────────────────────┐
        │  大脑：大模型（LLM）                  │
        │  理解意图、规划步骤、决定调用哪个工具 │
        └───────────────┬─────────────────────┘
                        │
        ┌───────────────▼─────────────────────┐
        │  手脚：浏览器自动化（Playwright）     │
        │  打开、点击、输入、读取、截图、下载   │
        └───────────────┬─────────────────────┘
                        │
        ┌───────────────▼─────────────────────┐
        │  循环：Agent 编排                     │
        │  执行→观察结果→再决策，直到任务完成   │
        └─────────────────────────────────────┘
```

### 2.3 为什么选 Playwright（而不是 Selenium）

| 对比项 | Selenium | Playwright |
| --- | --- | --- |
| 等待机制 | 手动 `sleep`/显式等待，脆弱 | **自动等待**元素可交互，稳定 |
| 速度 | 较慢 | 快（更接近浏览器底层协议） |
| 多浏览器 | 需各自装 driver | 一套 API 统一 chromium/firefox/webkit |
| 现代特性 | 支持有限 | 原生支持下载/上传/网络拦截/多标签 |
| 安装 | driver 版本对齐痛苦 | 一条命令装内核 |

对企业级 Agent 来说，**稳定性（自动等待）** 和 **现代特性（下载/网络拦截）** 是关键，所以我们选 Playwright Java。

## 四、真实项目中的它

在我们要构建的 **ZeroHub AI Agent Platform** 中，Browser Agent 是一个**独立的能力模块**，对外提供两类接口：

- **原子动作接口**（`/day09/browser/action/*`）：供其他系统直接集成，比如"给我这个 URL 的正文"；
- **自然语言接口**（`/day09/browser/agent/run`）：供上层对话式 AI 调用，比如用户说"帮我查下这个快递到哪了"，平台就把这句话交给 Browser Agent 去自主完成。

它和前面几天的模块并列，共同组成平台的"能力矩阵"：RAG 负责"知道"，Workflow 负责"编排"，Browser 负责"动手"。真正的商业级 Agent，一定是这些能力的组合。

**设计上的企业级考量**（后面章节会逐一落地）：

- 浏览器是**贵资源**（一个进程几百 MB 内存），必须复用、必须限流；
- 会话有**状态**（登录态、Cookie），必须隔离，否则张三的订单会串到李四；
- 自动化会**失败**（网络抖动、页面变化），必须有超时、有降级、有异常兜底；
- 要能**水平扩展**（多实例部署），会话态要能外置到 Redis。

这些，就是"玩具脚本"和"生产系统"的分水岭，也是这一天真正的含金量所在。

## 五、避坑指南（先建立敬畏心）

即使还没写代码，也先把这些"血泪教训"刻在脑子里，后面每一章你都会真切体会到：

1. **别把 Browser Agent 当爬虫脚本写**：脚本跑一次就退出，而 Agent 是常驻服务，资源管理是第一要务。
2. **别每个请求新开一个浏览器**：一个 Browser 进程几百 MB，10 个并发就是几个 G，服务器分分钟 OOM。
3. **别让 Context 跨请求复用**：登录态会污染，A 用户的会话被 B 用户看到，是严重的安全事故。
4. **别用 `Thread.sleep` 等页面**：睡短了元素还没出来，睡长了浪费时间。要用 Playwright 的自动等待。
5. **别忘了装浏览器内核**：Playwright 依赖引进来不等于内核装好了，第一次运行必须 `install`。
6. **别在 Docker 里忘加 `--no-sandbox`**：容器里 Chromium 不加这个参数直接崩。
7. **别把整页 HTML 塞给大模型**：几万字的 HTML 会让 token 成本爆炸、上下文超限。
8. **别忽略并发限流**：不限流的话，一次流量高峰就能把浏览器进程拖垮。
9. **别忘了资源回收**：借了会话不还、许可泄漏，池子会越用越小直到死锁。
10. **别忽视合规边界**：自动化操作他人系统要注意授权与合规，技术能力不等于可以随意使用。

## 本章小结

- Browser Agent 解决的是"无 API 系统的自动化"这一真实企业痛点，是 Agent 与真实世界交互的关键能力；
- 它由**大模型（脑）+ 浏览器自动化（手）+ 循环编排**三部分组成，我们用 Playwright Java 作为自动化引擎；
- 企业级 Browser Agent 的核心不在于会调 API，而在于**把浏览器这种贵、有状态、易失败的资源管好**；
- 从下一章开始，我们将从 Playwright 的对象模型讲起，一步步搭出这个模块。
