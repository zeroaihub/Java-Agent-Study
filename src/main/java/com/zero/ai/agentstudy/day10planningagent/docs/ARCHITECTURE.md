**设计要点**：`planner-core` 只管「想出计划」，`planner-executor` 只管「执行」，`planner-engine` 做「调度 + 状态机」把两者串起来，`planner-reflection` 做「质检」，`planner-context` 是贯穿全局的「共享黑板」，`planner-memory` 负责持久化与经验复用。**职责单一、可独立测试、可插拔替换**——这就是企业级 Agent 与 Demo 的分水岭。

## 二、Planner 生命周期（状态机）

```
   [NEW] ──plan()──▶ [PLANNING] ──ok──▶ [READY]
                          │ fail             │ schedule
                          ▼                  ▼
                      [FAILED]          [EXECUTING] ◀────┐
                          ▲                  │           │ next step
                          │             step done        │
                          │                  ▼           │
              max replan  │            [REFLECTING]───────┘ (continue)
                          │                  │
                          │        ┌─────────┼──────────┐
                          │        │         │          │
                     need replan   ok    need human   all done
                          │        │         │          │
                          └────[RE_PLANNING] │          ▼
                                   ▲    [WAITING_HUMAN] [SUCCEEDED]
                                   └─────────┘ (Day11)
```

状态说明：
- `NEW`：收到目标，尚未规划。
- `PLANNING`：LLM 正在拆解目标为 Plan。
- `READY`：计划就绪，等待调度。
- `EXECUTING`：Executor 正在执行当前步骤。
- `REFLECTING`：一步（或全部）执行完，Reflector 审视结果。
- `RE_PLANNING`：反思判定需要改计划，回到规划。
- `WAITING_HUMAN`：高风险步骤等待人工审批（Day11 启用）。
- `SUCCEEDED / FAILED`：终态。`FAILED` 触发条件：超出 maxReplan / maxSteps / 预算耗尽。

**为什么用状态机**：Agent 执行是长流程、可暂停、可恢复、可回溯的。用状态机而非一串 if/else，才能做到「宕机后从 EXECUTING 续跑」「REFLECTING 后动态跳回 RE_PLANNING」，且状态可落库、可观测。

## 三、Planning 主流程（ReAct + Plan-and-Solve 混合）

```
  goal
   │
   ▼
 ┌──────────────┐   （可选）检索历史相似任务经验
 │ 1. 理解目标   │◀───────────── planner-memory
 └──────┬───────┘
        ▼
 ┌──────────────┐   LLM 产出结构化 Plan(JSON) → 解析 → 校验 → 落 context
 │ 2. 生成计划   │
 └──────┬───────┘
        ▼
```

## 四、Reflection（反思）流程

```
   step 执行结果(StepResult)
        │
        ▼
 ┌───────────────────────────┐
 │ Reflector.reflect(...)     │  输入：目标 + 当前步骤 + 结果 + 历史观察
 └────────────┬──────────────┘
              │ LLM 判定
   ┌──────────┼───────────┬───────────────┐
   ▼          ▼           ▼               ▼
 SUCCESS   RETRY_STEP  REPLAN        ABORT
（合格,   （本步重试, （计划有问题, （无法完成,
  继续）    换参数）    重新规划）     终止上报）
```

**为什么反思要独立成模块**：把「做」和「判断做得对不对」分开，才能用不同的 Prompt / 甚至不同的模型（更强/更便宜）做质检；也便于设「反思次数上限」防止犹豫循环。

## 五、Re-Planning（动态重规划）流程

```
 Reflector 判定 REPLAN
        │
        ▼
 ┌───────────────────────────┐   replanCount++
 │ 检查 replanCount ≤ maxReplan│──超限──▶ [FAILED] 上报
 └────────────┬──────────────┘
              │ 未超限
              ▼
 ┌───────────────────────────┐  把「已完成步骤 + 失败原因 + 观察」作为上下文
 │ Planner.replan(context)    │  让 LLM 只重规划「剩余部分」，保留已成功结果
 └────────────┬──────────────┘
              ▼
        新 Plan（增量）→ 回到执行循环
```

**关键设计**：重规划**不是从零重来**，而是带着「已完成的成果 + 失败教训」做增量修正——既省 Token，又避免推翻正确的部分。

## 六、Tool Selection（工具选择）流程

```
 当前子任务(SubTask)
        │
        ▼
 ┌──────────────────┐   全部候选工具的 name/description/schema
 │ ToolRegistry     │──────────────────────────────┐
 └──────────────────┘                               ▼
                                          ┌──────────────────┐
                                          │ ToolSelector      │
                                        │ (LLM 或 规则匹配)  │
                                          └────────┬─────────┘
                                                   ▼
                                     选中 ToolSpec + 生成参数(JSON)
                                                   │ 参数校验
                                                   ▼
                                          交给 Executor 调用
```

**企业约束**：LLM 只能从**白名单注册表**里选工具，参数必须过 **Schema 校验**，杜绝「调用不存在的工具 / 传非法参数」的幻觉。

## 七、Task 调度流程（依赖 + 优先级）

```
   Plan = [step1, step2, step3, step4]  （带 dependsOn / priority）
                │
                ▼
   构建 TaskGraph（DAG）
   step1 ──▶ step3
   step2 ──▶ step3 ──▶ step4
                │
                ▼
   Scheduler 每轮挑选：所有「依赖已完成」且「优先级最高」的就绪步骤
   ┌─────────────────────────────────────────────┐
   │ ready = steps.filter(deps 全 done).sortBy(pri)│
   │ pick ready.first()  →  执行                    │
   └─────────────────────────────────────────────┘
   （支持串行；扩展点：ready 有多个时可并行执行）
```

## 八、与平台其他模块的关系

```
        ┌──────────────────────── Planning Agent (Day10) ────────────────────────┐
        │                         "指挥官 / 大脑"                                   │
        └───┬──────────┬──────────┬──────────┬──────────┬──────────┬─────────────┘
            │          │          │          │          │          │
   as Tool  ▼   as Tool▼  as Tool ▼  subtask ▼   经验    ▼   知识    ▼
      ┌─────────┐ ┌────────┐ ┌────────┐ ┌──────────┐ ┌────────┐ ┌──────┐
      │Browser  │ │Workflow│ │  MCP   │ │Multi-    │ │Memory  │ │ RAG  │
      │Agent D9 │ │  D6    │ │  D7    │ │Agent D8  │ │  D4    │ │  D5  │
      └─────────┘ └────────┘ └────────┘ └──────────┘ └────────┘ └──────┘
```

**核心思想**：前九天的每种能力，对 Planning Agent 而言都是「一个可调度的资源」——Browser/Workflow/MCP 被封装成 `Tool`，Multi-Agent 的专家被当作「可派发子任务的执行者」，Memory/RAG 提供「规划前的经验与知识」。Planning Agent站在最上层做**宏观决策**。

## 九、为什么这样设计 / 如何扩展

| 设计决策 | 为什么 | 如何扩展 |
|----------|--------|----------|
| 规划/执行分离 | 单一职责，可分别测试与替换 | 换更强模型只改 Planner，不动 Executor |
| 状态机驱动 | 长流程可暂停/恢复/回溯/落库 | 加 `WAITING_HUMAN` 即得 Day11 HITL |
| Context 黑板 | LLM 无状态，进度必须外置 | 换 Redis/PG 实现即得分布式持久化 |
| 工具注册表 | 防幻觉、可治理、白名单 | 新工具实现接口 + 注册即可，无需改核心 |
| 反思独立模块 | 质检与执行解耦，可用不同模型 | 增/换反思策略（规则/LLM/多数投票） |
| 预算护栏 | 防死循环、防烧钱 | 按租户/任务配额动态下发预算 |

## 十、可观测性（Tracing）

每一步都产出一条结构化 Trace，落 `planner-memory`：

```
{ planId, step, state, thought, tool, args, observation, tokens, latencyMs, ts }
```

线上排障时，一条 planId 就能还原 Agent「当时怎么想、调了什么、看到什么、为什么改计划」的完整心路历程。**先可观测，再谈优化。**
