# 第一章：为什么需要 Planning Agent？

> 本章不写代码，先建立「思想」。Planning 是 Agent 从「被驱动的执行器」进化为「自主的行动者」的分水岭。
> 严格遵循五段教学模板：① 为什么学 ② 是什么 ③ 怎么用 ④ 用在哪 ⑤ 避坑。

---

## 第一部分：为什么学（核心价值）

### 1. 为什么 ChatBot 不需要 Planning？

ChatBot 的交互模型是**单步、无状态、被动**的：

```
用户问一句 → LLM 想一下 → 回一句 → 结束
```

它的任务边界是「回答这一个问题」。它不需要「先做 A 再做 B、A 失败了改走 C」——因为它根本没有「多步任务」的概念。**ChatBot 的世界里只有『回合（turn）』，没有『任务（task）』。** 所以它不需要 Planning。

### 2. 为什么 AI Agent 必须 Planning？

Agent 的任务模型是**多步、有状态、主动**的。给它的不是「一个问题」，而是「一个目标」：

> 「帮我分析 GitHub Trending 今天最热门的 AI Agent 项目，并总结生成 Markdown。」

这句话背后藏着一连串**运行时才能确定的决策**：

- 先打开浏览器还是先查缓存？（顺序）
- 打开哪个页面？trending 的哪个分类？（参数）
- 提取到的内容要不要二次总结？（依赖）
- 页面打不开怎么办？换个源还是重试？（失败恢复）
- 总结得不好怎么办？重新总结还是重新提取？（反思与修正）

**没有一个「人」或「预先写死的代码」能提前把这些决策全部枚举出来**——因为它们取决于运行时的真实情况。这些决策必须由 Agent 自己在运行中做出，这就是 Planning。

**一句话：ChatBot 处理『问题』，Agent 完成『目标』。目标天然是多步的，多步就需要规划。**

### 3. 为什么 Workflow 不等于 Planning？

这是最容易混淆、也最关键的一点。我们 Day6 已经做了很强的 Workflow，为什么还要 Planning？

| 维度 | Workflow（Day6） | Planning（Day10） |
|------|------------------|-------------------|
| 流程图（DAG） | **编译期人画死** | **运行时 LLM 动态生成** |
| 步数 | 固定已知 | 未知，可能循环 N 次 |
| 分支 | 预设好的条件分支 | 依据运行结果临时决定 |
| 失败处理 | 预设的重试/降级节点 | 反思后**改变计划本身** |
| 适合 | 流程明确的稳定业务 | 目标明确但路径未知的任务 |

**一句话：Workflow 回答『怎么走这张既定的图』；Planning 回答『这张图本身应该长什么样』。** 前者是「执行确定流程」，后者是「生成流程」。二者不是替代关系，而是**上下层关系**——Planning 在宏观决策，遇到「某段流程是固定的」时，它会把那段 Workflow 当成一个工具去调用。

### 4. 为什么 Multi-Agent 必须有 Planner？

Day8 的 Multi-Agent 让多个专家 Agent 协作。但「谁先干、谁后干、干到什么程度、结果不满意谁重做」——这个**协调决策**必须有人来做。这个「人」就是 Planner。**在 Multi-Agent 体系里，Planner 就是那个『项目经理 / 协调者 Agent』**，它把大目标拆成子任务，再派发给合适的专家。没有 Planner 的 Multi-Agent，就是一群没有 leader 的专家，各自为战、无法收敛。

### 5. 真实企业案例：它们为什么都有 Planning？

| 产品 | 它做什么 | 为什么必须有 Planning |
|------|----------|----------------------|
| **Claude Code** | AI 写代码/改代码 | 「实现一个功能」= 读代码→改多个文件→跑测试→修错误→再跑，多步且失败要修正 |
| **OpenAI Codex** | 代码生成 Agent | 同上，长任务需要拆解与自我纠错 |
| **Cursor Agent** | IDE 里的自主编码 | 「重构这个模块」需要自己决定改哪些文件、按什么顺序 |
| **Devin** | AI 软件工程师 | 端到端交付需求，从理解到部署，全程自主规划几十上百步 |
| **Manus** | 通用任务 Agent | 「帮我订机票+酒店+做行程」需要动态拆解、选工具、失败重来 |
| **AutoGPT** | 全自主 Agent 先驱 | 「目标→自动拆任务→执行→循环」，第一个把 Planning 闭环跑通的开源项目 |

**共同点：它们面对的都是『目标明确、但达成路径运行时才知道』的任务。** 这正是 Planning 的用武之地，也是它们被称为「Agent」而非「工具」的根本原因。

### 6. Planning 带来了什么？商业价值是什么？

- **能力跃迁**：从「回答一个问题」到「独立完成一件事」，产品价值量级提升。
- **减少人工**：原本需要人一步步操作的流程，Agent 自主跑完，直接替代人力。
- **护城河**：谁的 Agent「更能自主、更少翻车」，谁的 AI SaaS 就更有竞争力——这是纯 API 套壳产品无法复制的工程壁垒。
- **可规模化**：一个 Planning Engine 支撑 AI Coding、AI Office、AI 客服等多条业务线，边际成本极低。

## 第二部分：是什么（本章只做概念定位）

本章先建立「Planning Agent 在整个体系中的位置」，具体的 Goal / Plan / TaskGraph / 状态机等概念，第二章会逐个展开并画 ASCII 图。这里先给一张**能力进化全景图**：

```
   ChatBot         Tool Agent        Workflow Agent      Planning Agent
   （会说话）    →   （会用手）     →    （会走固定流程）  →   （会自己定流程）
      │                │                    │                     │
   一问一答         单步调工具           执行预设DAG           运行时生成DAG
      │                │                    │                     │
   无状态           无编排              人编排               自编排 + 自纠错
                                                                  ▲
                                                    Day10 在这里
```

**核心定位**：Planning Agent = 一个**「会规划、会执行、会反思、会重规划」**的自主循环。它站在 ZeroHub 平台的最上层，把前九天的所有能力（LLM/Memory/RAG/Workflow/MCP/Multi-Agent/Browser）当作可调度的资源。

它的最小闭环是四个动词（后续章节逐一实现）：

```
  规划(Plan) → 执行(Execute) → 反思(Reflect) → 重规划(Re-Plan) → ……直到目标达成
```

## 第三部分：怎么用（本章不落代码，先讲思路）

本章是「思想章」，不写 Java 代码。但我们要先想清楚：**如果让你现在动手，你会怎么设计？** 带着这个问题进入后续章节，你的收获会大得多。

先给你一个「心智模型」——把 Planning Agent 想象成一个**靠谱的实习生**：

1. 你给他一个目标（不是详细步骤）。
2. 他先**列个计划**（拆任务）——好实习生不会闷头就干。
3. 他**一步步做**，每做完一步**回头看看对不对**（反思）。
4. 做错了他**自己调整**，而不是傻等你来救（自我修正 / 重规划）。
5. 全程他**记得自己做到哪了**（上下文 / 状态）。
6. 但你会给他**约束**：别无限试、别乱花钱、危险操作先问我（预算护栏 / HITL）。

后续每一章，就是把这个「靠谱实习生」的每一项能力，用 Java + Spring AI **真正实现出来**：

- chapter-03：实现「列计划」（`LlmPlanner`）
- chapter-04：实现「记得做到哪 + 按依赖调度」（`Context` + `Scheduler`）
- chapter-05：实现「一步步做 + 失败重试」（`Executor`）
- chapter-06：实现「回头看对不对 + 自我修正」（`Reflector`）
- chapter-07：实现「选对工具」（`ToolSelector`）
- chapter-08：实现「做错了重新规划」（`replan`）
- chapter-09：把它接上 Browser/Workflow/MCP，跑通完整案例

## 第四部分：用在哪（真实项目）

Planning Agent 是当下最有商业价值的 Agent 形态，典型落地场景：

- **AI Coding（Claude Code / Cursor / Devin）**：把需求拆成「读码→改码→测试→修复」的自主循环。
- **AI Office**：「帮我把这份销售数据做成周报」→ 读表→分析→画图→写结论→排版，多步自主。
- **AI Customer Service**：复杂工单「退货并补偿」→ 查订单→判定政策→发起退款→通知用户，带审批断点。
- **AI Search（Deep Research）**：一个问题→拆成多个子查询→分别检索→交叉验证→综合成报告。
- **AI Knowledge**：「整理这个领域的知识库」→ 收集→去重→结构化→生成→校验。
- **AI Trading**：「监控并在满足条件时提示」→ 拉数据→计算指标→判断→（高风险动作走 HITL）。
- **Browser Agent 场景（我们今天的 Demo）**：「分析 GitHub Trending 并总结」→ 浏览→提取→总结→质检→输出。

它们的企业实现共性：**任务规划 + 步骤拆解 + 动态执行 + 自动修正 + 失败恢复 + 工具选择 + 多 Agent 协作**——正是我们 Day10 要逐一实现的能力。

## 第五部分：避坑（本章先建立「危险意识」，共 10 条）

Planning Agent 是「双刃剑」——自主性越强，失控风险越大。企业级落地必须防的十个坑（后续章节会逐一给出工程对策）：

1. **无限循环**：Agent 反复「做→反思→重做」不收敛。对策：`maxSteps` 硬上限。
2. **Planner 死循环**：反复重规划出同样的错计划。对策：`maxReplan` + 每次重规划必须带「上次失败原因」。
3. **Token 爆炸**：每步都把全部历史塞进 Prompt，上下文越滚越大。对策：滑窗 + 观察摘要。
4. **Prompt 爆炸**：工具太多，把几百个工具描述全塞进去。对策：先粗筛候选工具再交给 LLM 选。
5. **工具误选**：LLM 选了不合适或不存在的工具。对策：白名单注册表 + Schema 校验。
6. **重复执行**：同一步被反复执行（尤其是有副作用的写操作）。对策：幂等设计 + 步骤去重。
7. **计划失效**：环境变了但计划没更新（如页面改版）。对策：反思机制及时触发重规划。
8. **上下文污染**：错误的中间结果污染了后续所有推理。对策：反思时能「废弃坏观察」。
9. **反思过多**：过度自我怀疑，反复反思不干活。对策：反思次数上限 + 明确的「够好就停」标准。
10. **不可观测**：出了问题不知道 Agent 当时怎么想的。对策：每步落结构化 Trace（planId 全链路）。

**企业最佳实践总纲：给自主性套上『预算 + 白名单 + 可观测 + 有限反思』四道护栏，让 Agent 既聪明又可控。**

## 本章小结

- ChatBot 处理「问题」，Planning Agent 完成「目标」；目标天然多步，多步就需要规划。
- Workflow 是「执行确定流程」，Planning 是「运行时生成流程」，二者是上下层关系。
- Planning Agent 的最小闭环：**规划 → 执行 → 反思 → 重规划**。
- 自主性必须配套护栏：预算、白名单、可观测、有限反思。

### 常见问题（FAQ）

- **Q：有了 Planning 是不是就不需要 Workflow 了？** A：不。稳定、明确的固定流程用 Workflow 更省钱更可控；Planning 用于路径未知的任务，并把 Workflow 当工具调用。
- **Q：Planning 一定要用 LLM 吗？** A：不一定。经典任务可用规则/搜索规划；但面对自然语言目标，LLM 规划是目前最通用的方案，我们采用 LLM + 工程护栏。
