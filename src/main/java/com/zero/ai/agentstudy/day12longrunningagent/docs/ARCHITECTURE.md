## 一、整体架构

```
                          ┌───────────────────────────────────────────┐
                          │              Runtime API (REST)             │
                          │  create / trigger / suspend / resume / get  │
                          └───────────────────────┬─────────────────────┘
                                                  │
                          ┌───────────────────────▼─────────────────────┐
                          │                Agent Runtime                 │
                          │  (生命周期总控 / 装配 Session / 分发任务)      │
                          └───┬───────────┬───────────┬──────────┬───────┘
                              │           │           │          │
                 ┌────────────▼──┐  ┌─────▼─────┐ ┌───▼────┐ ┌───▼──────┐
                 │  Scheduler    │  │ Task Queue│ │ Event  │ │ Monitor  │
                 │ (Cron/Delay)  │  │  + DLQ    │ │  Bus   │ │ +Metrics │
                 └───────┬───────┘  └─────┬─────┘ └───┬────┘ └────┬─────┘
                         │                │           │           │
                         └────────┬───────┴───────────┘           │
                                  │                               │
                         ┌────────▼─────────┐                     │
                         │  Agent Executor  │◄────────────────────┘
                         │ (逐步执行 Steps)  │   (发事件/上报指标)
                         └───┬───────────┬──┘
                             │           │
             ┌───────────────▼──┐   ┌────▼───────────────────────┐
             │   Agent Steps    │   │  Checkpoint / Snapshot      │
             │ plan/browse/llm/ │   │  (每步前后保存可恢复状态)     │
             │ approve/send ... │   └────┬───────────────────────┘
             └───────┬──────────┘        │
                     │                   │
        ┌────────────▼───────┐   ┌───────▼──────────────┐
        │  Day09 Browser     │   │  State Persistence    │
        │  Day10 Planning    │   │  Session / Context    │
        │  Day06 Workflow    │   │  Redis 8 / PostgreSQL │
        │  Day04 Memory      │   └───────┬──────────────┘
        │  Day11 HITL        │           │
        └────────────────────┘   ┌───────▼──────────┐
                                  │  Recovery        │
                                  │ (崩溃后重建状态)   │
                                  └──────────────────┘
```

**为什么这样设计**：Runtime 作为总控，把"何时执行（Scheduler）""执行什么（Task Queue）""怎么执行（Executor + Steps）""状态怎么存（Persistence/Checkpoint）""坏了怎么办（Recovery/Retry/DLQ）""外界怎么看（Event/Monitor）"六件事彻底解耦。每个盒子职责单一、面向接口，可独立替换与测试。

**企业为什么这样实现**：这与 Temporal、Netflix Conductor 的分层完全一致——把"业务逻辑（Steps）"与"可靠性机制（持久化/重试/恢复）"分离，让业务开发者只写 Step，可靠性由 Runtime 统一保障。

## 二、Agent 生命周期（状态机）

```
        create
          │
          ▼
      ┌────────┐  start   ┌─────────┐  step done & has next  ┌─────────┐
      │CREATED │─────────►│ RUNNING │───────────────────────►│ RUNNING │
      └────────┘          └────┬────┘                        └─────────┘
                               │
        ┌──────────────────────┼───────────────────────────────┐
        │ need approval        │ error(retryable)               │ all done
        ▼               ▼                                ▼
   ┌───────────┐         ┌───────────┐  retry<=max         ┌───────────┐
   │ SUSPENDED │         │ RETRYING  │────────────────────►│ COMPLETED │
   └─────┬─────┘         └─────┬─────┘                      └───────────┘
         │ resume              │ retry>max
         ▼                     ▼
   ┌───────────┐         ┌───────────┐
   │  RUNNING  │         │  FAILED   │──► Dead Letter Queue
   └───────────┘         └───────────┘
         ▲
         │ cron next fire
   ┌───────────┐
   │  WAITING  │  (周期任务：本轮完成后等待下一次触发)
   └───────────┘
```

合法状态：`CREATED / RUNNING / SUSPENDED / RETRYING / WAITING / COMPLETED / FAILED / CANCELLED`。

**为什么这样设计**：用显式状态机约束流转，非法跳转（如 `COMPLETED→RUNNING`）在入口即被拒绝，避免状态混乱导致的重复执行或数据错乱。

**企业为什么这样实现**：金融、审批类系统对"状态正确性"是零容忍的。状态机是把"业务规则"编码为"不可绕过的约束"的标准手段。

## 三、事件流程（Event Driven）

```
   Executor / Scheduler / Recovery
            │  publish
            ▼
      ┌───────────┐
      │ Event Bus │  (进程内异步分发；生产可换 Redis Pub/Sub / Kafka)
      └─────┬─────┘
            │ dispatch
   ┌────────┼─────────┬───────────────┐
   ▼        ▼         ▼               ▼
┌──────┐ ┌──────┐ ┌────────────┐ ┌──────────────┐
│Monitor│ │ Log  │ │Checkpoint  │ │ Business Hook│
│指标   │ │审计  │ │Trigger     │ │(如通知/回调) │
└──────┘ └──────┘ └────────────┘ └──────────────┘

事件类型：AgentStarted / StepStarted / StepCompleted / StepFailed /
          Suspended / Resumed / Completed / Failed / CheckpointSaved / Recovered
```

**为什么这样设计**：事件驱动让"发生了什么"与"谁来响应"解耦。新增一个监听者（如接入告警）不需要改动 Executor。

**企业为什么这样实现**：解耦 + 可扩展 + 可审计。所有关键动作皆有事件，天然形成审计流水，满足合规追溯要求。

## 四、恢复流程（Recovery）

```
   进程崩溃 / 机器重启 / 部署升级
            │
            ▼
   ┌──────────────────┐  1.扫描持久化中未终态的 Session
   │  Recovery Service │  (state ∈ {RUNNING, SUSPENDED, RETRYING})
   └────────┬─────────┘
            │ 2.抢占租约(分布式锁)，防止重复恢复
            ▼
   ┌──────────────────┐  3.加载该 Session 最近一次 Checkpoint
   │  CheckpointStore  │
   └────────┬─────────┘
            │ 4.重建 AgentContext(step指针 + 中间产物)
            ▼
   ┌──────────────────┐  5.从 checkpoint.step+1 继续执行(已完成步骤不重放)
   │   Agent Executor  │
   └──────────────────┘
```

**为什么这样设计**：恢复的本质是"从最近的一致性点继续"，而非从头重来。step 指针 + 幂等保证不重复执行有副作用的步骤。

**企业为什么这样实现**：崩溃恢复能力是"生产可用"与"Demo"的分水岭。Temporal 的 Event Sourcing、数据库的 WAL 日志，思想同源——先持久化、后执行、崩溃后重放。

## 五、重试流程（Retry）

```
   Step 执行
      │
      ▼
   ┌────────┐  success   ┌─────────────┐
   │ 执行中  │───────────►│ 打 Checkpoint│
   └───┬────┘            └─────────────┘
       │ throw
       ▼
   ┌───────────────┐  可重试异常?  否 ┌─────────┐
   │ 判定异常类型   │──────────────►│ FAILED  │──► DLQ
   └──────┬────────┘               └─────────┘
          │ 是
          ▼
   ┌───────────────┐  attempt < max ? 否 ┌─────────┐
   │ 计算退避时间   │──────────────────►│ FAILED  │──► DLQ
   │ (指数退避+抖动)│                    └─────────┘
   └──────┬────────┘
          │ 是，sleep(backoff) 后重试
          └──────────────► 回到"Step 执行"
```

退避公式：`delay = min(base * 2^(attempt-1), maxDelay) + random_jitter`。

**为什么这样设计**：指数退避避免"雪崩式重试"打垮下游；抖动避免大量任务同时重试造成"惊群"；区分可重试/不可重试异常避免对业务错误无意义重试。

**企业为什么这样实现**：这是 AWS SDK、gRPC、消息中间件的通用重试范式。DLQ 保证"最终一定有人管"，不会有任务被静默丢弃。

## 六、状态持久化流程（State Persistence）

```
   内存中的 AgentContext(运行态)
          │  序列化(JSON)
          ▼
   ┌──────────────────────────────────────────────┐
   │            State Persistence Layer             │
   │  ┌────────────┐        ┌───────────────────┐  │
   │  │  Redis 8   │ 热数据 │   PostgreSQL 17    │  │
   │  │ Session索引 │       │  Session/Checkpoint │  │
   │  │ 租约/心跳   │       │  历史/审计/持久快照 │  │
   │  └────────────┘        └───────────────────┘  │
   └──────────────────────────────────────────────┘
          ▲                          ▲
   反序列化(恢复时)             pgvector(可选：记忆/RAG)
```

**为什么这样设计**：热路径（判活、租约、当前状态）放 Redis 追求低延迟；冷/持久数据（历史 Checkpoint、审计）放 PostgreSQL 追求可靠与可查询。分层存储兼顾性能与可靠。

**企业为什么这样实现**：几乎所有大型有状态系统都采用"缓存热点 + 关系库持久"的分层存储。pgvector 让长期记忆与状态库统一在 PostgreSQL，降低运维复杂度。

## 七、如何接入既有能力（组合视图）

```
             ┌────────────────────────────────────────────┐
             │            Long Running Agent                │
             │  (Runtime + Lifecycle + Persistence)         │
             └───────────────────┬──────────────────────────┘
                                 │ 每个能力 = 一个 AgentStep
   ┌──────────┬──────────┬───────┼────────┬──────────┬──────────┐
   ▼          ▼          ▼       ▼        ▼          ▼          ▼
Planning   Browser    Workflow Memory    MCP     Multi-Agent  HITL
(Day10)    (Day09)    (Day06) (Day04)  (Day07)   (Day08)    (Day11)
 规划步骤   抓取步骤    编排段   记忆读写  工具调用   子Agent    审批挂起
```

**为什么这样设计**：Runtime 是底座，前序所有能力都以"可持久化、可恢复的 Step"形态被编排进长任务。这样既复用了已有能力，又赋予它们"跨越时间、崩溃可恢复"的新特性。

**企业为什么这样实现**：平台化的关键是"能力可组合"。统一的 Step 抽象让新能力接入零成本，是 ZeroHub 平台可持续演进的基础。

## 八、多节点与高可用（未来扩展）

```
   ┌────────┐   ┌────────┐   ┌────────┐
   │Node A  │   │Node B  │   │Node C  │   (Kubernetes StatefulSet)
   └───┬────┘   └───┬────┘   └───┬────┘
       │            │            │
       └────────────┼────────────┘
                    ▼
        ┌───────────────────┐
          │   Redis (租约/锁)  │  同一 Session 同一时刻仅一个节点持有
          │   PostgreSQL       │  Session/Checkpoint 共享存储
          └───────────────────┘

   节点宕机 → 租约超时 → 其他节点抢占 → 从 Checkpoint 恢复(Failover)
```

**为什么这样设计**：无状态化调度 + 共享持久化 + 租约抢占 = 水平扩展 + 自动故障转移。

**企业为什么这样实现**：这是分布式任务系统（Quartz 集群、ElasticJob、Temporal Cluster）的标准高可用模型，久经生产验证。
