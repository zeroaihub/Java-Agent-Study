# Chapter 01 · 为什么需要 Long Running Agent（理论与商业价值）

> 本章目标：从工程与商业双视角，彻底讲清"为什么 Agent 不能一次完成""为什么企业 Agent 可以运行数天""为什么 Workflow 不够""为什么需要 Runtime"，并用真实产品案例佐证商业价值。本章不写业务代码，聚焦"心智模型"的建立。

---

## 第一部分 · 为什么学

### 1.1 为什么 Agent 不能一次完成？

我们已经在 Day01–Day11 里把"单次智能"打磨得很好：LLM 会推理（Day01/02）、会用工具（Day03）、有记忆（Day04）、能检索（Day05）、能编排（Day06）、能协作（Day08）、能操作浏览器（Day09）、能规划（Day10）、能等人（Day11）。但这些能力有一个共同的隐含前提：**它们都发生在"一次请求"的时间窗内**。

而真实世界的任务，天然是"跨越时间"的。请看几个例子：

- "帮我盯着这个 GitHub Issue，一旦有人回复就总结并通知我" —— 可能等 3 天。
- "每天早上把昨天的销售数据汇总成日报发给团队" —— 永远不结束。
- "帮我把这份 2000 页的合同逐条审查并生成风险清单" —— 需要几十分钟到几小时。
- "监控竞品官网，一旦上新就抓取并分析" —— 7×24 常驻。

这些任务无法"一次完成"，根本原因有三：

1. **物理时间限制**：LLM 单次调用有 Token 上限、有响应时长；HTTP 请求有网关超时（通常 30–60s）。任务再简单，只要跨越这个时间窗就必须"分段"。
2. **依赖外部时间**：任务要"等"——等定时、等审批、等外部回调、等数据到达。等待期间 Agent 必须"活着但不占用资源"。
3. **可靠性要求**：分段执行意味着中间会崩，崩了必须能续。"一次完成"的模型没有"续"的概念。

**一句话**：Agent 不能一次完成，是因为"任务的时间尺度 > 单次请求的时间尺度"，这是一个物理事实，不是能力问题。

### 1.2 为什么需要 Long Running？

既然任务要分段、要等待、可续，我们就需要一套机制来管理"Agent 的一生"：什么时候生（创建）、什么时候动（执行）、什么时候睡（挂起/等待）、什么时候醒（恢复）、什么时候死（完成/失败）。这套"生命周期管理"能力，就是 Long Running 的本质。

Long Running ≠ "跑得久"，而是 = **"具备跨越时间、跨越故障、跨越等待，持续推进同一个任务直到真正完成的能力"**。

### 1.3 为什么企业 Agent 可以运行数天？

秘诀不是"进程一直不退出"（那不现实，机器会重启、会部署升级），而是：

> **把 Agent 的"当前状态"持久化到外部存储，让 Agent 的"逻辑生命"独立于任何单个进程的"物理生命"。**

进程可以死，但状态在数据库里。新进程起来后，从数据库里读回状态，接着往下跑。于是"逻辑上"这个 Agent 已经活了三天，尽管承载它的进程可能已经换了五个。这就是"数天运行"的工程真相——**状态外置 + 崩溃恢复**。

### 1.4 为什么 Workflow 不够？

Day06 我们做了 Workflow。它把任务拆成节点、按图执行。但 Day06 的 Workflow 是**进程内、同步、一次性**的：一个请求进来，从头节点跑到尾节点，返回结果。它有三个致命短板：

| 短板 | Workflow（Day06） | Long Running Runtime（Day12） |
| --- | --- | --- |
| 跨请求 | 不能，一次请求内跑完 | 能，状态外置，可跨越无数请求 |
| 崩溃恢复 | 不能，进程死则重来 | 能，从 Checkpoint 恢复 |
| 等待/挂起 | 不能，节点必须立即返回 | 能，SUSPENDED 后可等数天 |
| 定时/重复 | 不能 | 能，Scheduler 驱动 |

所以 Workflow 是 Runtime 的一个**子集**——Runtime 内部的"一段同步执行"可以用 Workflow 来组织，但 Runtime 额外提供了"持久化、恢复、等待、调度"这些 Workflow 没有的能力。**Workflow 解决"怎么编排"，Runtime 解决"怎么长期可靠地跑"。**

### 1.5 为什么需要 Runtime？

Runtime（运行时）是把上述所有能力（生命周期、持久化、恢复、调度、重试、事件、监控）**收敛为一个统一底座**的东西。没有 Runtime，你就得在每个 Agent 业务代码里手写"存状态、判超时、搞重试、做恢复"——重复、易错、不可维护。有了 Runtime，业务开发者只写"业务步骤（Step）"，可靠性由 Runtime 统一保障。这正是**关注点分离**在 Agent 领域的体现。

## 第二部分 · 是什么

Long Running Agent 在概念上由两层构成：

```
┌─────────────────────────────────────────────┐
│  业务层：Agent Steps (plan/browse/llm/send)   │  ← 你写的业务逻辑
├─────────────────────────────────────────────┤
│  运行时层：Runtime                            │  ← 平台提供的可靠性底座
│  Lifecycle · Session · Persistence ·          │
│  Checkpoint · Recovery · Scheduler ·          │
│  Queue · Retry · Event · Monitor              │
└─────────────────────────────────────────────┘
```

- **上层（业务）**：关心"做什么"——登录、抓取、总结、发送。
- **下层（运行时）**：关心"如何可靠地做"——什么时候做、崩了怎么办、状态存哪里。

本章只需建立这个"两层心智模型"，具体每个组件（Runtime/Session/Checkpoint...）的实现将在 Chapter 02–07 逐个展开，Chapter 08 综合实战。

## 第三部分 · 怎么用（本章为认知铺垫，给出使用者视角）

作为**使用者**，你与 Long Running Agent 的交互只有几个动词，它们直接对应 REST API（详见 Chapter 08）：

```
create   → 定义一个长任务 Agent（类型 + 触发规则），得到 sessionId
trigger  → 立即触发一次执行（演示用，不必等定时）
suspend  → 主动挂起
resume   → 恢复挂起的 Agent
get      → 查询当前状态、执行到第几步、历史 Checkpoint
cancel   → 终止
```

作为**开发者**，你只需实现 `AgentStep` 接口，把业务塞进去，其余交给 Runtime。这种"使用者动词 + 开发者 Step"的极简接口，是优秀 Runtime 的标志——把复杂性藏在底座里。

## 第四部分 · 真实项目

以下产品/框架都是 Long Running Agent 思想的现实印证：

- **OpenAI Operator**：让 Agent 长时间操作浏览器完成任务（订票、购物），任务跨越多个页面、多分钟，需要状态保持与中断恢复。
- **Claude Code / AI Coding Agent**：一个"重构整个模块"的任务可能跑几十分钟，涉及大量文件读写与编译验证，天然是长任务，需要进度保持。
- **Google Jules**：异步编码 Agent，你提交任务后它在后台跑，跑完通知你——典型的"提交即挂起、完成即回调"长生命周期模型。
- **Microsoft Copilot Agent / Azure AI Agent Service**：企业级 Agent 托管服务，内建 Thread（会话）、Run（执行）、持久化状态，本质就是一个 Agent Runtime。
- **LangGraph**：以"图 + 持久化状态（checkpointer）"为核心，支持中断（interrupt）与恢复，是 Long Running Agent 的开源代表。
- **Temporal / Netflix Conductor**：虽非 AI 专用，但它们的"持久化工作流 + 崩溃恢复 + 重试"正是 Agent Runtime 借鉴的工程母体。

**商业价值**：企业愿意为 Agent 付费，不是因为它"会聊天"，而是因为它能"可靠地、无人值守地、7×24 地替人完成有价值的长流程业务"。可靠性 = 商业价值。而可靠性正是 Long Running Runtime 提供的。一个会 90% 任务但 10% 概率丢状态的 Agent，在企业里价值为负（因为要人兜底）；一个能力朴素但 99.99% 可靠可恢复的 Agent，才能真正替代人力、产生 ROI。

## 第五部分 · 避坑（认知层面的十大误区）

1. **误区：Long Running = 让进程一直别退出。** 正解：靠状态外置 + 恢复，进程可随时更替。
2. **误区：把长任务塞进一个超长 HTTP 请求。** 正解：请求负责"触发"，执行在后台异步推进。
3. **误区：用 Workflow 直接当长任务引擎。** 正解：Workflow 是进程内同步的，缺少持久化/恢复/等待。
4. **误区：状态只存内存。** 正解：进程一崩全丢，必须外置到 Redis/PostgreSQL。
5. **误区：恢复 = 从头重跑。** 正解：从最近 Checkpoint 续跑，且已完成的副作用步骤不重放。
6. **误区：所有异常都重试。** 正解：区分"系统失败（可重试）"与"业务失败（不该重试）"。
7. **误区：无限重试。** 正解：设上限 + 退避 + DLQ 兜底。
8. **误区：忽视幂等。** 正解：恢复会重放，副作用步骤必须幂等，否则重复发消息/重复扣款。
9. **误区：没有监控就上线。** 正解：长任务"看不见"最可怕，必须有状态/指标/日志可观测。
10. **误区：以为单机够用。** 正解：企业需要多节点，要提前考虑租约/失败转移，避免脑裂与重复执行。

## 本章小结

- Agent 不能一次完成是"时间尺度"的物理事实，不是能力问题。
- "运行数天"靠的是"状态外置 + 崩溃恢复"，让逻辑生命独立于进程物理生命。
- Workflow 是 Runtime 的子集；Runtime 额外提供持久化、恢复、等待、调度。
- 商业价值的核心是"可靠性"，这正是 Long Running Runtime 的价值。
