# Chapter 02 · 是什么：Office Agent 架构与 Document Pipeline 原理

> 本章对应教学模板"第二部分：是什么"。chapter-01回答了"为什么值得做"，本章回答"它到底是什么、由什么构成、按什么原理运转"。读完本章，你要能在白板上画出 Office Agent 的完整架构，讲清 Document IR、Document Pipeline、七阶段流水线、Spring AI 2 的集成方式，并为 chapter-03 开始写代码打下认知地基。

---

## 一、先建立一个精确的定义

在 chapter-01 我们给过一个通俗定义："AI Office Agent 是把大模型能力翻译成办公结果的引擎。"通俗定义适合对 CEO 讲，但工程师需要一个**可落地为代码的精确定义**：

> **AI Office Agent 是一个"以自然语言指令为输入、以可交付办公制品为输出"的自主执行系统。它由感知、规划、生成、渲染、审批、交付、观测七个阶段构成一条流水线（Pipeline）；其中'内容'以统一的中间表示（Document IR）在阶段之间流转，与'格式'彻底解耦。**

这个定义里藏着三个关键词，它们是本章的三根支柱：

1. **自主执行系统**：不是一次函数调用，而是一条可编排、可重试、可审批、可观测的流程。
2. **Document IR（中间表示）**：内容与格式解耦的载体，是整个架构的"通用货币"。
3. **七阶段 Pipeline**：把"一句话 → 一整套交付"拆成七个可独立治理的阶段。

我们逐一拆解。

## 二、Office Agent 的宏观解剖：五个子系统

如果把 Office Agent 拆开看内部器官，它由五个子系统组成。这五个子系统与 README 的"五大能力域"一一对应，但这里我们从"是什么"的角度重新定义每个子系统的**职责边界**与**输入输出契约**。

```
┌──────────────────────────────────────────────────────────────────────┐
│                         AI Office Agent                                │
│                                                                 │
│  ┌────────────┐   ┌────────────┐   ┌────────────┐   ┌──────────────┐  │
│  │ ① 感知子系统 │──▶│ ② 规划子系统 │──▶│ ③ 生成子系统 │──▶│ ④ 渲染子系统   │  │
│  │  Perceive  │   │   Plan     │   │  Generate  │   │   Render     │  │
│  └────────────┘   └────────────┘   └────────────┘   └──────┬───────┘  │
│                                                            │          │
│                                    ┌───────────────────────┘          │
│                                    ▼                                   │
│                            ┌──────────────┐      ┌──────────────────┐  │
│                            │ ⑤ 交付子系统   │◀────│  审批闸门(横切)     │  │
│                            │   Deliver    │      │  Human Approval  │  │
│                            └──────────────┘      └──────────────────┘  │
│                                                                        │
│         观测子系统(横切) Observe：Trace + Metric + Audit 贯穿全部       │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.1 感知子系统（Perceive）

- **职责**：把"外部世界的原始信息"转成"Agent 能理解的结构化上下文"。
- **输入**：用户指令、附件（Excel/PDF/图片）、知识库检索请求。
- **输出**：`PerceivedContext`——包含解析后的表格数据、OCR 文本、RAG 检索到的相关片段、用户历史偏好（Memory）。
- **复用**：Day5 RAG（检索）、Day4 Memory（偏好）。
- **本课程新增**：文件解析器（Excel 读取、PDF 文本抽取、图片 OCR）。

### 2.2 规划子系统（Plan）

- **职责**：把"一个复合目标"拆解为"一串有序、可执行的步骤"。
- **输入**：用户指令 + `PerceivedContext`。
- **输出**：`OfficePlan`——一个有向步骤列表，每个 `Step` 声明"要调用哪个能力、依赖哪些前置步骤的产出"。
- **复用**：Day10 Planning、Day6 Workflow、Day8 Multi-Agent。
- **本课程新增**：面向办公领域的 Step 类型（ReadExcel / Analyze / GenWord / GenPpt / SendMail ...）。

### 2.3 生成子系统（Generate）

- **职责**：调用 LLM，产出**结构化内容**，即 Document IR。**注意：这里 LLM 绝不产出 Word 二进制或 POI 代码，只产出 IR。**
- **输入**：某个 Step 的指令 + 上下文。
- **输出**：`DocumentIR`——章节、段落、表格、图表、列表的结构化树。
- **复用**：Day2 LLM API、Day3 Function Calling。
- **本课程新增**：把 LLM 的自由文本"约束"成结构化 IR 的 Prompt 工程与 Schema 校验。

### 2.4 渲染子系统（Render）

- **职责**：把 `DocumentIR` 渲染成具体格式的文件（.docx / .xlsx / .pptx / .pdf / .md）。
- **输入**：`DocumentIR` + 目标格式 + 模板（可选）。
- **输出**：真实文件（字节流 / 存储路径）。
- **复用**：无（这是本课程的**全新核心**）。
- **实现**：Apache POI、docx4j、PDFBox 等，藏在 `DocumentRenderer` 端口背后。

### 2.5 交付子系统（Deliver）

- **职责**：把渲染好的制品"送出去"——发邮件、写日历、上传共享盘、存知识库。
- **输入**：文件 + 交付目标（收件人 / 日历 / 存储位置）。
- **输出**：交付结果（发送回执 / 上传 URL / 知识库文档 ID）。
- **复用**：Day7 MCP（工具协议）、Day9 Browser（上传）、Day5 RAG（存知识库）。
- **本课程新增**：邮件、日历、待办的领域封装。

### 2.6 两个横切子系统

- **审批闸门（Human Approval）**：不是一个阶段，而是插在"渲染完成"与"对外交付"之间的**横切关卡**。复用 Day11。
- **观测（Observe）**：Trace / Metric / Audit 贯穿所有阶段，是横切关注点（Cross-Cutting Concern）。

> **认知要点**：五个"串行子系统"负责推进流程，两个"横切子系统"负责治理流程。这正是企业级系统与 Demo 的分水岭——Demo 只有前者，产品必须有后者。

## 三、核心概念一：Document IR（文档中间表示）

Document IR 是整个 Office Agent 架构的"心脏"。理解它，就理解了本课程 80% 的设计。

### 3.1 为什么必须有 IR？——三个致命反例

假设我们**不用** IR，让 LLM 直接生成 Word。会发生什么？

**反例一：让 LLM 直接输出 POI 代码。**
```
用户 → LLM → 生成一段 "new XWPFDocument(); ..." 的 Java 代码 → 编译执行
```
灾难：LLM 生成的代码可能编译不过、可能有安全风险（任意代码执行）、无法审计、换成 PPT 就要重新生成一套代码。**不可控、不安全、不可维护。**

**反例二：让 LLM 直接输出 Word 的 XML/二进制。**
灾难：docx 的 OOXML 极其复杂，LLM 极易生成格式错乱的文档；且 Token 消耗巨大；且无法复用到 PPT/PDF。**贵、脆、不通用。**

**反例三：为每种格式各写一套"从文本到文件"的逻辑。**
灾难：Word 一套、PPT 一套、PDF 一套，逻辑重复；改一处内容结构，三处都要改。**违反 DRY，维护地狱。**

### 3.2 IR 的解法：内容与格式解耦

IR 的核心思想是在"内容"与"格式"之间插入一个**稳定的、格式无关的中间层**：

```
                     ┌──────────────┐
   LLM 只负责产出 ──▶ │  Document IR  │ ──▶ 渲染器负责变成格式
   (结构化内容)       │  (格式无关)    │     (纯工程问题)
                     └──────┬───────┘
                            │ 一份 IR，多格式导出
        ┌──────────┬────────┼────────┬──────────┐
        ▼          ▼        ▼        ▼          ▼
      .docx      .xlsx    .pptx    .pdf       .md
```

**这带来四个决定性好处：**

1. **LLM 的职责被极大简化**：它只需产出"有哪些章节、每段写什么、表格是什么"，不关心字体字号页边距。
2. **一份内容，多格式导出**：同一份 IR 能同时渲染成 Word、PPT、PDF——这正是"生成周报同时做 PPT"场景的技术基础。
3. **内容可被审批、被二次编辑**：IR 是结构化的、可读的，审批人能看懂、能修改，改完再渲染。
4. **格式渲染成为纯工程问题**：与 AI 无关，可用成熟的 POI/PDFBox，可单元测试，可保证格式正确。

### 3.3 IR 的结构设计（概念模型）

Document IR 本质是一棵**文档树**。我们先在概念层面把它画出来（chapter-03 落地为 Java 代码）：

```
DocumentIR
├── metadata (标题, 作者, 租户, 创建时间, 主题/VI)
└── blocks : List<Block>            ← 文档由有序的"块"组成
     ├── HeadingBlock   (level, text)          标题块（1~6 级）
     ├── ParagraphBlock (runs)                 段落块（含富文本 Run）
     ├── TableBlock     (headers, rows)        表格块
     ├── ListBlock      (ordered, items)       列表块（有序/无序）
     ├── ChartBlock     (type, series)         图表块（柱/线/饼）
     ├── ImageBlock     (source, caption)      图片块
     └── PageBreakBlock                        分页块
```

**为什么用"块（Block）"模型？** 这借鉴了 Notion 的 Block 设计（见 chapter-01 竞品分析）。块是文档的最小结构单元，它让我们能：
- 精确地对文档某一部分做操作（"重写第三段""替换这张表"）。
- 统一 Word/PPT/PDF 的内容模型——PPT 的一页就是一组 Block，PDF 的一节也是一组 Block。
- 让 LLM 以"块清单"的形式产出内容，天然结构化。

### 3.4 IR 与富文本：Run 的概念

段落内部并非一整块纯文本，而是由多个 **Run** 组成——每个 Run 是"一段样式一致的文字"。这是所有办公格式（Word/PPT）通用的富文本模型：

```
ParagraphBlock
└── runs : List<Run>
     ├── Run("本季度销售额增长 ", 普通)
     ├── Run("32%", 加粗+红色)
     └── Run("，超额完成目标。", 普通)
```

**为什么需要 Run？** 因为"加粗某几个字""给关键数字标红"是办公文档的刚需。若段落只存纯字符串，就无法表达局部样式。Run 模型是 Word 和 PPT 的底层共识，我们的 IR 直接对齐它，渲染时零阻抗。

## 四、核心概念二：Document Pipeline（七阶段流水线）

IR 是"数据模型"，Pipeline 是"处理模型"。IR 是名词，Pipeline 是动词。

### 4.1 为什么是"流水线"而不是"一个大方法"？

一个自然的问题：为什么不写一个 `generateAndSendReport()` 方法把所有事做完？

因为办公任务有四个特性，逼着我们必须用流水线：

1. **多步骤**：读数据、分析、生成、渲染、审批、发送——天然是多阶段。
2. **可失败可重试**：LLM 可能超时、邮件可能发送失败。每阶段需独立重试，而非从头再来。
3. **需人工介入**：中间要停下来等审批。一个大方法无法"暂停并等待外部事件"。
4. **需可观测**：老板问"我的周报卡在哪一步了？"，你得答得出来。只有分阶段才能定位。

流水线（Pipeline）架构完美满足这四点：每阶段是一个可独立治理的处理单元。

### 4.2 七阶段全解（含每阶段的输入/输出/失败策略）

```
 阶段              输入                 输出                  失败策略
 ────────────────────────────────────────────────────────────────────────
 ① Perceive  用户指令+附件         PerceivedContext      解析失败→提示补充材料
    感知      +知识库检索请求       (表格/OCR/RAG片段)
 ────────────────────────────────────────────────────────────────────────
 ② Plan      指令+PerceivedCtx     OfficePlan            规划失败→降级为单步/追问
    规划                          (有序 Step 列表)
 ────────────────────────────────────────────────────────────────────────
 ③ Generate  Step 指令+上下文      DocumentIR            LLM超时→重试/换模型
    生成                          (结构化内容树)          Schema不合→约束重生成
 ────────────────────────────────────────────────────────────────────────
 ④ Render    DocumentIR+格式+模板  文件(字节/路径)        渲染异常→回退纯文本/记录
    渲染
 ────────────────────────────────────────────────────────────────────────
 ⑤ Review    待交付制品+租户策略    审批结论              超时→按策略挂起/降级
    审批                          (Approve/Reject)
 ────────────────────────────────────────────────────────────────────────
 ⑥ Deliver   文件+交付目标         交付回执              发送失败→重试+补偿
    交付                          (URL/回执/文档ID)
 ────────────────────────────────────────────────────────────────────────
 ⑦ Observe   全阶段事件           Trace/Metric/Audit    (横切，不阻断主流程)
    观测
```

### 4.3 阶段之间靠什么传递数据？——WorkflowContext

阶段与阶段之间不直接调用，而是通过一个共享的 **WorkflowContext**（工作流上下文）传递数据。这借鉴了 Day6 Workflow 的设计：

```
   ┌───────────────── WorkflowContext ─────────────────┐
   │  instruction : String       (原始指令)             │
   │  tenant      : TenantContext(租户/用户/权限)        │
   │  perceived   : PerceivedContext                    │
   │  plan        : OfficePlan                          │
   │  irMap       : Map<StepId, DocumentIR>             │
   │  artifacts   : Map<StepId, Artifact> (渲染产物)     │
   │  approvals   : List<ApprovalRecord>                │
   │  trace       : TraceContext                        │
   └────────────────────────────────────────────────────┘
        ▲          ▲          ▲          ▲          ▲
        │ 读写      │ 读写      │ 读写      │ 读写      │ 读写
     Perceive    Plan     Generate    Render     Deliver
```

**为什么用共享上下文而非层层传参？**
- 阶段数量多，参数会爆炸；用一个上下文对象承载，签名统一为 `Stage.execute(WorkflowContext ctx)`。
- **可持久化**：把 `WorkflowContext` 存进 Redis/PG，就能实现"断点续跑"（Day12 Long Running）——审批等了两小时，进程重启了，从上下文恢复即可。
- **可观测**：整个上下文就是一份天然的执行快照，便于追踪与审计。

### 4.4 Pipeline 的执行引擎：责任链 + 状态机

七个阶段如何被驱动执行？我们用**责任链（Chain of Responsibility）+ 状态机（State Machine）**的组合：

```
 责任链：阶段串成链，每个 Stage 处理完把 ctx 交给下一个
 ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
 │Perceive│──▶│  Plan  │──▶│Generate│──▶│ Render │──▶ ...
 └────────┘   └────────┘   └────────┘   └────────┘

 状态机：整个任务有明确状态，审批/失败会改变状态流转
 CREATED → PERCEIVING → PLANNING → GENERATING → RENDERING
        → PENDING_APPROVAL ──approve──▶ DELIVERING → COMPLETED
                          └──reject───▶ REJECTED
        (任一阶段异常) ──▶ FAILED ──重试──▶ 回到失败阶段
```

- **责任链**负责"正常路径"的推进。
- **状态机**负责"异常路径"和"人工介入"的治理：审批挂起、失败重试、任务取消，都是状态迁移。

这套组合是 chapter-08 `officeworkflow` 的核心，本章先建立认知。

## 五、核心概念三：端口与适配器（Hexagonal）在 Office Agent 的落地

chapter-01 和 ARCHITECTURE 都提到六边形架构。这里我们讲清楚它在 Office Agent 里**具体隔离了什么**。

### 5.1 领域核心不能知道的"脏东西"

`officecore` 领域核心里，绝不能出现这些类型：`XWPFDocument`（POI）、`javax.mail.Session`（邮件）、`Playwright`（浏览器）、`ChatClient`（Spring AI 的具体类）。

为什么？因为一旦领域核心 import 了 POI，就等于把"业务规则"和"Word 用哪个库"焊死了。将来要：
- 换 docx4j 替代 POI？改核心。
- 换国产模型替代 OpenAI？改核心。
- 单元测试领域逻辑？必须启动真实 POI/SMTP，测不动。

### 5.2 端口（Port）：领域核心向外看的"插座"

领域核心只定义**接口（Port）**，声明"我需要一个能把 IR 渲染成文件的东西""我需要一个能发邮件的东西",但不关心谁来实现：

```
                officecore (领域核心, 零技术依赖)
   ┌──────────────────────────────────────────────────┐
   │  «Port» DocumentRenderer  render(IR,fmt):Artifact  │
   │  «Port» MailSender        send(Mail):Receipt       │
   │  «Port» FileStorage       save(bytes):URL          │
   │  «Port» KnowledgeStore    index(doc):DocId         │
   │  «Port» OcrEngine         recognize(img):Text      │
   │  «Port» ModelPort         complete(prompt):IR      │
   └──────────────────────────────────────────────────┘
         ▲            ▲            ▲            ▲
         │ implements │            │            │  (适配器在核心之外)
   ┌─────┴────┐ ┌─────┴────┐ ┌─────┴────┐ ┌─────┴────┐
   │PoiWord   │ │JavaMail  │ │MinioFile │ │PgVector  │
   │Renderer  │ │Sender    │ │Storage   │ │Knowledge │
   └──────────┘ └──────────┘ └──────────┘ └──────────┘
   officeword    officemail   基础设施适配器  officecore之外
```

### 5.3 依赖倒置：谁依赖谁？

关键在于**依赖方向倒过来**了（依赖倒置原则 DIP）：

```
 传统分层（错误）：  核心 ──依赖──▶ POI/邮件/模型   ❌ 核心被技术绑架
 六边形（正确）：    核心 ◀──依赖── POI/邮件/模型   ✅ 技术依赖核心的接口
```

适配器（`officeword` 等）依赖 `officecore` 的接口，而不是反过来。这样领域核心保持纯净，任何技术实现都是"可插拔的外设"。

### 5.4 这对我们意味着什么（工程收益）

1. **可测试**：测领域逻辑时，用 Mock 的 `DocumentRenderer` 即可，秒级单测。
2. **可替换**：客户要私有化、要换国产模型？只写一个新适配器，核心一行不动。
3. **可并行开发**：定好端口接口后，写 Word 引擎的人和写编排的人可以并行开工。

## 六、Spring AI 2.0 在 Office Agent 中的集成方式

本课程技术栈是 Spring Boot 4.1 + Spring AI 2.0。这里讲清楚 Spring AI 在架构里的**位置**与**用法边界**（原理不重复 Day2/Day3）。

### 6.1 Spring AI 只出现在"适配器层"

按六边形原则，Spring AI 的 `ChatClient`、`ChatModel` 等具体类，**只允许出现在 `ModelPort` 的适配器实现里**，绝不进入领域核心。

```
 officecore 定义:   «Port» ModelPort {  DocumentIR generate(GenSpec spec)  }
                                    ▲
                                    │ implements
 适配器实现(可见 Spring AI):  SpringAiModelAdapter
                             ├── 注入 ChatClient (Spring AI 2)
                             ├── 拼 Prompt（把 GenSpec 转成结构化生成指令）
                             ├── 调用 chatClient.prompt()...call()
                             └── 把返回解析/校验成 DocumentIR
```

### 6.2 结构化输出：让 LLM 直接吐 IR

Spring AI 2 支持结构化输出（Structured Output）——把模型返回直接映射成 Java 对象。我们用它让 LLM 直接产出 IR 的骨架：

```
 概念流程（chapter-03/04 落地代码）：
   GenSpec(要写什么) 
      │
      ▼
   ChatClient.prompt()
      .system("你是文档结构化生成器，只输出符合 Schema 的 JSON")
      .user(拼装的生成需求)
      .call()
      .entity(DocumentIR.class)   ← Spring AI 结构化输出，直接得到 IR
      │
      ▼
   Schema 校验 → 合格则进入渲染，不合格则约束重生成
```

**为什么用结构化输出？** 它把"让 LLM 产出结构化内容"这件事从"手写 JSON 解析 + 容错"变成"声明一个类"。这大幅降低了生成子系统的复杂度，也让 IR 成为 LLM 与渲染器之间的强类型契约。

### 6.3 工具调用（Tool）：把办公能力暴露给 Agent

规划子系统需要 LLM"决定调用哪个能力"。Spring AI 2 的Tool（Function Calling）机制让我们把办公动作注册为工具：

```
 注册工具：  @Tool readExcel(path)     读 Excel
             @Tool generateWord(ir)    生成 Word
             @Tool sendMail(mail)      发邮件
             ...
 LLM 规划：  根据用户指令，自主决定调用序列
```

> **边界提醒**：Tool 的原理是 Day3 的内容，本课程不重复。这里只强调"办公动作如何封装成 Tool 供规划层使用"。真正的复杂度不在调用机制，而在"如何把办公动作设计成粒度合适、可组合的 Tool"——这是 chapter-08 的重点。

## 八、常见误区澄清（是什么 ≠ 你以为的那样）

在真正写代码前，先破除几个新手常见的错误认知：

1. **误区：Office Agent = 调用 LLM 生成文本 + 塞进 Word。**
   - 澄清：那只是"生成 + 渲染"两个阶段，缺了感知、规划、审批、交付、观测。缺了这些，它是个玩具，不是产品。

2. **误区：IR 是可有可无的中间层，直接生成文件更快。**
   -澄清：没有 IR，"一份内容多格式导出""内容可审批可编辑""格式可测试"三个企业级能力全部丧失。IR 是架构的地基，不是装饰。

3. **误区：把所有逻辑写在一个 Service 里更简单。**
   - 澄清：短期简单，长期灾难。无法重试、无法审批挂起、无法观测定位、无法横向扩展。企业级的复杂度是"必要复杂度"。

4. **误区：Spring AI 应该在业务层到处用。**
   - 澄清：Spring AI 只能在 `ModelPort` 适配器里出现。让它渗透到领域核心，就丧失了可替换、可测试、可私有化。

5. **误区：审批是可选的"锦上添花"。**
   - 澄清：在企业场景，"对外发送/上传"不经审批就是**合规事故**。审批是刚需，不是选配。

## 九、本章小结与思考题

### 核心结论

1. Office Agent 的精确定义 = 七阶段自主执行系统 + Document IR + 内容格式解耦。
2. 五个串行子系统（感知/规划/生成/渲染/交付）推进流程，两个横切子系统（审批/观测）治理流程。
3. **Document IR** 是架构心脏：内容与格式解耦，一份 IR 多格式导出，内容可审批可测试。IR 是"块 + Run"的文档树。
4. **Document Pipeline** 是处理模型：七阶段各有输入/输出/失败策略，靠 WorkflowContext 传递数据，用责任链 + 状态机驱动。
5. **六边形端口**隔离一切技术（POI/邮件/模型），领域核心零技术依赖，可测试、可替换、可私有化。
6. **Spring AI 2** 只出现在适配器层，用结构化输出让 LLM 直接产出 IR，用 Tool 把办公能力暴露给规划层。

### 面试题（自测）

- 为什么 Office Agent 必须引入 Document IR？请用"一份内容多格式导出"和"内容可审批"两个场景论证。
- Document Pipeline 为什么用责任链 + 状态机，而不是一个大方法？分别解决了什么问题？
- 在六边形架构下，`officecore` 里为什么绝不能出现 `XWPFDocument`？依赖方向应该是怎样的？
- Spring AI 的 `ChatClient` 应该出现在哪一层？为什么不能进入领域核心？
