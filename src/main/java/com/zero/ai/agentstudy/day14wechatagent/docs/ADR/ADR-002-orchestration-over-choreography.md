# ADR-002：编排（Orchestration）而非编舞（Choreography）

- **状态**：Accepted
- **日期**：2026-08-04

## 背景

会议纪要全链路涉及多步骤：读会话 → 规划 → 生成纪要 → 上传 → 存知识库 → 人工审批 → 发送通知。
这些步骤之间存在**强顺序依赖**，且中间需要**人工审批挂起**。
实现多步业务流程有两种范式：

- **编排（Orchestration）**：一个中心协调者（编排器/引擎）显式调度每一步。
- **编舞（Choreography）**：各服务通过事件互相触发，去中心化。

## 决策

采用**编排模式**：由 `WorkflowEngine` 中心调度步骤，`MeetingSummaryOrchestrator` 作为用例入口。

关键考量——本场景需要：
- **强顺序**：步骤严格有序，前置产出喂给后续；
- **可挂起审批**：Human Approval 需要在中途停下等待人工，编排天然支持挂起-续跑；
- **可观测**：中心调度点便于打点、追踪、干预；
- **中断-恢复**：靠「状态驱动执行」（取下一个 PENDING 步骤）恢复，无需分布式游标。

## 后果

**正面**：
- 流程一目了然，审批挂起/续跑实现简单；
- 全链路可追踪、可人工干预；
- 便于加超时、重试、Saga 补偿。

**负面**：
- 编排器是流程的中心，需警惕演变成「上帝类」——通过「只编排不写业务规则」的纪律约束；
- 中心节点是关注点，需保证其可用性与幂等。

## 备选方案

- **编舞（事件驱动）**：松耦合、易扩展，但跨服务链路难追踪、审批挂起态难管理、调试困难。对本项目「强顺序 + 人工审批」的需求不划算，被否决。
- **未来演进**：局部可引入事件（如通知送达回执），但主流程保持编排。
