## 二、为什么架构设计要先于编码

很多团队的知识库项目最终腐化成「大泥球（Big Ball of Mud）」，根因是**从未定义模块边界**：检索里塞了解析逻辑，切分里写了权限判断，改一处崩三处。

架构设计的本质，是提前回答三个问题：

1. **系统由哪些部分组成？**（模块切分）
2. **各部分谁依赖谁？**（依赖方向）
3. **数据/控制如何流动？**（数据流）

回答清楚这三点，就有了「地图」。后续每写一行代码，都能对照地图确认「我在哪、我能调用谁」。

## 三、核心设计精讲

### 3.1 如何切分模块：按「变化的原因」

我们没有按技术分层切成 `controller / service / dao`，而是按**业务能力 + 变化原因**切成 14 个模块。判断依据是**单一职责原则（SRP）的模块级表述**：

> 一个模块应该只有一个「变化的原因」。

- `parser` 变化的原因：**新增文件格式**（新增 Word/CAD 解析）。
- `retrieval` 变化的原因：**检索算法演进**（加入新的融合策略）。
- `reranker` 变化的原因：**精排模型升级**。

它们变化的原因彼此独立，因此必须是独立模块。若把三者塞进一个 `SearchService`，任何一个原因的变化都会冲击其余两者。

### 3.2 依赖方向：单向、无环、指向稳定

对照 [`ARCHITECTURE.md`](../ARCHITECTURE.md) 第二节的依赖表，有三条铁律：

| 铁律 | 含义 | 违反后果 |
| --- | --- | --- |
| **单向** | A 依赖 B，则 B 不能依赖 A | 双向耦合，无法独立测试/复用 |
| **无环** | 不存在 A→B→C→A | 循环依赖，编译/启动/理解全困难 |
| **指向稳定** | 依赖应指向更不易变的模块 | 依赖易变模块 = 自己也变得易变 |

`core` 零依赖、最稳定，所有人依赖它；`integration` 依赖所有人、最易变，没人依赖它。这正是「稳定依赖原则（SDP）」的体现——**依赖箭头永远从易变指向稳定**。

### 3.3 端口与适配器：领域如何「使唤」基础设施

领域层需要向量存储，但**绝不能直接 import pgvector 的类**（那会让领域依赖基础设施，违反依赖规则）。解法是**依赖倒置**：

```java
// 领域层：定义端口（我要什么）
public interface VectorStorePort {
    void upsert(List<VectorRecord> records);
    List<ScoredChunk> search(EmbeddingVector query, SearchFilter filter, int topK);
}

// 基础设施层：提供适配器（我怎么给）
public class PgVectorStoreAdapter implements VectorStorePort { /* 调 pgvector */ }
```

领域层只认 `VectorStorePort` 接口，运行时由 Spring 注入 `PgVectorStoreAdapter`。**换向量库只需换适配器，领域代码一行不改**——这就是六边形架构「可插拔」的威力。

### 3.4 两条数据流的设计哲学

**写入流水线**用「状态机 + 事件」串联：文档在 `UPLOADED → PARSED → CHUNKED → EMBEDDED → INDEXED` 间流转，每步产出事件，下游异步消费。好处是**可断点续跑**——嵌入阶段挂了，重跑只需从 `CHUNKED` 继续，不必重新解析。

**检索流水线**的灵魂是 **ACL 前置**：

```
❌ 错误：先检索 TopK → 再过滤掉无权的 → 可能不足 K 条，且已把敏感数据读进内存
✅ 正确：把 ACL 变成向量库的 metadata filter → 只召回有权数据
```

前者是「先偷看再假装没看」，后者是「压根看不到」。在合规敏感的企业场景，只有后者可接受。

## 四、架构思想升华

1. **康威定律**：系统结构会映射组织结构。14 模块的边界，也应是团队协作的边界——一个小组维护 `parser`，另一小组维护 `retrieval`，互不踩脚。
2. **架构守护测试**：架构不是画完图就完事，会随时间腐化。用 Spring Modulith 编写「依赖断言测试」，让 CI 自动拦截违规依赖（第 13/14 章落地）。
3. **演进式架构**：v1.0 是单体 Modulith（模块清晰但同进程）。因为模块边界清晰，v2.0 拆微服务时几乎零成本——**好的单体是好的微服务的前提**。

## 五、企业实战案例

### 案例：某制造业知识库的「检索越权」审计事故

某企业早期检索实现为「先向量召回 Top50，再在 Java 里遍历过滤无权文档」。安全审计时发现：**无权文档的正文已被读入应用内存并写进了日志**，虽未返回给用户，但已构成「数据接触」，审计不通过。

**整改**：改为 ACL 前置——把用户可见的 `kb_id` 集合下推为 pgvector 的 `WHERE kb_id = ANY(...)` 过滤，无权数据从 SQL 层就被挡住，内存里根本不出现。审计通过。

**启示**：安全边界要尽可能**靠近数据源**，而非靠近用户。这正是本平台把 `acl-retrieval` 独立成模块、并前置到召回的原因。

## 六、面试高频题

1. **六边形架构与传统三层架构的本质区别？**
   三层是「技术分层」（controller/service/dao），依赖单向向下但领域仍耦合框架；六边形是「领域为中心」，通过端口/适配器让领域完全不依赖技术细节，可插拔、易测试。

2. **如何防止模块间产生循环依赖？**
   ① 明确依赖方向（指向更稳定的模块）；② 用领域事件替代直接调用做解耦；③ 用 Spring Modulith / ArchUnit 写守护测试在 CI 拦截。

3. **多租户为什么选行级隔离而非独立库？如何保证不串租户？**
   行级隔离成本低、易伸缩；靠「强类型 `TenantId` + `TenantContext` 强制在场 + 所有查询自动注入 tenant 过滤 + ACL 前置」四重保障防串租户。

4. **RRF 融合为什么优于简单加权？**
   RRF 只依赖排名而非分数，天然规避「向量相似度分数」与「BM25 分数」量纲不可比的问题，鲁棒且无需调参归一化。
