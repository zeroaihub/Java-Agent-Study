# 第 8 章：knowledge-reranker —— 精排与 MMR 多样性去重

> 配套代码：`reranker/`
> 可运行 Demo：`demo/Chapter08Demo.java`

## 一、这一章要解决的问题

第 7 章我们拿到了「融合后的 Top-N 候选」。**但融合分高，不等于真正相关。**

两个真实的尴尬：

1. **排序不够准**：召回阶段为了覆盖百万级数据，用的是"可预计算、可索引"的便宜方法，
   它的排序精度天然有限。真正相关的那条可能排在第 3 而不是第 1；
2. **结果高度重复**：企业知识库里，同一段政策往往被写在 5 份文档里
   （制度原文、部门细则、培训材料、FAQ、邮件通知），措辞几乎一样。
   纯按相关性排序，**Top-5 会被这份重复内容占满**。

第 2 点的后果比想象中严重：

> **LLM 拿到的上下文里 80% 是冗余信息，而 Token 预算已耗尽。**
> 用户问「报销要注意什么」，得到的是同一个句子的五种说法，
> 而「发票开具要求」「审批时效」这些真正有用的信息全被挤掉了。

本章交付两个能力：**精排（Rerank）** 与 **多样性去重（MMR）**。

## 二、为什么需要"两阶段"：召回与精排的分工

| | 召回阶段（Retriever） | 精排阶段（Reranker） |
| --- | --- | --- |
| **目标** | 别漏掉（高召回） | 排得准（高精度） |
| **候选量** | 百万级 | 几十条 |
| **算法** | 双塔向量 / BM25（可预计算、可索引） | Cross-Encoder（必须在线算） |
| **耗时** | 毫秒级 | 十到百毫秒级 |

关键在于**向量检索是「双塔（Bi-Encoder）」结构**：

- query 和 chunk **各自独立编码**，两者从不"见面"，最后只算一个余弦；
- 好处是 chunk 向量可以**离线预计算并建索引**，所以能撑起百万级检索；
- 代价是**无法捕捉 query 与 chunk 之间的细粒度交互**。

而 **Cross-Encoder** 把 query 和 chunk **拼在一起**送进模型：

```
[CLS] 员工出差怎么报销 [SEP] 差旅费用报销标准：员工出差返回后… [SEP]
```

让每一对 token 都能互相注意力。精度高得多，
但**每一对都必须重新算一遍，无法预计算、无法建索引**。
所以它只能用于几十条候选的精排。

> **这就是工业界标准的「召回-精排（Retrieve & Rerank）」两阶段架构：**
> 先用便宜的方法从百万里捞出 50 条，再用贵的方法从 50 条里挑出最好的 5 条。
> **用 5% 的成本，买到 80% 的质量提升。**

## 三、三种 Reranker 实现

### 3.1 PassThroughReranker —— Null Object 的价值

它什么也不做，直接截断返回前 topN 条。

**为什么需要一个"什么都不做"的实现？**

1. **消灭 `if (reranker != null)`**：Null Object 模式让调用方代码变干净；
2. **提供基线**：想知道重排序到底带来多少提升？
   跑一遍直通、跑一遍真正的重排序，对比 NDCG@5——
   **没有基线的优化都是自嗨**；
3. **降级时的安全选择**：Cross-Encoder 不可用时自动切到直通。

### 3.2 HeuristicReranker —— 可解释的精排

它没有模型，用一组**人工特征**加权打分：

| 特征 | 权重 | 说明 |
| --- | --- | --- |
| 查询词覆盖率 | 1.0 | 查询里的词有多少比例出现在候选文本中，最朴素也最有效 |
| 融合分（归一化） | 0.35 | 召回阶段的 RRF 得分作为先验，它不是 0，因为召回排序本身包含信息 |
| 精确短语命中 | 0.6 | 整个查询串作为连续子串出现，比"部分词命中"强得多 |
| 标题命中 | 0.4 | 标题是作者写的摘要，命中标题的信号强度远高于正文 |
| 多路命中加成 | 0.25 | Hybrid Search 独有的免费信号 |
| 长度惩罚 | −0.3 ~ 0 | 见下方 |

**长度惩罚为什么做成"两端惩罚"？**

- 太短的切片（<30 字）往往是页眉页脚、目录碎片、表格标题，
  它看起来"词都命中了"，但**信息量为零**；
- 太长的切片（>800 字）会挤占宝贵的 Prompt 预算，而且主题发散、相关性被稀释。

所以我们惩罚两端，偏爱「刚好把一件事说清楚」的中等长度切片。

> **它的定位**：不是 Cross-Encoder 的替代品（精度差得远），
> 但它零依赖、完全可解释，而且**揭示了精排的本质**——
> 所谓精排，就是「用更丰富的特征，对一个更小的候选集做更精细的打分」。

### 3.3 CrossEncoderReranker —— 接真实精排模型

```java
POST /rerank
{"model":"bge-reranker-v2-m3",
 "query":"报销流程是怎样的",
 "documents":["...", "..."]}

→ {"results":[{"index":0,"relevance_score":0.93}, ...]}
```

**三个必须做对的工程细节：**

1. **超时必须设，且要短**——精排在主链路的关键路径上，
   延迟直接叠加到用户等待时间。这里给 2 秒连接超时 + 5 秒请求超时；
2. **必须优雅降级**——精排服务挂了，检索服务必须照样能用。
   `fallback` 参数就是为此准备的；
3. **候选数必须限制**——Cross-Encoder 是 O(n) 次推理，
   n 从 20 涨到 200，延迟涨 10 倍。
   工业界公认的甜点区是 **top 50 召回 → top 5 精排**。

## 四、MMR：解决「Top-N 里全是同一件事」

### 4.1 公式

```
  MMR = argmax [ λ · Relevance(d) − (1 − λ) · max Sim(d, s) ]
          d∈R\S                              s∈S
```

直觉非常朴素：**每选一条，就惩罚掉和已选内容太像的候选。**

- `λ = 1`：退化成纯相关性排序；
- `λ = 0`：退化成纯多样性。

### 4.2 λ 怎么取

默认 0.7——因为**知识检索场景下相关性优先**：
用户来是找答案的，不是为了看百花齐放的观点。

但对「总结这个知识库」「这个主题有哪些说法」这类**探索性问题**，
应该把 λ 降到 0.5 左右。

### 4.3 一个隐蔽的实现 Bug（本章真实踩过）

初版代码里，计算"与已选项的最大相似度"时，
是靠**回 pool 里查下标**来取已选项的 token 集合的：

```java
for (int s = 0; s < selected.size(); s++) {
    int selectedOriginalIdx = indexOf(pool, selected.get(s));
    if (selectedOriginalIdx < 0) continue;   // ← 永远走这里
    maxSim = Math.max(maxSim, jaccard(...));
}
```

**但已选项在选中时就被从 pool 中移除了，回查必然返回 −1。**

结果就是**多样性惩罚恒为 0，MMR 悄悄退化成纯相关性排序**。

> 这是一类非常隐蔽的 bug：**程序照常运行、结果看起来也没错，
> 只是 MMR 完全没起作用。** 如果只看输出条数，你永远发现不了。

修复方式：单独维护 `selectedTokenSets`，在选中时把 token 集合一起移过去。

### 4.4 另一个编排错误：候选池被提前截断

初版 `RerankService` 是这样写的：

```java
List<RetrievedChunk> reranked = reranker.rerank(query, toRerank, topN);  // ← 截成 topN
return diversifier.diversify(reranked, topN);                            // ← 只能在 5 条里排
```

**问题**：MMR 只能在"已经定死的 topN 条"里重新排序。
那 5 条里若有 3 条是重复内容，MMR 再怎么打散也**变不出第 4 条新信息**。

Demo 实测，修复前 Top5 是：

```
1. doc-g  员工出差回来怎么报销…
2. doc-a  差旅报销总流程…
3. doc-c  发票要求（部门细则）…   ← 三份重复内容占了 3/5
4. doc-b  发票要求（制度原文）…
5. doc-d  发票要求（培训材料）…
```

修复后（精排保留 3 倍候选池，MMR 再挑 5 条）：

```
1. doc-g  员工出差回来怎么报销…
2. doc-c  发票要求（部门细则）…
3. doc-a  差旅报销总流程…
4. doc-h  境外发票：境外取得的票据需附翻译件…      ← 新增信息点
5. doc-f  发票遗失处理：如发票遗失，需提供…        ← 新增信息点
```

**两条重复内容被替换成了两个全新的信息点。**

> **正确的分工是**：精排负责「把最相关的排在前面」（保留较多候选），
> MMR 负责「从这批相关候选里挑出 topN 条彼此不重复的」。

## 五、为什么 MMR 必须放在精排之后

因为两者的**目标不同、输入要求也不同**：

- **精排**只看「这条与 query 有多相关」，对每条候选**独立打分**，
  看不到其它候选；它需要候选已按相关性粗排过；
- **MMR** 需要「每条候选之间的相似度」，是**全局的、迭代的**；
  它要求输入的 score 已经是**可信的相关性分数**，
  否则"用相关性减去冗余度"这个公式就失去意义。

**顺序反了，MMR 就是在给一堆噪声做去重。**

---

## 六、关于 topN 的"中间迷失"现象

`RerankService` 默认返回 5 条（约 1500 字），
这是塞进 Prompt 又不挤占生成空间的甜点区。

需要更多上下文时可以放宽到 10 条，但要警惕
**「中间迷失（Lost in the Middle）」**现象：

> 研究表明 LLM 对长上下文中**首尾**位置的信息利用最好，
> **中间部分容易被忽略**。

**塞得越多，不等于用得越好。** 这和第 8 章长度惩罚偏爱中等长度切片是同一个道理。

## 八、避坑指南

| 坑 | 后果 | 对策 |
| --- | --- | --- |
| 不做精排 | Top-K 混入大量弱相关片段，LLM 被噪声干扰 | 两阶段：召回 + 精排 |
| 精排候选数过大 | 延迟随候选数线性增长 | top 50 → top 5 |
| 精排无超时 | 一个慢请求挂住整个链路 | 连接 2s / 请求 5s |
| 精排失败导致整体失败 | 单点故障放大 | 优雅降级 + 告警 |
| MMR 候选池 = topN | MMR 无内容可替换，形同虚设 | 保留 2~3 倍候选池 |
| MMR 里回查已选项下标 | 惩罚恒为 0，MMR 静默失效 | 单独维护 selectedTokenSets |
| Top-N 塞太多 | 「中间迷失」，中间部分被 LLM 忽略 | 5~10 条为宜 |
| 无基线对比 | 无法证明优化有效 | 用 PassThroughReranker 做基线 |

## 九、面试题

**Q1：向量检索已经是语义检索了，为什么还要 Cross-Encoder 精排？**

> 因为向量检索用的是**双塔（Bi-Encoder）**结构：
> query 和 chunk 各自独立编码，两者从不交互，最后只算一个余弦。
> 这种结构让 chunk 向量可以离线预计算、可以建索引，
> 所以能支撑百万级检索——**但也正因如此，它无法捕捉 query 与 chunk 之间的细粒度交互**。
>
> Cross-Encoder 把两者拼在一起送进模型，让每一对 token 都能互相注意力，
> 精度高得多；代价是无法预计算、无法建索引。
>
> 所以两者不是替代关系，而是**分工**：
> 便宜的方法负责从百万里捞出几十条，贵的方法负责从几十条里挑出最好的几条。

**Q2：MMR 的 λ 该怎么调？**

> λ 控制"相关"与"多样"的权衡。
> 知识检索场景默认 0.7，**相关性优先**——用户是来找答案的。
>
> 但如果是"总结这个知识库""这个主题有哪些说法"这类**探索性问题**，
> 应该降到 0.5 左右，让更多不同角度的内容进来。
>
> 实际落地时建议做成**可配置参数**，并按问题类型路由。

**Q3：为什么 MMR 必须放在精排之后，不能之前？**

> MMR 的公式是「相关性 − 冗余度」，
> 它要求输入的 score 是**可信的相关性分数**。
>
> 如果放在精排之前，输入的是召回阶段的粗排分数（RRF 分或向量相似度），
> 这些分数的排序精度有限——**拿一堆不够准的分数去做去重，
> 等于在给噪声做多样性**。
>
> 所以正确顺序是：先精排拿到可信的相关性分数，再用 MMR 在此基础上打散冗余。

**Q4：精排服务挂了怎么办？**

> 优雅降级：自动退回到启发式精排或直通，
> 保证检索服务整体可用，只是质量下降。
>
> 关键是**必须同时做两件事**：
> 1. 降级要**被记录**（`lastFailures()`），
> 2. 降级要**触发告警**——否则它会悄悄变成永久状态，
>    你以为在用 Cross-Encoder，实际上已经降级半年了都不知道。

## 十、本章小结

- **召回与精排是两个目标不同的阶段**，用便宜方法覆盖、用昂贵方法精选。
- **双塔 vs Cross-Encoder** 的根本差异在于"query 与 chunk 是否交互"，
  这决定了前者可索引、后者更准。
- **Null Object（直通）既是基线也是降级方案**，没有基线的优化都是自嗨。
- **MMR 解决的是"重复内容挤占上下文预算"**，它让每一条结果都贡献新信息。
- **MMR 的候选池必须大于 topN**，否则它无内容可替换。
- **精排必须设超时 + 优雅降级**，它在主链路的关键路径上。
