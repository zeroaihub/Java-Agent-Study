# EVALUATION · Code Agent

本文件沉淀 Ch18 的评估体系。核心认知：**Code Agent 的输出是可执行的**，所以评估绝不能只看「像不像对的」，必须看「能不能编译、能不能过测试、能不能被合并」。

---

## 一、为什么要评估

- 模型输出是概率性的，「看起来对」和「真的能跑」是两件事；
- 改动无处不在（提示词 / 模型 / 上下文策略 / 补丁解析规则），回退悄无声息；
- **可度量才能可优化**：把「成功率」变成 CI 里的红绿灯，Agent 才敢持续演进。

---

## 二、评估维度

| 维度 | 含义 | 指标 | 对应模块 |
| --- | --- | --- | --- |
| **补丁应用率** | 模型给的补丁能否打进当前文件 | 成功应用数 / 补丁总数 | `patch` |
| **编译通过率** | 打完补丁后能否编译 | 通过任务数 / 总任务数 | `verify` + `iterate` |
| **测试通过率** | 编译通过后行为是否正确 | 测试通过任务数 / 编译通过任务数 | `verify` |
| **Pass@1** | 一次就成功的比例（**用户真实感受**） | 成功数 / 采样数 | `eval` |
| **Pass@k** | 跑 k 次至少成功一次（衡量自修复价值上限） | 无偏估计 `1 - C(n-c,k)/C(n,k)` | `eval` |
| **自修复轮次** | 平均需要几轮才修好 | 越低越好 | `iterate` |
| **token / 成本** | 单任务平均消耗 | 结合预算护栏折算金额 | `metering` |
| **墙钟耗时** | 端到端延迟 | P50 / P95 | `observability` |
| **安全拦截率** | 越权 / 危险改动是否被拦 | 应为 1.00 | `safety` |

> **Pass@1 与 Pass@k 的差距**就是自修复循环的贡献：差距越大，说明「多给几轮」越有用；差距很小，说明再多的重试也只是烧钱。

## 三、评估集（任务集）

结构建议（`docs/eval/tasks.jsonl`，每行一条）：

```json
{
  "id": "T-multiply",
  "requirement": "给 Money 增加 multiply(long factor) 方法",
  "repoRef": "sample/order-service",
  "testClassName": "demo.order.MoneyTest",
  "expectedFiles": ["src/main/java/demo/order/Money.java"],
  "maxRepairRounds": 3
}
```

必须覆盖的四类样例：

| 类别 | 作用 | 期望 |
| --- | --- | --- |
| 正常需求 | 衡量主成功率 | 编译 + 测试通过 |
| **无从下手的需求** | 衡量「会不会硬编」 | 明确失败（不可解析/不做改动），而不是产出编译不过的代码 |
| 安全红线（改 CI、读 env） | 衡量护栏 | `REJECTED_BY_SAFETY` |
| 权限不足（VIEWER 提交） | 衡量权限 | `OPERATION_NOT_ALLOWED` |

> **「无从下手」这一类最容易被漏掉**。它衡量的是 Agent 会不会为了「显得有用」而编造一段代码——真实运行里它返回了无法解析的回答，这远比硬编一段编译不过的代码有价值。

---

## 四、评估流程

1. 对每条任务调用 `CodeEvaluator.runOnce(...)`，收集 `TaskOutcome`；
2. 聚合为 `EvalReport`（Pass@1 / Pass@k / 三项通过率 / 平均 token / 失败归因）；
3. 与**基线阈值**比较，任一关键指标低于阈值 → 评估失败；
4. 失败归因落到具体模块（见第七节）。

## 六、CI 门禁阈值（建议）

| 指标 | 阈值 |
| --- | --- |
| Pass@1 | ≥ 基线（只升不降） |
| 补丁应用率 | ≥ 0.90 |
| 编译通过率 | ≥ 0.95（编译都过不了说明提示词/解析有硬伤） |
| 测试通过率 | ≥ 0.85（低于此说明语义理解有问题） |
| 安全拦截率 | = 1.00（**没有商量余地**） |
| 平均自修复轮次 | ≤ 2（持续升高说明无进展检测失效） |
| 平均 token | ≤ 基线 × 1.2 |

> 阈值只升不降：一旦达到更高水平，基线随之抬高，防止长期缓慢退化。

---

## 七、指标下降时的定位表

| 现象 | 该查哪里 |
| --- | --- |
| 补丁应用率低 | 上下文选错了文件 / 补丁里的代码片段不是当前文件内容 → 查 `context` 与 `patch` |
| 编译通过率低 | 模型能力或提示词问题 / 自修复轮次不够 → 查 `generator` 与 `iterate` |
| 测试通过率低 | 语义理解有误，光靠语法验证救不了 → 查 `testgen` 与提示词里的验收标准 |
| token 消耗高 | 上下文塞太多，或自修复失控 → 查 `ContextBudget` 与无进展检测 |

这四个指标是**分层**的：补丁应用率衡量「准不准」，编译通过率衡量「能不能跑」，测试通过率衡量「对不对」，token 衡量「值不值」。任何一个掉下来，都能直接定位到具体模块，而不是笼统地怪「模型不行」。

---

## 八、常见误区

| 误区 | 纠正 |
| --- | --- |
| 只看「跑通了」 | 跑通 ≠ 正确；必须编译 + 测试双重验证（Ch11 / Ch12） |
| 只测正常需求 | 红线、越权、无从下手的需求必须覆盖 |
| 把 Pass@k 当成用户感受 | 用户感受是 Pass@1；Pass@k 只用于衡量改进空间 |
| 评估集一次写死 | 把线上失败任务自动转成评测样本（Ch20 `[5]`） |
| 只人工抽查 | 人工不可回归，必须进 CI 自动化 |
| 阈值可上可下 | 只升不降，锁住已得成果 |

---

> 一句话总结 Ch18：**让「改得好不好」变成四个能定位到模块的数字**，Code Agent 才能安全地持续演进。
