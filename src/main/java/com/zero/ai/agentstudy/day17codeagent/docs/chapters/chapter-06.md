# Chapter 06 · 上下文工程：把有限的窗口花在刀刃上

> 本章目标：掌握上下文预算的分配与「全文 → 签名 → 丢弃」三级降级策略，理解为什么**必须为输出预留空间**，以及为什么「必选文件」要能覆盖打分结果。

---

## 一、为什么要学（Why）

有了 RepoMap（Ch05），我们知道了仓库长什么样。但真到拼提示词时，问题变成了：**窗口就这么大，到底放什么？**

三个真实的失败场景：

**场景一：塞满了输入，模型一个字都吐不出来。**
有人把上下文预算全部分给「输入代码」，觉得「多给点代码模型更懂」。结果输入占满了整个窗口，**输出预留为 0**，模型生成到一半就被截断——补丁只有一半，应用必然失败。这是最反直觉的一个坑：**给得太多反而什么都得不到。**

**场景二：按文件大小排序，选中的全是无关的长文件。**
「正文命中次数」这个信号有个天然偏差：**文件越长，命中次数越多**。不归一化，`OrderService` 这种长文件永远排第一，而真正该改的短文件被挤掉。

**场景三：改了 A 却没把依赖 A 的 B 放进来。**
模型改了 `Money` 的方法签名，却不知道 `OrderService` 在调用它——因为 `OrderService` 没进上下文。结果补丁应用成功、编译失败，白白浪费一轮。

## 二、是什么（What）

### 2.1 预算：先扣固定开销，剩下的才是代码的

```java
public record ContextBudget(
        int total,            // 模型总窗口
        int systemReserve,    // 系统提示词（角色 + 工具 + 输出契约）
        int outputReserve,    // 给模型输出的预留 —— 必须 > 0
        int historyReserve    // 多轮对话历史
) {
    public int availableForCode() {
        return total - systemReserve - outputReserve - historyReserve;
    }
}
```

两个构造期校验是刻意的（真实输出见 3.5）：

1. `outputReserve <= 0` → 直接拒绝：「不留会让上下文被输入占满，模型一个字都生成不出来」；
2. 固定开销之和 `>= total` → 直接拒绝：「没有空间留给代码」。

**预算必须在写代码之前算清楚，而不是等超了再截断。**

### 2.2 打分：四路加权

| 信号 | 权重 | 含义 |
| --- | --- | --- |
| 符号命中 | 6.0 | 需求里的词**正好**是某个符号名（强信号） |
| 符号模糊 | 2.4（6.0×0.4） | 符号名包含查询词 |
| 依赖联动 | 3.0 | 命中文件的**反向依赖者**一并带上 |
| 关键词 | 2.0 | 文件名匹配（×1.5）/ 正文命中（按长度归一化） |
| 路径提示 | 1.5 | 路径里包含查询词 |
| 用户必选 | +100 | 覆盖一切 |

「依赖联动」这一路是 Code Agent 特有的：写代码不是检索，**改 A 必须知道谁在用 A**。

### 2.3 装填：三级降级

```
按分数降序，逐个尝试装填：
  能放下全文  → FULL        （最理想）
  放不下      → 降级为 SIGNATURE（只放签名，来自 RepoMap）
  还放不下    → 丢弃，并记录到 dropped
```

降级还有一个**必须特判**的情况：非 Java 文件（比如 `README.md`）没有符号摘要，降级后的签名是**空字符串**。如果照样塞进上下文，等于白占一个位置，还让模型以为「这个文件是空的」。所以必须：

```java
String signature = repoMap.render(List.of(path));
if (signature.isBlank()) {
    // 非 Java 文件没有符号摘要，降级后是空内容。
    // 若照样塞进上下文，等于白占一个位置还让模型以为「这个文件是空的」。
    dropped.add(path);
    continue;
}
```

## 三、怎么用（How）

> 运行：`java -Dstdout.encoding=UTF-8 -cp target/classes com.zero.ai.agentstudy.day17codeagent.context.Chapter06Demo`

### 3.1 Token 估算：中文与英文不是一个价

```
=== [1] Token 估算器 ===
  英文 52 字符 → 15 token
  中文 16 字符 → 11 token
  分词：[请, 请在, 在, checkout, 下, 下单, 单, 单流, 流, 流程, 程, 程里, 里, 里支, 支, 支持, 持, vip, 折, 折扣, 扣]
```

中文一个字接近一个 token，英文大约 3.5 字符一个 token。所以**中文需求写长了很费 token**。分词用「ASCII 词 + 中文 uni/bi-gram」——中文二元组让「下单」「折扣」这类词能被匹配上。

### 3.2 预算充足：全放全文

```
=== [2] 32k 预算：能放全文 ===
  需求：我想给 OrderService 的 checkout 方法加上 VIP 折扣校验，Money 也要支持乘法
  SelectionResult{选中 4 个文件, 丢弃 0 个, 占用 597/23768 token (2.5%)}
    OrderService.java                              FULL         246 token  score=18.17  符号模糊:orderservice, 符号命中:checkout, 文件名匹配:orderservice, 正文命中 7 次, 路径提示:orderservice
    Money.java                                     FULL         191 token  score=10.07  符号模糊:money, 文件名匹配:money, 正文命中 10 次, 路径提示:money
    DiscountPolicy.java                            FULL         105 token  score=2.93  符号模糊:vip, 正文命中 5 次
    README.md                                      FULL          55 token  score=0.53  正文命中 3 次
    精确符号命中（可用于定位改动点）：
        method checkout @ src/main/java/demo/order/OrderService.java:16
    影响面文件：[OrderService.java, Money.java, DiscountPolicy.java]
```

注意 `score=18.17` 的构成被完整打印出来了——**打分必须可解释**。线上出现「选错了文件」的投诉时，你能立刻看出是哪一路信号出了问题。

### 3.3 预算不足：观察降级行为

```
=== [3] 极窄预算（可用于代码仅 380 token）：观察降级行为 ===
  ContextBudget{total=4096, system=3000, output=500, history=216, 可用于代码=380}
  SelectionResult{选中 3 个文件, 丢弃 1 个, 占用 372/380 token (97.9%)}
    OrderService.java                              FULL         246 token  score=18.17  ...
    Money.java                                     SIGNATURE     81 token  score=10.07  ...（预算不足，降级为签名）
    DiscountPolicy.java                            SIGNATURE     45 token  score=2.93  ...（预算不足，降级为签名）
    因预算不足丢弃：[README.md]
```

`OrderService` 分数最高，优先保住全文；`Money` / `DiscountPolicy` 降级为签名（模型至少知道有哪些方法）；`README.md` 因为非 Java 文件签名是空的，直接丢弃。

**97.9% 的利用率**——预算被榨干但没超支，这正是贪心装填的目标。

### 3.4 需求变了，选择随之改变

```
=== [4] 换个需求，选中文件随之改变 ===
  需求：DiscountPolicy 的 VIP_THRESHOLD 常量是多少，解释一下阶梯折扣
  SelectionResult{选中 3 个文件, 丢弃 0 个, 占用 406/23768 token (1.7%)}
    DiscountPolicy.java                            FULL         105 token  score=12.65  ...
    OrderService.java                              FULL         246 token  score=3.00  ...
    README.md                                      FULL          55 token  score=0.35  ...
```

同一个仓库，`DiscountPolicy` 从第 3 名（2.93）跃升到第 1 名（12.65）。**上下文选择必须随需求动态变化**，写死「永远带上这几个文件」的做法在真实仓库里必然失效。

### 3.5 必选文件：+100 覆盖打分

```
=== [5] 用户显式指定必须包含 README.md ===
    README.md [FULL, 55 token, score=100.35] 正文命中 2 次, 用户指定必须包含
```

用户说「照着 README 里的规范改」，那 README 就必须在上下文里——**哪怕模型打分算法认为它不重要**。`mustInclude` 用 +100 分覆盖一切，这是对「算法不能凌驾于用户意图」的兜底。

### 3.6 两类预算事故被拦在构造期

```
=== [6] 常见事故：不为输出预留空间 ===
  ✓ 被拦截：必须为模型输出预留空间：不留会让上下文被输入占满，模型一个字都生成不出来
  ✓ 被拦截：固定开销 7000 已超出总窗口 4096，没有空间留给代码
```

这两条校验把「模型吐不出东西」和「代码一个字都没进去」这两类诡异故障，消灭在了构造期。

## 四、真实项目中的应用

| 课程实现 | 生产替换 |
| --- | --- |
| 估算器（0.28/0.8 系数） | 用模型厂商的真实 tokenizer（tiktoken / QwenTokenizer） |
| 单轮选择 | 多轮：把历史补丁与编译错误放进 `historyReserve` |
| 全量 RepoMap | 大仓库只渲染「与需求相关的 N 个文件 + 目录树」 |
| 内存打分 | 缓存热门需求的选择结果 |

两个真实经验：

1. **输出预留要按「补丁最大可能长度」估算**，而不是拍脑袋 500。一个跨 3 个文件的大补丁可能要 3000 token。
2. **`dropped` 列表要告知模型**。「以下文件因预算未包含：`xxx`，如需查看请用 read_file」——让模型知道有这些文件存在，它会在需要时主动去读。

## 五、避坑与优化

### 坑 1：输出预留设为 0
**后果**：输入占满窗口，输出被截断，补丁只有一半，应用必然失败。
**做法**：`outputReserve > 0` 是构造期硬校验。

### 坑 2：正文命中次数不做长度归一化
**后果**：长文件天然分高，真正该改的短文件被挤掉。
**做法**：`occurrences / sqrt(body.length())`。

### 坑 3：非 Java 文件降级后塞空内容
**后果**：白占预算，且模型误以为「这个文件是空的」。
**做法**：`signature.isBlank()` 时直接 `dropped`。

### 坑 4：忘了带依赖方
**后果**：改了 A 的签名，B 编译失败，浪费一轮自修复。
**做法**：依赖联动 +3.0，把 `impactSet` 里的文件一并带上。

### 坑 5：用字符数当 token 数
**后果**：中文场景严重低估，实际超窗口。
**做法**：中文按 ≈1 token/字 估算，并**略微高估**（宁可少放一点）。

### 优化建议
- **打分理由必须打印**：线上排查「选错文件」全靠它。
- **必选文件机制要保留**：用户显式指定的文件永远优先于算法。

## 本章小结

- 预算 = 总窗口 −（系统 + **输出** + 历史），剩余才是代码空间；**输出预留必须 > 0**。
- 四路加权打分：符号命中 6.0 > 依赖联动 3.0 > 关键词 2.0 > 路径提示 1.5；用户必选 +100 覆盖一切。
- 装填三级降级：**FULL → SIGNATURE → 丢弃**；非 Java 文件降级为空时必须直接丢弃。
- 打分**可解释**（理由被打出来），选择**随需求动态变化**。
- 两类预算事故（不留输出、固定开销超窗口）被拦在构造期。
