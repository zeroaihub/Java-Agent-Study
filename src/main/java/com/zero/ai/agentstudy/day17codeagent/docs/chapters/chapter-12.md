# Chapter 12 · 测试验证：编译通过 ≠ 正确

> 本章目标：用一个真实反例证明编译验证的盲区，掌握在沙箱内运行测试并解析断言失败的方法，理解「编译 → 测试 → 评审」三道验证的分工。

---

## 一、为什么要学（Why）

Chapter 11 的编译验证能抓住语法错误，但它有一个**结构性盲区**：

> 编译器只检查「代码合法不合法」，不检查「代码做的是不是你要的事」。

来看这个真实反例：把 `Money.zero()` 的返回值从 `BigDecimal.ZERO` 改成 `BigDecimal.ONE`。

- 语法完全合法 ✓
- 类型完全正确 ✓
- 编译**照样通过** ✓
- 但 `zero()` 现在返回 1 而不是 0 ✗

**这类错误在生产上极其常见**：改错常量、改反了比较符号、`>=` 写成 `>`、复制粘贴改漏一处。它们全都能通过编译，只能由测试抓住。

所以 Code Agent 的验证必须是三道，缺一不可：

| 验证 | 抓什么 | 抓不到什么 |
| --- | --- | --- |
| **编译** | 语法、类型、引用 | 逻辑错误、边界条件 |
| **测试** | 行为是否符合预期 | 测试没覆盖的部分、代码质量 |
| **评审** | 反模式、安全红线、可读性 | 需要深度业务理解的问题 |

## 二、是什么（What）

### 2.1 在沙箱里跑测试

测试不是「调用一下方法」，而是**在沙箱内启动一个子进程**执行测试类：

```java
public TestExecutionResult runTest(Path classesDir, String testClassName) {
    // 必须显式带上编码参数：沙箱清空了宿主环境变量，子进程会回退到平台默认编码
    //（中文 Windows 上是 GBK），中文日志与断言消息会变成乱码，排查问题时非常痛苦。
    ExecResult result = sandbox.exec(new CommandRequest(
            "java",
            List.of("-ea", "-Dfile.encoding=UTF-8",
                    "-Dstdout.encoding=UTF-8", "-Dstderr.encoding=UTF-8",
                    "-cp", classesDir.toString(), testClassName),
            null, Duration.ofSeconds(60), 64 * 1024));
    ...
}
```

三个关键点：

1. **`-ea`（enable assertions）**：Java 的 `assert` 默认是关闭的。不加这个参数，**所有断言都不会执行，测试永远「通过」**——这是最危险的假绿灯。
2. **三个编码参数**：沙箱清空了环境变量（Ch10），子进程会回退到平台默认编码，中文断言消息会变成乱码。
3. **走沙箱**：测试代码是模型生成的，必须在沙箱里跑。

### 2.2 断言计数约定

课程里的测试类用 `assert` + `main` 实现，并约定每行打印 `PASS: xxx`：

```java
int total = countAssertions(output);      // 统计 "PASS:" / "FAIL:" 行数
int passedCount = passed ? total : Math.max(0, total - failures.size());
```

这个约定让「跑了多少断言、过了多少」可统计，而不只是「退出码 0」。

## 三、怎么用（How）

> 运行：`java -Dstdout.encoding=UTF-8 -cp target/classes com.zero.ai.agentstudy.day17codeagent.verify.Chapter12Demo`

### 3.1 编译主代码 + 测试代码

```
=== [1] 编译主代码 + 测试代码 ===
  CompilationResult{编译通过, files=5, errors=0, warnings=0, 522ms}
```

5 个文件 = 4 个主代码 + 1 个测试类。

### 3.2 运行测试（原实现）

```
=== [2] 运行测试（原实现）===
  TestSuiteResult{通过 1 / 1, 通过率 100.0%, 耗时 1809ms}
    demo.order.MoneyTest PASS (3/3 断言, 1809ms)
        PASS: zero() 返回 0
        PASS: add(100, 50) = 150
        PASS: 200 > 100
```

全绿。注意每条断言都有中文描述——**这直接决定了失败时模型能不能看懂**。

### 3.3 引入逻辑错误：编译照样通过

```
=== [3] 引入逻辑错误：Money.zero() 返回 1 而不是 0 ===
  PatchResult[OK src/main/java/demo/order/Money.java 匹配 1 处, 策略=EXACT]
  重新编译 → 编译通过（注意：编译照样通过！语法完全合法）
```

**这就是本章的核心证据**：一个彻头彻尾的逻辑错误，编译器一声不吭。

### 3.4 测试抓住了这个错误

```
=== [4] 再次运行测试：断言抓住了这个错误 ===
  TestSuiteResult{通过 0 / 1, 通过率 0.0%, 耗时 1101ms}
    demo.order.MoneyTest FAIL (0/0 断言, 1101ms)
    失败信息：
        Exception in thread "main" java.lang.AssertionError: zero() 应该等于 0
```

失败信息 `zero() 应该等于 0` 是**断言里手写的中文描述**。它的价值在于：

- 人一眼看懂；
- 模型一眼看懂——这份信息会直接喂回自修复循环。

对比一下如果断言不写描述会怎样：

```java
// ✗ 没有描述
assert money.equals(Money.ZERO);
// 失败信息：java.lang.AssertionError          ← 什么信息都没有

// ✓ 有描述
assert money.equals(Money.ZERO) : "zero() 应该等于 0";
// 失败信息：java.lang.AssertionError: zero() 应该等于 0   ← 可直接用于修复
```

**断言描述是自修复循环的输入质量来源**，写测试时务必带上。

### 3.5 小结

```
=== [5] 小结 ===
  编译验证拦不住逻辑错误，必须由测试来拦；
  所以 Code Agent 的验证闭环是：编译 → 测试 → 评审，三道缺一不可。
```

## 四、真实项目中的应用

| 课程实现 | 生产替换 |
| --- | --- |
| assert + main 测试类 | JUnit 5 + Maven Surefire |
| `PASS:` 行约定 | JUnit XML 报告解析 |
| 沙箱内 `java -ea` | 沙箱内 `mvn test -Dtest=Xxx` |
| 手写断言描述 | `assertThat(x).as("zero() 应该等于 0").isEqualTo(...)` |

一条生产铁律：**Agent 的改动必须有测试，而且测试要在改动之前就存在**。

- 如果仓库已有测试 → 直接跑，这是最好的回归保护；
- 如果没有测试 → 让 Agent 先生成（Ch16），再执行改动；
- 无论如何，**「改了代码但没跑任何测试」的 PR 不应被合并**。

## 五、避坑与优化

### 坑 1：忘了 `-ea`
**后果**：Java 断言默认关闭，**所有 assert 都不执行，测试永远通过**——最危险的假绿灯。
**做法**：显式 `-ea`；生产用 JUnit 则无此问题。

### 坑 2：子进程编码乱码
**后果**：沙箱清空环境后回退 GBK，中文断言消息变成 `zero() Ӧõ��� 0`，无法定位。
**做法**：`-Dfile.encoding=UTF-8 -Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8` 三个都加。

### 坑 3：断言不写描述
**后果**：失败信息只有一个 `AssertionError`，模型无法知道哪里错了，自修复无从下手。
**做法**：每条断言带业务语义描述。

### 坑 4：只看退出码不看断言数
**后果**：测试类一个断言都没跑（比如 `main` 里漏调用），退出码仍是 0，误判通过。
**做法**：统计断言数量，`total == 0` 视为异常。

### 坑 5：测试超时被当成失败
**后果**：死循环导致超时，却被解析成「断言失败」，模型去改根本不存在的逻辑错误。
**做法**：与 Ch10 一样，`timedOut` 单独判定并给出「可能存在死循环」的提示。

### 优化建议
- **先跑已有测试再改代码**：拿到「改动前的基线」，才能判断失败是不是本次改动引入的。
- **测试要快**：测试跑 18 秒（Demo 里 1809ms 主要是 JVM 启动）会严重拖慢自修复循环；生产应复用 JVM 或用测试守护进程。

## 本章小结

- **编译通过 ≠ 正确**：把 `zero()` 改成返回 1，编译器一声不吭，只有测试能抓住。
- 验证三道：编译（语法）→ 测试（行为）→ 评审（质量），缺一不可。
- 沙箱内跑测试必须带 `-ea`，否则 Java 断言不执行，**测试永远假绿**。
- 三个编码参数必加，否则沙箱清空环境后中文断言消息乱码。
- **断言必须带业务描述**：它直接决定自修复循环的输入质量。
- 测试超时（`timedOut`）要与断言失败分开判定，否则模型会去修一个不存在的错误。
