# Chapter 14 · 安全护栏：落盘前的最后一道闸

> 本章目标：建立「路径 / 敏感文件 / 删除体量 / 高危 API / 密钥」五类检查，理解 REJECT 与 WARN 的分级哲学，以及为什么**安全审查必须发生在应用补丁之前**。

---

## 一、为什么要学（Why）

回顾一下我们已经有的三层防护：

| 层 | 防什么 | 章节 |
| --- | --- | --- |
| 租户 / 角色 | 越权用户提交任务 | Ch01 |
| 路径（VFS） | 写到仓库外 | Ch03 |
| 命令（沙箱） | 执行危险命令 | Ch10 |

还缺一层：**内容层面的危险改动**。因为模型完全可能合法地写出这样的补丁：

```
File: .github/workflows/ci.yml        ← 改 CI 配置
File: .env                            ← 改密钥文件
File: src/main/java/.../Money.java    ← 一次删掉 260 行
File: src/main/java/.../AiConfig.java ← 里面写着 apiKey = "sk-proj-..."
```

这些改动在「路径合法性」「语法正确性」上统统没问题——**只有内容审查能抓住**。

还有一个关键的顺序问题：**安全审查必须在应用补丁之前**。如果先打补丁再审查，那么被拒的补丁已经在磁盘上留下了半成品，还得回滚；而放在前面，被拒的补丁**不会浪费任何编译与测试资源，也不会留下任何痕迹**。

---

## 二、是什么（What）

### 2.1 五类检查

| 检查 | 命中结果 | 理由 |
| --- | --- | --- |
| **路径黑名单** | `REJECT` | CI、密钥文件不该由 Agent 碰 |
| **敏感文件** | `WARN` | 构建配置需要人工复核，但不是不能改 |
| **删除体量** | `REJECT` | 一次删几百行通常是理解错误或幻觉 |
| **高危 API** | `WARN` | 执行系统命令 / 读环境变量 / 网络访问 / 反射 |
| **密钥扫描** | 记录 + 告警 | 模型可能写出真实格式的密钥 |

### 2.2 为什么要分 REJECT 与 WARN

这是本节最重要的设计哲学：

| 判定 | 含义 | 后果 |
| --- | --- | --- |
| `REJECT` | **确定是错的** | 阻止，不留商量余地 |
| `WARN` | **可能是对的，但需要人看一眼** | 继续，但在 PR 里标注 |

如果把所有可疑项都设成 `REJECT`，Agent 会被大量合理需求卡死（比如「帮我把日志改成结构化输出」确实要用日志 API）；如果都设成 `WARN`，真正的危险就混过去了。

**判据是：能不能想象出一个合理的业务场景需要它。**
- 改 CI 配置？想象不出来 → `REJECT`
- 改 pom.xml 加依赖？完全合理 → `WARN`
- 用 `System.getenv()` 读配置？合理但需复核 → `WARN`

## 三、怎么用（How）

> 运行：`java -Dstdout.encoding=UTF-8 -cp target/classes com.zero.ai.agentstudy.day17codeagent.safety.Chapter14Demo`

### 3.1 路径黑名单 → REJECT

```
=== [1] 路径黑名单：CI 配置 ===
  [REJECT] .github/workflows/ci.yml
        理由：禁止修改受保护路径：.github/workflows/ci.yml
        建议：CI 配置与密钥文件不允许由 Agent 修改，请提交人工处理
  [REJECT] .env
        理由：禁止修改受保护路径：.env
        建议：CI 配置与密钥文件不允许由 Agent 修改，请提交人工处理
```

一个真实的风险场景：Agent 被要求「让 CI 跑得更快」，它可能会去改 CI 配置**跳过测试步骤**。这类改动即使是人做的也要走审批，何况是模型。

### 3.2 敏感文件 → WARN

```
=== [2] 敏感文件：构建配置 (WARN 而非 REJECT) ===
  [WARN] pom.xml
        理由：修改了敏感文件：pom.xml
        建议：此项变更需要人工重点复核（构建配置变更会影响整个工程的依赖）
```

注意代码里的一个细节：**黑名单优先于敏感名单**：

```java
for (String sensitive : SENSITIVE_PATHS) {
    if (verdict != Verdict.REJECT && (path.startsWith(sensitive) || path.endsWith(sensitive))) {
        ...
        verdict = Verdict.WARN;
    }
}
```

`verdict != REJECT` 这个条件保证「已经被判 REJECT 的不会被降级成 WARN」——**判定只能变严，不能变松**。

### 3.3 删除体量 → REJECT

```
=== [3] 体量失控：一次删上百行 ===
  [REJECT] src/main/java/demo/order/Money.java
        理由：删除行数 260 超过上限 200
        建议：请拆分为多个更小的补丁，或确认删除确实是需求的一部分
```

为什么限制删除而不是新增？因为**删除是破坏性的**：新增的代码可以再删，删掉的代码如果没有版本控制就找不回来了。而一次删几百行，通常是模型理解错了（比如以为整个类都不用了）。

### 3.4 高危 API → WARN

```
=== [4] 危险 API ===
  [WARN] src/main/java/demo/order/OrderService.java
        理由：新增代码使用了高危 API：执行系统命令
        建议：如确有必要，请在评审时说明理由；否则应改用受控的替代方案
  [WARN] src/main/java/demo/order/OrderService.java
        理由：新增代码使用了高危 API：读取环境变量
        建议：如确有必要，请在评审时说明理由；否则应改用受控的替代方案
```

检查**只看新增内容**（`patch.replace()`）：

```java
String addedText = patch.replace() == null ? "" : patch.replace();
for (Map.Entry<String, Pattern> api : DANGEROUS_API.entrySet()) {
    if (api.getValue().matcher(addedText).find()) {
        ...
    }
}
```

与 Ch15 的评审一样——**只审查增量**。如果连被删掉的旧代码里的 `Runtime.exec` 也报一遍，告警会淹没人。

### 3.5 正常改动必须放行

```
=== [5] 正常业务改动应当放行 ===
  [PASS] src/main/java/demo/order/Money.java
```

**这一条和前面五条同样重要**。如果规则误报太高，团队会开始忽略告警，护栏就形同虚设。Demo 里专门验证了「干净补丁零告警」。

### 3.6 密钥扫描 + 强制脱敏

```
=== [6] 密钥泄露扫描 ===
  OpenAI API Key @ src/main/java/demo/order/AiConfig.java:2 → sk-p************
  AWS Access Key @ src/main/java/demo/order/AiConfig.java:3 → AKIA************
  JDBC 密码 @ src/main/java/demo/order/AiConfig.java:5 → jdbc************
  脱敏演示：raw = sk-proj-AbCdEfGhIjKlMnOpQrStUvWx → sk-p************
  → 日志里绝不能打印原文明文，否则等于把刚拦下的密钥又泄露一遍
  干净代码命中数 = 0（用环境变量注入才是正确姿势）
```

**「脱敏」这一条是安全模块的自我约束**：如果扫描器发现密钥后把原文打进日志，那等于「刚拦下的密钥又泄露了一遍」——而且日志往往比代码传播得更广。

7 条密钥规则：OpenAI `sk-`、AWS `AKIA`、GitHub `gh[pousr]_`、Slack `xox[baprs]-`、私钥头、通用密码赋值、JDBC 密码。

## 四、真实项目中的应用

| 课程实现 | 生产替换 |
| --- | --- |
| 静态规则集 | 规则进配置中心，支持按租户 / 按仓库定制 |
| 正则密钥扫描 | 加熵值检测（可抓住非标准格式密钥）+ 已知密钥库比对 |
| `WARN` 只记录 | `WARN` 要进 PR 的「需要关注」区块（Ch17） |
| 只查补丁内容 | 加上「全仓库定期扫描」 |

三条生产经验：

1. **规则要能灰度**。新规则先设 `WARN` 观察误报率，稳定后再升 `REJECT`。直接上 `REJECT` 误伤正常改动会迅速失去信任。
2. **被拒记录要留存**。谁、什么时候、想改哪个文件被拒了——这是审计材料，也能反映有没有人在尝试诱导 Agent。
3. **密钥扫描要双向**：既扫「Agent 写进去的」，也扫「上下文里读出来的」。如果仓库里本来就有硬编码密钥，把它塞进上下文等于传给模型服务商。

## 五、避坑与优化

### 坑 1：安全审查放在应用补丁之后
**后果**：磁盘上留下半成品，且浪费了编译与测试资源。
**做法**：审查在 `PatchApplier` **之前**（Ch20 流水线第 5 步就是这么排的）。

### 坑 2：所有可疑项都设 REJECT
**后果**：合理需求被卡死，团队开始想办法绕过护栏。
**做法**：按「能否想象出合理业务场景」区分 REJECT / WARN。

### 坑 3：判定可以被降级
**后果**：已被 REJECT 的路径又被敏感名单改成 WARN，护栏被绕过。
**做法**：`verdict != REJECT` 守卫，**判定只能变严**。

### 坑 4：审查全量代码
**后果**：历史遗留问题一次性倾泻，告警淹没，没人看。
**做法**：只看 `patch.replace()` 新增内容。

### 坑 5：扫描结果打印原文
**后果**：把刚拦下的密钥打进日志，二次泄露。
**做法**：强制脱敏（前 4 字符 + 星号）。

### 优化建议
- **规则清单要可导出**：Demo 的 `[7]` 打印了禁止路径 / 高危 API / 密钥规则三张清单——它们同时也是给使用者的文档。
- **误报率要监控**：把「被 WARN 但人工判定无问题」的比例做成指标，超过阈值就调规则。

## 本章小结

- 四层防护之外还需**内容层**审查：路径黑名单、敏感文件、删除体量、高危 API、密钥。
- **`REJECT` vs `WARN` 的判据是「能否想象出合理的业务场景」**；判定只能变严不能变松。
- **安全审查必须在应用补丁之前**：被拒的补丁不浪费任何编译测试资源，也不留半成品。
- 只审查**新增内容**（`patch.replace()`），否则告警淹没。
- 密钥扫描必须**强制脱敏**——日志里打印原文等于二次泄露。
- 规则要灰度上线、误报率要监控，否则护栏会失去信任。
