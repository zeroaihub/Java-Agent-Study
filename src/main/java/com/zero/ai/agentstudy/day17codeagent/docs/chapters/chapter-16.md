# Chapter 16 · 测试生成：把「顺便写测试」变成可控工序

> 本章目标：依据签名自动生成测试计划与可执行测试类，打通「编译 → 运行 → 红绿循环」管道；并诚实说明占位断言的价值与边界。

---

## 一、为什么要学（Why）

Chapter 12 证明了「没有测试就抓不住逻辑错误」。但真实仓库里大量代码**本来就没有测试**。于是很自然的一个想法是：

> 「让模型顺便把测试也写了吧。」

这个想法在实践中会翻车，原因是：**模型在写业务代码的同时写测试，两边都写不好**——它往往把测试写成对实现的复述（实现错了，测试也跟着错），或者直接生成一堆编译不过的测试代码。

正确的做法是把它拆成**两道独立工序**：

1. **先生成测试**（基于签名，不依赖实现细节）；
2. **再改业务代码**，然后跑测试。

这样测试才是「独立的一方」，才能真正起到验证作用。

另一个动机是**可控性**：让模型自由发挥写测试，你会得到各种风格、各种框架、各种编译不过的代码；而按签名生成，你能保证它编译得过、跑得起来、结果可统计。

## 二、是什么（What）

### 2.1 测试计划

```java
public record TestPlan(
        String testClassName,
        String packageName,
        String targetClass,
        List<Case> cases
) {
    public record Case(
            JavaSymbol targetSymbol,
            String name,
            String description,
            Kind kind
    ) { }

    public enum Kind {
        HAPPY_PATH("正常路径"),
        BOUNDARY("边界条件"),
        EXCEPTION("异常路径");
    }
}
```

生成规则：

| 用例类型 | 触发条件 | 例子 |
| --- | --- | --- |
| `HAPPY_PATH` | 每个 public 方法 | `testOf`、`testAdd` |
| `BOUNDARY` | 方法含数值参数 | `testOfBoundary`（0 / 极小值） |
| `EXCEPTION` | 构造器带参 | `testInvalidInput`（入参非法应抛明确异常） |

跳过 `toString` / `hashCode` / `equals`——给它们生成测试纯属噪音。

### 2.2 渲染成可执行测试类

生成的测试类用 `assert` + `main` 实现（不依赖 JUnit 运行时，保证零依赖可跑）：

```java
public static void main(String[] args) {
    testOf();
    testOfBoundary();
    ...
    System.out.println("ALL DONE");
}
```

每条用例打印 `PASS: <name>`——这是 Ch12 统计断言数的约定。

## 三、怎么用（How）

> 运行：`java -Dstdout.encoding=UTF-8 -cp target/classes com.zero.ai.agentstudy.day17codeagent.testgen.Chapter16Demo`

### 3.1 依据签名生成测试计划

```
=== [1] 依据 Money 的签名生成测试计划 ===
  TestPlan{MoneyTest, 被测=Money, 用例 7 个，覆盖方法 [of, zero, add, greaterThan, amount, (unknown)]}
    testOf                       正常路径       验证 Money of(long) 的正常路径
    testOfBoundary               边界条件       验证 of 在边界值（0 / 极小值）下的行为
    testZero                     正常路径       验证 Money zero() 的正常路径
    testAdd                      正常路径       验证 Money add(Money) 的正常路径
    testGreaterThan              正常路径       验证 boolean greaterThan(Money) 的正常路径
    testAmount                   正常路径       验证 BigDecimal amount() 的正常路径
    testInvalidInput             异常路径       入参非法时应当抛出明确异常
  覆盖率摘要 = {用例总数=7, 覆盖方法数=6, 边界用例=1, 异常用例=1}
```

复用的是 Ch05 的 `LightweightJavaParser`——**同一个符号表，既服务于上下文选择，也服务于测试生成**。这就是模块划分的收益：一份解析结果多处复用。

### 3.2 渲染并编译

```
=== [3] 编译（含生成的测试）===
  CompilationResult{编译通过, files=5, errors=0, warnings=0, 465ms}
```

5 个文件 = 4 主代码 + 1 生成的测试类。

### 3.3 在沙箱里运行

```
=== [4] 在沙箱里运行生成的测试 ===
  TestSuiteResult{通过 1 / 1, 通过率 100.0%, 耗时 1781ms}
    demo.order.MoneyTest PASS (7/7 断言, 1781ms)
        PASS: testOf
        PASS: testOfBoundary
        PASS: testZero
        PASS: testAdd
        PASS: testGreaterThan
        PASS: testAmount
        PASS: testInvalidInput
        ALL DONE
```

7/7 全过——注意这里跑的是**沙箱内的真实子进程**（Ch10），断言真的被执行了（`-ea`，Ch12）。

### 3.4 诚实交代：占位断言

```
=== [5] 诚实交代：占位断言的价值与边界 ===
  这批断言写的是 assert true，所以永远会通过。
  它的真正价值在于：『编译 + 运行 + 红绿循环』这条管道已经打通，
  只要把第 2 步的渲染替换成 LLM 生成的真实断言，这条管道就直接可用。
  生成的测试失败时会自动进自修复循环，人只需要最终审阅。
  若不做这一步，『让模型顺便写测试』往往演变成一堆编译不过的测试代码。
```

这一段必须说清楚，否则就是在自欺欺人：

| 层面 | 状态 |
| --- | --- |
| 管道（生成 → 编译 → 沙箱运行 → 统计断言 → 进自修复） | **真实可用** |
| 断言语义（`assert true`） | **占位，永远通过** |

**价值在于管道。**把 `render()` 换成 LLM 生成真实断言，管道立刻就能用；而不先做这一步，「让模型顺便写测试」往往演变成一堆编译不过的测试代码——连管道都跑不通。

这也是本课程一贯的方法论：**先用便宜的实现跑通全链路因果，再逐个换成昂贵的真实实现**（Ch02 已说明）。

## 四、真实项目中的应用

| 课程实现 | 生产替换 |
| --- | --- |
| `assert` + `main` | JUnit 5 + AssertJ + Surefire |
| 占位断言 | LLM 生成真实断言（输入：方法签名 + 业务语义 + 已有测试风格） |
| 基于签名的计划 | 加上分支覆盖分析（JaCoCo）定位未覆盖分支 |
| 7/7 全绿即结束 | 变异测试（PIT）验证测试是否真的能抓住错误 |

三个生产经验：

1. **测试必须独立于实现生成**。如果测试读的是实现代码，它会把实现的 bug 一起复制过去。基于**签名 + 业务描述**生成才能保证独立性。
2. **生成的测试同样要进评审**。否则 Agent 会用「写一堆永远通过的测试」来假装自己完成了任务——这是一个真实的对齐风险。
3. **测试要快**。Demo 里 1781ms 主要是 JVM 启动开销；自修复循环里每轮都要跑，必须想办法摊薄（守护进程 / 测试选择）。

## 五、避坑与优化

### 坑 1：让模型在写业务代码时「顺便」写测试
**后果**：测试成为实现的复述，实现错了测试也跟着错，双重失效。
**做法**：拆成两道工序，测试先于或独立于实现生成。

### 坑 2：盲目相信「测试全绿」
**后果**：占位断言永远通过，Agent 用「N/N 通过」假装完成。
**做法**：诚实标注占位状态；生产用变异测试验证测试的有效性。

### 坑 3：给 `toString`/`hashCode`/`equals` 生成测试
**后果**：纯噪音，降低评审意愿。
**做法**：跳过通用方法。

### 坑 4：生成的测试不进评审
**后果**：测试代码本身的质量无人把关。
**做法**：测试同样过 Ch15 的规则评审。

### 坑 5：测试太慢
**后果**：自修复循环每轮都要跑，拖垮整体耗时。
**做法**：只跑受影响测试、复用 JVM、并行执行。

### 优化建议
- **覆盖率摘要要输出**：`{用例总数=7, 覆盖方法数=6, 边界用例=1, 异常用例=1}` 让「测了多少」可度量。
- **测试计划先给人看**：人可以删掉无意义的用例，比事后改生成结果便宜。

## 本章小结

- 测试生成必须成为**独立工序**，不能是「顺便写点」——否则测试会变成实现的复述。
- 计划由**签名**驱动（复用 Ch05 解析器）：正常路径 + 边界（数值参数）+ 异常（构造器带参）。
- 渲染成 `assert` + `main` 测试类，约定打印 `PASS: <name>` 供统计。
- 生成的测试在**沙箱内真实运行**（`-ea`），7/7 通过——管道打通。
- **诚实边界**：断言是 `assert true` 占位，价值在于「编译 + 运行 + 红绿循环」管道已通；换成 LLM 真实断言即可直接用。
- 生产要补：JUnit 5、真实断言、变异测试、测试评审。
