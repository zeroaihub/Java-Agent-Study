# Chapter 17 · GitOps：变更集、风险分级与 PR 草稿

> 本章目标：把「改了什么」自动化成可审阅的变更集与风险分级，产出一份「能直接提上去」的 PR 草稿；并理解为什么**编译失败的 PR 必须自带不可合并标记**。

---

## 一、为什么要学（Why）

到 Chapter 16，Agent 已经能改代码、能验证、能自修了。但交付给人时，最常见的失败是：

> PR 描述里只有一句「已修复」。

 reviewer 完全不知道：改了哪些文件？为什么改？验证了吗？有什么需要重点看的？于是要么逐行读 diff（慢），要么直接关掉（Agent 白干一场）。

还有两个更具体的问题：

**问题一：用「修改时间」判定改动会产出噪声。**
文件系统会把「被读取过」「被 touch 过」的文件也算作改动，于是 PR 里出现一堆 `+0 / -0` 的条目，淹没真正的变化。正确做法是**按内容差异**判定——这正是 Ch03 快照指纹的用途。

**问题二：「这个 PR 该找谁审」靠拍脑袋。**
改 README 和改支付核心逻辑，需要的 review 强度完全不同。风险必须**可计算**，才能路由给不同级别的 reviewer。

## 二、是什么（What）

### 2.1 变更集（Content-based）

```java
public static ChangeBundle from(RepoSnapshot before, RepoSnapshot after) {
    // 用快照 diff（内容比对），而不是修改时间
    ...
}
```

`ChangeBundle` 记录每个文件的：变更类型（新增/修改/删除/重命名）、增删行数、风险等级、说明。

### 2.2 风险分级规则

```java
public RiskLevel risk() {
    int scale = changedLines();
    boolean core = path.contains("src/main/java") && !path.contains("test");
    if (scale == 0) return RiskLevel.NONE;
    if (core && scale >= 60) return RiskLevel.HIGH;   // 核心源码 + 大改动
    if (scale >= 20 || core) return RiskLevel.MEDIUM; // 大改动，或动到核心
    return RiskLevel.LOW;
}
```

| 风险 | 条件 | 例子 |
| --- | --- | --- |
| 高 | 核心源码 且 ≥60 行 | `OrderService.java` +80/-20 |
| 中 | ≥20 行 或 动到核心 | `Money.java` +8/-2 |
| 低 | 其他 | `README.md` +3/-1 |
| 无 | 零改动 | — |

**两个维度相乘**：改动体量 × 是否核心。这与人的直觉一致——改 60 行文档没事，改 60 行支付逻辑就是大事。

### 2.3 PR 草稿结构

| 区块 | 内容 |
| --- | --- |
| 标题 | `[类型] 需求摘要` |
| 变更动机 | 需求原文 |
| 变更明细 | 表格：文件 / 类型 / 增删 / 风险 |
| 验证情况 | 编译是否通过、测试通过数、评审计数 |
| 需要关注 | 编译失败 / BLOCKER / 触及核心 / 高风险 |
| 标签 | `code-agent`、`auto-generated`、`risk-*`、`do-not-merge` |

## 三、怎么用（How）

> 运行：`java -Dstdout.encoding=UTF-8 -cp target/classes com.zero.ai.agentstudy.day17codeagent.gitops.Chapter17Demo`

### 3.1 应用补丁 → 变更集

```
=== [2] 变更集 ===
  ChangeBundle{文件 2 个, +10 -0, 整体风险=中}
    修改   src/main/java/demo/order/Money.java                  +4    -0    [中]
    修改   src/test/java/demo/order/MoneyTest.java              +6    -0    [低]

  关键：没有任何内容变化的 4 个原文件不出现在变更集里。
  → 若用「修改时间」判定改动，这里会多出一堆 +0/-0 的噪声条目。
```

**这一句对照是本节的重点**：仓库里有 6 个文件，只有 2 个真的变了，另外 4 个虽然被操作过但内容没变——它们**不出现在变更集里**。

> 顺带一个实用提醒：Demo 里 `MoneyTest.java` 是**预先创建**的（只有 `package demo.order;` 一行）。因为 SEARCH/REPLACE 无法凭空创建文件——**新建文件应该用 `write_file` 工具**（Ch04），补丁只适合修改已有文件。

### 3.2 生成 PR 草稿

```
=== [4] 生成 PR 草稿 ===
# [重构] Money 需要支持乘法运算，并补充对应单元测试

> 修改 2 个文件（+10 / -0 行），整体风险 中。

## 变更动机
Money 需要支持乘法运算，并补充对应单元测试

## 变更明细
| 文件 | 类型 | 增删 | 风险 |
|---|---|---|---|
| `src/main/java/demo/order/Money.java` | 修改 | +4 / -0 | 中 |
| `src/test/java/demo/order/MoneyTest.java` | 修改 | +6 / -0 | 低 |

## 验证情况
- 编译验证：✅ 通过
- 测试验证：MoneyTest 1/1 通过

## 需要关注
- 改动触及核心源码，建议由该模块的负责人复核

## 标签
`code-agent` `auto-generated` `risk-medium`

---
_本 PR 由 Code Agent 自动生成，请重点核对上述「需要关注」部分。_
```

四个区块各有明确用途：**明细**让人快速了解范围；**验证**让人知道跑过什么；**关注**把注意力导向真正有风险的地方；**标签**让 CI / 路由规则可以自动化处理。

### 3.3 编译失败 → 必须自带不可合并标记

```
=== [5] 编译失败时，PR 必须自带不可合并标记 ===
  标签 = [code-agent, auto-generated, risk-medium, do-not-merge]
  需要关注：
    - 编译未通过，**请勿合并**
    - 改动触及核心源码，建议由该模块的负责人复核
```

```java
if (!compiled) {
    concerns.add("编译未通过，**请勿合并**");
    labels.add("do-not-merge");
}
```

**这一条是硬性要求**。为什么编译失败了还要生成 PR？因为：

1. 让人能看到 Agent 做了什么、卡在哪（有价值的调试信息）；
2. 有些场景人想接着手工修。

但**必须打上 `do-not-merge`**，否则一个编译不过的 PR 混进队列被误合并就是事故。

### 3.4 风险分级：把「该找谁审」变成规则

```
=== [6] 风险分级：核心目录 + 大改动 = 高风险 ===
    修改   README.md                                            +3    -1    [低]
    修改   src/main/java/demo/order/Money.java                  +8    -2    [中]
    修改   src/main/java/demo/order/OrderService.java           +80   -20   [高]
  → 风险等级把「这个 PR 该找谁审」从拍脑袋变成可自动化规则
```

有了风险等级，路由规则可以这样写：

| 风险 | 路由 |
| --- | --- |
| 低 | 单人快速审，甚至自动合并（如果测试全绿） |
| 中 | 模块负责人审 |
| 高 | 负责人 + 架构组双人审 |

## 四、真实项目中的应用

| 课程实现 | 生产替换 |
| --- | --- |
| `ChangeBundle` 内存计算 | JGit 真实分支 diff |
| PR 草稿 Markdown | 调用 GitHub / GitLab API 真实创建 PR |
| 标签写死 | 按仓库配的标签体系 + CODEOWNERS 自动指派 reviewer |
| 风险两级维度 | 加上「历史故障率」「测试覆盖率变化」等维度 |

三个生产经验：

1. **PR 描述要「能独立阅读」**。reviewer 往往不会去看任务上下文，PR 本身就是全部信息。
2. **`do-not-merge` 标签要接入 CI 门禁**，而不只是视觉提醒——人眼会漏，CI 不会。
3. **风险分级要能人工覆盖**。规则算出来是「中」，但 reviewer 知道这个文件下周要重构，那它就是「高」。

## 五、避坑与优化

### 坑 1：用修改时间判定改动
**后果**：一堆 `+0/-0` 噪声条目淹没真正的变化。
**做法**：内容快照 diff（Ch03 指纹）。

### 坑 2：想用 SEARCH/REPLACE 创建新文件
**后果**：文件不存在，SEARCH 匹配不到，补丁失败。
**做法**：新建文件用 `write_file` 工具；补丁只改已有文件。

### 坑 3：编译失败也生成「看起来正常」的 PR
**后果**：误合并编译不过的代码。
**做法**：`do-not-marge` 标签 + 「请勿合并」置顶关注项。

### 坑 4：PR 里没有验证信息
**后果**：reviewer 不知道跑过什么，只能自己重跑一遍。
**做法**：编译 / 测试 / 评审计数全部写进「验证情况」。

### 坑 5：风险分级只有体量一个维度
**后果**：改 60 行文档和改 60 行支付核心被评为同等级。
**做法**：体量 × 是否核心，两个维度相乘。

### 优化建议
- **变更集要按风险排序**：reviewer 从上往下看，先看到最危险的。
- **「需要关注」要少而准**：列 10 条等于没列；只留真正需要人判断的。

---

## 本章小结

- 变更集必须**按内容差异**计算，不能用修改时间——否则一堆 `+0/-0` 噪声。
- 风险分级 = **体量 × 是否核心源码**（核心且 ≥60 行 → 高），把「该找谁审」变成可自动化规则。
- PR 草稿四区块：变更明细、验证情况、需要关注、标签。
- **编译失败的 PR 必须打 `do-not-merge`** 并置顶「请勿合并」——人眼会漏，标签 + CI 不会。
- 新建文件用 `write_file`，补丁只改已有文件。
