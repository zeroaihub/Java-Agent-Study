# Chapter 18 · 评测体系：Pass@k 与四项分层指标

> 本章目标：用 Pass@1 / Pass@k 把「Agent 有多好」量化，掌握四个**分层**指标的定位价值，理解为什么「无从下手时明确失败」比硬编代码更有价值。

---

## 一、为什么要学（Why）

「我们的 Agent 成功率 90%」——这句话几乎没有任何信息量，除非你回答：

- 90% 是**一次就成**还是**重试 5 次后成**？（用户感受到的是前者）
- 失败的那 10% 是**补丁打不上**、**编译不过**，还是**测试没过**？
- 每次平均烧多少 token？

没有这些，你既无法判断该不该上线，也不知道该优化哪个模块。

还有一个更根本的问题：**「改了模型 / 改了提示词 / 改了上下文策略」之后，质量是变好了还是变坏了？** 没有评估集，这个问题只能靠「感觉」回答——而感觉在概率性系统里是不可靠的。

---

## 二、是什么（What）

### 2.1 Pass@k：无偏估计

跑了 `n` 次，成功 `c` 次，那么「随机抽 k 次至少成功一次」的概率是：

```
pass@k = 1 - C(n-c, k) / C(n, k)
```

```java
public double passAtK(int k) {
    int n = outcomes.size();
    int c = (int) succeededCount();
    if (n == 0 || k <= 0) return 0.0;
    if (k > n) k = n;
    if (n - c < k) return 1.0;        // 失败次数不够 k 个，必成功
    return 1.0 - (double) combinations(n - c, k) / combinations(n, k);
}
```

两个容易写错的地方：

1. **`k > n` 要夹紧**：否则 `C(n-c, k)` 越界返回 0，算出来 100%，虚假乐观；
2. **`n - c < k` 直接返回 1.0**：失败样本少于 k 个时，怎么抽都至少有一个成功。

> 为什么不用「至少成功一次的样本占比」这种直观算法？因为它是**有偏估计**：小样本下会系统性高估。上面的公式是无偏的。

### 2.2 四个分层指标

| 指标 | 衡量 | 下降时该查 |
| --- | --- | --- |
| **补丁应用率** | 准不准（补丁能不能打进去） | `context` 选错文件 / `patch` 片段不是当前内容 |
| **编译通过率** | 能不能跑 | `generator` 提示词 / `iterate` 轮次不够 |
| **测试通过率** | 对不对 | 语义理解有误，光靠语法验证救不了 |
| **平均 token** | 值不值 | 上下文塞太多 / 自修复失控 |

**这四个指标是分层的**：应用率 → 编译 → 测试，一层比一层深。任何一个掉下来都能直接定位到模块，而不是笼统地怪「模型不行」。

## 三、怎么用（How）

> 运行：`java -Dstdout.encoding=UTF-8 -cp target/classes com.zero.ai.agentstudy.day17codeagent.eval.Chapter18Demo`

### 3.1 单个任务

```
=== [1] 评测单个任务 ===
  T1 stub-code-model-1.0 | 补丁 1/1 | 编译 通过 | 测试 通过 | 修复 0 轮 | 1514 token | 645ms
  补丁应用率 = 100%  succeeded = true
```

每条 `TaskOutcome` 都带 `modelId`——**不同模型的结果不能混在一起算**。

### 3.2 一批任务的聚合

```
=== [2] 一批任务的聚合指标 ===
    T-multiply stub-code-model-1.0 | 补丁 1/1 | 编译 通过 | 测试 通过 | 修复 0 轮 | 1507 token | 119ms
    T-pay      stub-code-model-1.0 | 补丁 1/1 | 编译 通过 | 测试 通过 | 修复 0 轮 | 1178 token | 151ms
    T-discount stub-code-model-1.0 | 补丁 1/1 | 编译 通过 | 测试 通过 | 修复 0 轮 | 1262 token | 132ms
    T-unknown  stub-code-model-1.0 | 补丁 0/0 | 编译 失败 | 测试 失败 | 修复 0 轮 | 289 token  | 40ms | 输出无法解析为补丁

  EvalReport{样本 4, Pass@1=75.0%, Pass@3=100.0%, 补丁应用率=75.0%,
             编译通过率=75.0%, 测试通过率=75.0%, 平均 1059 token, 平均 0 轮}
  失败归因：
    1 × 输出无法解析为补丁

  → 注意最后一条：模型对「量子加密传输」这种无从下手的需求，
    返回了无法解析的回答。这比「硬编一段编译不过的代码」有价值得多。
```

最后一条任务 `T-unknown` 值得单独说：需求是「给订单服务加上量子加密传输」——**无从下手**。模型返回了无法解析的回答。

**这是好结果，不是坏结果。** 一个会硬编一段「看起来像量子加密」的代码的 Agent，比一个明确说「我做不了」的 Agent 危险得多——前者会把垃圾混进代码库，后者至少让你知道要人工介入。

### 3.3 Pass@k：同一个任务跑多次

```
=== [3] Pass@k：同一个任务跑多次 ===
    采样 1：失败（2 轮修复）
    采样 2：成功（0 轮修复）
    采样 3：成功（0 轮修复）
    采样 4：成功（0 轮修复）
    采样 5：成功（0 轮修复）
  n = 5, c = 4
  Pass@1 = 80.0%
  Pass@2 = 100.0%
  Pass@3 = 100.0%
  → Pass@1 才是用户实际感受到的成功率；
    Pass@k 与 Pass@1 差距越大，说明自修复循环越有价值。
```

**这组数据直接决定了 Ch13 的 `maxRepairRounds = 3`**：

- `Pass@1 = 80%` → 用户真实感受；
- `Pass@2 = 100%` → 第 2 轮就把剩下的 20% 全救回来了；
- `Pass@3 = 100%` → 第 3 轮**边际收益为零**。

所以给 3 轮（留一点余量）就够了，给 10 轮纯属烧钱。**参数不是拍脑袋定的，是算出来的。**

### 3.4 公式自检

```
=== [4] Pass@k 公式自检 ===
  C(5,3) = 10（应为 10）
  C(5,5) = 1（应为 1）
  C(3,5) = 0（越界应为 0）
```

组合数函数必须做越界自检——`C(3,5)` 返回 0 才能让 `passAtK` 的夹紧逻辑正确工作。

## 四、真实项目中的应用

| 课程实现 | 生产替换 |
| --- | --- |
| 4 条任务 + 5 次采样 | 上百条任务集，每条采样 5~20 次 |
| 桩模型 | 真实模型（成本要考虑进去！） |
| 内存聚合 | 评测样本落库 `eval_sample` 表（见 DATABASE.md） |
| 手动跑 | **进 CI 门禁**（见 EVALUATION.md 阈值） |

三个生产经验：

1. **评估集必须包含「无从下手」和「安全红线」样例**。只测正常需求，你会得到一个虚高的成功率，然后在真实场景里翻车。
2. **每次线上失败任务自动转成评测样本**（Ch20 `[5]`）。人工标注太慢，而每一次真实任务本身就是一份标注数据——这是持续提升的唯一可行路径。
3. **Pass@k 的采样成本很高**（k 次就要跑 k 遍）。实践中 Pass@1 + Pass@5 两个点通常够用。

## 五、避坑与优化

### 坑 1：把 Pass@k 当成用户感受
**后果**：对外宣称「成功率 100%」（其实是 Pass@5），用户实际体验 80%，信任崩塌。
**做法**：对外的数字永远是 **Pass@1**；Pass@k 只用于衡量改进空间。

### 坑 2：组合数越界返回错误值
**后果**：`C(3,5)` 若返回 1 而非 0，`passAtK` 会算出虚假的 100%。
**做法**：`k > n` 夹紧 + `combinations` 越界返回 0 + 单元自检。

### 坑 3：不同模型的结果混在一起
**后果**：换了模型后指标「变好」，其实只是样本构成变了。
**做法**：`modelId` 记入每条样本，报告按模型分组。

### 坑 4：评估集只有正常需求
**后果**：成功率虚高，真实场景翻车。
**做法**：覆盖正常 / 无从下手 / 安全红线 / 权限不足四类。

### 坑 5：不进 CI
**后果**：改了提示词悄悄回退，很久以后才发现。
**做法**：阈值门禁，且**阈值只升不降**。

### 优化建议
- **失败归因要自动分类**：「输出无法解析为补丁」这种归因能直接指向可优化的点。
- **把 token 成本换算成钱**：`平均 1059 token × 单价`，让「值不值」变成业务能理解的数字。

---

## 本章小结

- Pass@k 用无偏估计 `1 - C(n-c,k)/C(n,k)`；注意 `k>n` 夹紧与 `C(3,5)=0` 越界自检。
- **Pass@1 是用户真实感受**，Pass@k 只衡量改进空间；两者差距 = 自修复的价值。
- 实测 `Pass@1=80% → Pass@2=100% → Pass@3=100%`，**这就是 `maxRepairRounds=3` 的依据**——参数要算不要拍。
- 四项指标分层：补丁应用率（准不准）→ 编译通过率（能不能跑）→ 测试通过率（对不对）→ token（值不值），各自定位到具体模块。
- 「无从下手时明确失败」是好结果——比硬编一段编译不过的代码有价值得多。
- 评估集必须覆盖四类样例，且进 CI 门禁（阈值只升不降）。
